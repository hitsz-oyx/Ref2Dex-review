### 现在的数据逻辑

V1.1 已经改成 **每个 asset 各采 4096 点**。manipulated object 本身是 4096；每个 environment asset 也各自采 4096。不同 sequence 可以有不同数量的 asset，因此 full scene pool 不再要求固定 8192。每个 sequence 保存 `asset_offsets`、`scene_asset_id` 和 asset metadata。

例如：

```text
cup       0 ~ 4095
table     4096 ~ 8191
floor     8192 ~ 12287
...
```

然后针对当前 sample 对应的**一只手**计算：

[
\mathcal C_t=
{p_i:\min_j|p_i-h_j|\le 5cm}
]

再从所有 asset 的 candidate 中统一随机采：

[
\boxed{512}
]

模型完全不知道点属于 object 还是 environment。Sampling bank 已经升级为 `uint32 [T,B,512]`，invalid sentinel 是 `0xFFFFFFFF`，所以也不再受原来 uint16 的 scene-pool 上限约束。

### 左右手也符合你的要求

现在 sample 定义确实是：

[
\boxed{(sequence,\ side,\ current)}
]

Dataset 会分别遍历 `left` 和 `right` stream，但 `__getitem__` 只读取当前 `side` 的 hand 数据。因此：

```text
left sample:
512 scene + left 1538

right sample:
512 scene + right 1538
```

不存在 `1538 + 1538 = 3076` 的双手联合输入。

`dominant_hand_manifest` 在正式 V1.1 config 中也是 `null`，所以不再做主手/副手筛选。`active_only=true` 现在实际上就是：

> 这只手当前 5 cm 内至少有一个 scene candidate。

这正是我们最后定的规则。

### Cache 也基本按方案做完了

现在 DenseToken cache 已经是 sparse active-frame cache：

```text
dense_bank/right/
├── z_scene.npy
│   [T_active, B, 512, D]
├── z_hand.npy
│   [T_active, B, 1538, D]
├── hand_contact.npy
│   [T_active, B, 1538]
├── active_frame_id.npy
└── frame_to_dense.npy
```

而不是原来：

```text
[T, B, ...]
```

所有 inactive frame 不跑 DenseToken，也不占 feature cache。

而且 `build_dense_cache.py` 已经改成：

```python
np.lib.format.open_memmap(...)
```

边 forward、边写磁盘，不再把整条 sequence 的 feature 先 `np.empty` 到 RAM。所以 cache builder 的 RAM 从：

[
O(T)
]

变成：

[
O(batch).
]

最新提交还补了一个重要情况：

```text
某个 side 整条 sequence 都没有 candidate
```

比如真实 `cup_lift` 左手完全没 candidate。现在不会报错，而是创建：

```text
z_scene: [0,B,512,D]
z_hand:  [0,B,1538,D]

frame_to_dense[:] = -1
```

这正符合“左右手都保留，但没有有效 sample 的 side 自然贡献 0 个训练样本”。

# 现在我认为最大的剩余问题只有一个

就是 **DenseToken / spconv 非确定性**。

真实实验发现：

> 完全同一个输入，Frozen PTv3 连续 forward 两次，输出自己就不完全一致。

记录的最大差大约：

```text
z_scene max diff ≈ 1.68
z_hand  max diff ≈ 1.94
```

即使开 PyTorch deterministic，spconv implicit-GEMM CUDA kernel 仍然存在这个问题。

因此现在：

```text
online DenseToken
vs
cached DenseToken FP16
```

没办法满足原来设计的“严格数值 parity”。

但这里我现在**不建议因此卡住全量训练**。

因为目前这个 gate 定义得有点过严：

```text
cache vs online
```

本身就不可能比：

```text
online run A vs online run B
```

更一致。

正确的验证应该改成：

[
D_{OO}
======

D(
z_{\text{online},1},
z_{\text{online},2}
)
]

和：

[
D_{OC}
======

D(
z_{\text{online}},
z_{\text{cache}}
)
]

比较。

如果：

[
\boxed{
D_{OC}
\approx D_{OO}
}
]

那 cache 没引入额外问题，只是忠实保存了某一次合法的 spconv forward。

更重要的是直接测 downstream：

```text
同一批 samples

online feature → Cm → flow
cached feature → Cm → flow
```

比较：

[
\Delta EPE
]

而不是死盯 feature element-wise max error。

如果最终：

```text
online-online downstream variance ≈ online-cache variance
```

那我会直接接受 Dense cache，然后开全量。
