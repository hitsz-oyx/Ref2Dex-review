可以。按你这 4 点，我建议把当前实现改成 **Cm Scene Cache V1.1**。核心原则是：

[
\boxed{
\text{每个资产各采 4096 点}
\rightarrow
\text{当前单手 5cm crop}
\rightarrow
\text{统一随机采 512}
\rightarrow
Cm
}
]

模型和 loss 都不改；左右手都用，但**一个 sample 永远只有一只手的 1538 点**。

# 1. 数据定义重新统一成 Asset Scene

对每条 GRAB sequence，定义资产集合：

[
\mathcal A=
{
A_{\text{manipulated}},
A_{\text{env},1},
A_{\text{env},2},
...
}
]

每个资产都固定采：

[
\boxed{N_A=4096}
]

个 surface points。

例如：

```text
cup        → 4096
table      → 4096
floor      → 4096
other env  → 4096
```

如果这个 sequence 只有：

```text
cup + table
```

那么 scene pool：

[
N_{\text{pool}}=8192.
]

如果以后有：

```text
cup + table + floor
```

则：

[
N_{\text{pool}}=12288.
]

**不再要求所有 sequence 的 full scene pool 大小相同。**

因为模型根本看不到完整 pool，最终永远只输入 512 点。

这需要修改当前 V1 的一个假设：现在 `cache_schema.py` 会要求所有 sequence 的 scene pool size 一致。

---

# 2. 每个 asset 必须保持跨时间点对应

对于 asset (a)：

[
P_a^{cano}\in\mathbb R^{4096\times3}
]

固定一次 surface sampling。

每一帧：

[
P_{a,t}^{world}
===============

R_{a,t}P_a^{cano}+T_{a,t}.
]

因此：

```text
asset #2 point #157
```

在：

```text
t
t+1
t+5
```

永远是同一个 canonical surface point。

这样被选中的 scene index 才可以直接算：

[
\Delta p_i
==========

p_{i,t+s}-p_{i,t}.
]

对于 static environment：

[
p_{i,t+s}=p_{i,t}
]

自然：

[
\Delta p_i=0.
]

不用额外 environment loss。

---

# 3. 当前手附近统一做 5cm crop

对某个 sample：

[
(sequence,\ side,\ t)
]

只取**这个 side 的手**：

[
H_t^{side}\in\mathbb R^{1538\times3}.
]

整个 scene：

[
P_t=
P_{A_1,t}\cup P_{A_2,t}\cup\cdots
]

统一计算：

[
\mathcal C_t=
\left{
i:
\min_j|p_{t,i}-h_{t,j}|
\le0.05
\right}.
]

这里完全不区分：

```text
object
table
floor
background asset
```

然后继续使用当前 Cm 的采样逻辑：

```python
selected_idx, valid = sample_object_indices(
    candidate,
    num_samples=512,
    seed=seed,
)
```

也就是说：

* candidate > 512：随机下采样 512；
* candidate < 512：**继续保持现在 `sample_object_indices` 的 padding/valid-mask 语义，不另造规则**。

这一点可以保证和旧 Cm 的数据行为尽量一致。

# 4. 模型看到的永远只是 512 个 Scene Points

最终：

[
P_t^{input}\in\mathbb R^{512\times3}
]

模型不知道：

```text
point 0 是 cup
point 1 是 table
point 2 是 floor
```

输入仍然：

```text
obj_points      [512,3]
obj_normals     [512,3]

hand_points     [1538,3]
hand_normals    [1538,3]
hand_flow       [1538,3]
```

所以当前 `CmFlowModel` 根本不用改结构。它现在本来就固定接受 `512 + 1538`。

第一版继续保留旧变量名：

```python
obj_points
z_obj
pred_obj_flow
```

只是实际语义变成：

```text
local scene points
scene token
scene flow
```

# 5. 左右手：都训练，但绝不拼成 3076 点

这点按你的意思明确改。

数据单位：

[
\boxed{
sample=(sequence,\ side,\ current)
}
]

所以同一帧可以产生：

```text
sample A:
side = left
hand_points = left 1538

sample B:
side = right
hand_points = right 1538
```

但**绝不存在**：

```text
left 1538 + right 1538 = 3076
```

送进模型。

数据结构：

```text
sequence
├── left stream
│   └── 每个 sample 输入 Left MANO 1538
│
└── right stream
    └── 每个 sample 输入 Right MANO 1538
```

这样 Frozen DenseToken 的：

[
512+1538
]

合同保持完全不变。

# 10. Candidate Index 改成 uint32

当前 Sampling Bank：

```text
uint16
INVALID_INDEX = 0xFFFF
```

如果未来 asset 数量增加：

[
4096\times16=65536
]

刚好就越界了。

既然我们这次已经允许：

[
N_{assets}
]

变化，我建议直接一次改成：

```python
uint32
INVALID_INDEX = 0xFFFFFFFF
```

Sampling Bank：

```text
[T, B, 512] uint32
```

多占的空间很小：

原来每 frame，B=4：

[
4\times512\times2=4KB
]

现在：

[
4\times512\times4=8KB.
]

完全值得。


## 最终定义

这版我认为可以明确写成：

[
\boxed{
\begin{aligned}
&\text{每个资产 surface sample }4096\
&\downarrow\
&\text{组成 variable-size scene pool}\
&\downarrow\
&\text{针对当前单手 }H_t^{side}\text{ 做 5cm crop}\
&\downarrow\
&\text{随机选择 512 scene points}\
&\downarrow\
&(P_t^{512},H_t^{1538},\Delta H_t,\Delta t)\
&\downarrow\
&C_m\
&\downarrow\
&\hat{\Delta P}^{512}
\end{aligned}
}
]

左右手的关系则是：

```text
同一 sequence

Left:
scene + Left1538 → one sample

Right:
scene + Right1538 → another sample
```

**不是双手联合输入，而是双手数据都用于训练同一个单手条件模型。**

我认为这比当前 V1 更干净：既保住当前 DenseToken 的 `512+1538` 输入合同，又把数据量从 dominant-hand subset 扩展到左右手全部有效 interaction，同时 scene 表示真正升级成了任意数量资产。
