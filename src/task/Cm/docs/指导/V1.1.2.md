我现在的判断是：

[
\boxed{\text{前两层 cache 值得，DenseToken 全量 cache 暂时不值得}}
]

原因很直接。

当前 DenseToken cache 对每个 `(sequence, side, active frame)` 要存 4 个 sampling bank，而且 token dim 在真实 smoke 里是 96。 单个 active frame 大约需要：

[
4\times
(512\times96+1538\times96+1538)\times2\text{ bytes}
\approx1.51\text{ MiB}.
]

因此大致是：

```text
10 万 active frame   ≈ 148 GiB
20 万 active frame   ≈ 296 GiB
50 万 active frame   ≈ 739 GiB
100 万 active frame  ≈ 1.48 TiB
```

真实 `cup_lift` 单边 764 个 active frame，就已经大约是 **1.1 GiB Dense cache**。全 GRAB 做下去非常容易到几百 GB 甚至 TB 级别。

而且它还有三个问题。

第一，**生成 cache 本身要跑完整 Frozen PTv3**。B=4 就意味着每个 active current state 要跑 4 次 DenseToken。你只是把：

```text
训练时算 PTv3
```

提前搬成：

```text
训练前集中算 PTv3
```

只有在后续反复训练很多 epoch、很多组 Cm ablation 时，这个一次性成本才容易摊回来。

第二，训练时不是“零成本”。现在每个 sample 要随机从磁盘读大约：

[
1.51/4\approx0.38\text{ MiB}
]

的一组 bank feature。batch=8 就是约 3 MB 随机 feature IO，再加其他数据。整个 dense bank 如果几百 GB，OS page cache 不可能全放内存，全局 shuffle 下 NVMe 读盘本身也可能变成瓶颈。

第三，也是目前最不舒服的一点：**spconv 自己存在 nondeterminism（同输入重复运行也有数值差异）**，所以这个巨大的 cache 还不能带来严格可复现的 DenseToken representation。

所以它的收益没有我之前预想得那么漂亮。

---

## 我建议重新把三级 cache 改成两级正式方案

保留：

```text
Level 1
Scene geometry mmap

Level 2
5cm ragged candidates
+
B=4 sampling bank
```

去掉正式训练默认的：

```text
Level 3
DenseToken feature bank
```

也就是：

```text
raw GRAB
   ↓ 一次
scene mmap
   ↓
ragged 5cm candidate
   ↓
B=4 sampling indices
   ↓
训练时快速取 512 points
   ↓
online Frozen DenseToken
   ↓
Cm
```

前两层 cache 我认为**非常值得**。

因为它们把真正重复、没有学习价值的 CPU 工作拿掉了：

* raw `.npz` 解析；
* MANO reconstruction；
* mesh surface sampling；
* asset pose transform；
* scene 组织；
* hand-scene 5cm `cdist`；
* 每帧 candidate 搜索。

而且磁盘占用相对很小。

Sampling bank 本身每帧：

[
4\times512\times4=8192\text{ bytes}
]

也就是 **8 KB/frame/side**，几乎可以忽略。

这才是“高性价比 cache”。
