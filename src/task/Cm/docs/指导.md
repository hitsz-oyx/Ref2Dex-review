我检查了当前 `oyx` 分支代码，并解析了完整训练日志到 `step=58000、epoch=80`。

## 总体结论

当前训练**没有坍缩成全零预测**。相反，出现了另一种坍缩：

[
\boxed{\text{16 个动态 slot 几乎全部永久开启}}
]

同时：

[
\boxed{\text{decoder 基本平均使用全部 16 个动态 slot 和 null slot}}
]

也就是说，点流预测已经学得很好，但“动态减少 slot 数量”和“slot 专门化”目前没有学出来。

---

## 1. 点流没有坍缩，训练本身收敛正常

从 epoch 4 到 epoch 79：

| 指标             |             epoch 4 |         epoch 79 |
| -------------- | ------------------: | ---------------: |
| `flow_mse`     | (9.57\times10^{-4}) | (7\times10^{-6}) |
| GT flow norm   |           0.04182 m |        0.04159 m |
| Pred flow norm |           0.02674 m |        0.04139 m |

后期预测流幅值已经基本追上真实流幅值：

[
\frac{|\hat F|}{|F^{GT}|}
\approx
\frac{0.04139}{0.04159}
\approx 0.995
]

所以不存在：

```text
所有样本 → null
所有预测 → 0
```

这种坍缩。

---

## 2. gate 已经坍缩成“全部开启”

训练初期：

```text
epoch 4:
expected_active_mean ≈ 15.79
sampled_active_mean ≈ 15.77
gate_probability_mean ≈ 0.9869
```

训练后期：

```text
epoch 79:
expected_active_mean ≈ 15.9998
sampled_active_mean ≈ 16.0000
gate_probability_mean ≈ 0.999991
```

这说明模型没有尝试减少 slot，反而越来越确信所有 slot 都需要开启。

### 直接原因一：slot 数量损失太弱

当前代码是：

```python
slot_count_loss = slot_nonzero_prob.mean()
```

因此它的范围始终是：

[
0\leq \mathcal L_{\text{count}}\leq1
]

配置中：

```python
loss_slot_count_weight = 1e-3
```

即使 16 个 slot 全开，对总损失的贡献也只有：

[
10^{-3}\times1=0.001
]

日志后期：

```text
flow_smooth_l1 ≈ 0.03
slot count contribution ≈ 0.001
```

早期 `flow_smooth_l1` 甚至在 1～3 之间，数量损失更可以忽略。当前 Runner 和配置确实采用了这一计算方式。

更符合“每使用一个 slot 都付出代价”的写法应该是：

```python
slot_count_loss = (
    slot_nonzero_prob.sum(dim=-1)
).mean()
```

此时损失代表真正的预期 slot 数：

[
\mathcal L_{\text{count}}
=========================

\mathbb E[K_{\text{active}}]
]

仍使用：

```yaml
loss_slot_count_weight: 1.0e-3
```

全开时惩罚就会变成：

[
16\times10^{-3}=0.016
]

比现在强 16 倍，而且系数语义更清楚：

> 每开启一个 slot，损失增加约 0.001。

---

## 3. gate 初始化也过于接近全开

当前 gate 最后一层初始化为：

```python
weight = 0
bias = 2.0
```

Hard-Concrete 的非零概率为：

[
P(g_k>0)
========

\sigma
\left(
\log\alpha_k
------------

\beta\log\frac{-\gamma}{\zeta}
\right)
]

使用当前参数时，`bias=2` 对应初始非零概率大约为：

[
P(g_k>0)\approx0.973
]

即训练一开始预期就有：

[
16\times0.973\approx15.6
]

个 slot 开启，与日志完全一致。

随后流损失继续推动 gate 变大，最终概率逼近 1。概率接近 1 后：

[
\frac{\partial p}{\partial\log\alpha}
=====================================

p(1-p)
]

也接近 0，数量损失很难再把它拉回来。

下一次从头训练建议改成：

```python
nn.init.zeros_(self.slot_gate_head[-1].weight)
nn.init.zeros_(self.slot_gate_head[-1].bias)
```

此时初始非零概率约为：

[
0.832
]

预期约 13.3 个 slot，仍然保留大部分容量，但不至于一开始就完全饱和。

---

## 4. 当前 flat softmax 本身就在奖励“多开 slot”

这是比损失权重更深一层的问题。

当前代码将：

```text
null slot
16 个经过 gate 的动态 slot
```

直接拼在一起做一次 17 路 softmax。

假设：

* null logit 为 0；
* 所有动态 slot logit 也为 0；
* 动态候选流都近似相同，为 (\mathbf f)；
* 当前开启了 (K) 个动态 slot。

那么：

[
w_{\text{null}}=\frac{1}{K+1}
]

动态 slot 总权重为：

[
\sum_{k=1}^{K}w_k
=================

\frac{K}{K+1}
]

最终预测近似：

[
\hat{\mathbf f}
===============

\frac{K}{K+1}\mathbf f
]

当：

```text
K = 1  → dynamic mass = 0.5
K = 4  → dynamic mass = 0.8
K = 16 → dynamic mass = 0.941
```

所以在动态候选流还没有充分调整时：

> 多打开 slot，可以自动降低 null 对点流幅值的稀释。

这会让 flow loss 天然推动：

[
K\rightarrow16
]

日志中 null 后期使用率约为 0.051，恰好接近：

[
\frac{1}{17}\approx0.0588
]

这表明 null 与其他 slot 基本仍处于接近均匀混合状态。

### 推荐解决方式

不要直接使用一个平面的 17 路 softmax，而是改成两级混合：

第一层决定：

```text
使用 null
还是使用 dynamic slots
```

第二层只在 active dynamic slots 内做 softmax：

[
q_{ik}
======

\operatorname{softmax}*{k\in\mathcal A}
(l*{ik})
]

然后：

[
\hat{\mathbf f}_i
=================

p_{i,\text{null}}\mathbf f_{i,\text{null}}
+
(1-p_{i,\text{null}})
\sum_{k\in\mathcal A}
q_{ik}\mathbf f_{i,k}
]

这样动态分支的总质量始终是：

[
1-p_{\text{null}}
]

不会因为开启 1 个还是 16 个 slot 而改变。

null token 仍然：

* 来自 Slot Attention；
* 有自己的手点 assignment；
* 有自己的候选流；
* 接受零流监督。

只是 null 与 dynamic 的竞争不再受到 active slot 数量的隐式影响。

---

## 5. null 的零流监督已经成功

日志中：

```text
epoch 4:
null candidate flow norm ≈ 0.01015 m

epoch 79:
null candidate flow norm ≈ 0.000266 m
```

也就是 null 候选流已经从约 10 mm 降到约 0.27 mm。

当前：

```yaml
loss_null_zero_weight: 0.05
```

看起来是有效的，没有必要增加。

null decoder usage 也从约 11% 降至约 5.1%，所以 null 没有吞掉最终预测。

因此：

[
\boxed{\text{null zero loss 当前可以保持不变}}
]

---

## 6. 但 null 的手部 assignment 很异常

null 的手点分配质量从：

```text
epoch 4:  null assignment mass ≈ 0.206
epoch 79: null assignment mass ≈ 0.640
```

也就是说，后期大约 64% 的手点 assignment 概率被 null slot 吸收。

但 null 在 decoder 中只使用约 5%。

表现为：

```text
手部 Slot Attention：
null 占据大部分手点

物体点流解码：
null 基本不使用
```

这是明显的解耦。

原因在当前 Slot Attention 归一化方式：

```python
slot_assignment = softmax(logits, dim=slot)

slot_weights = (
    slot_assignment
    / slot_assignment.sum(dim=hand_point)
)
```

即使某个动态 slot 只分到很少的总 assignment mass，后面仍然会在手点维重新归一化成和为 1 的分布。因此 null 吸收 64% 的 assignment，并不会等比例削弱其他 slot 的更新。

从预测性能看，这暂时没有造成灾难；但它说明：

> `null_assignment` 现在不能解释为“真正无作用的手部区域”。

null 的零流监督只约束它的候选流，并没有约束它应该聚合哪些手点。

若你不强调 null 的手部可解释性，可以暂时接受。如果希望 null assignment 有实际语义，就需要进一步设计 assignment 约束，不能只靠零流监督。

---

## 7. decoder 没有形成 slot 专门化

后期：

```text
decoder_slot_usage_entropy ≈ 2.828
```

17 路均匀分布的最大熵为：

[
\log17\approx2.833
]

对应有效使用分支数约为：

[
\exp(2.828)\approx16.9
]

也就是说 decoder 几乎在平均使用全部 17 个分支。

后期每个动态 slot 的 usage 基本都在：

```text
0.055 ～ 0.063
```

null 约：

```text
0.051
```

所以模型目前很可能学成：

```text
每个动态 slot 都预测相似的完整物体流
→ decoder 将它们平均
```

而不是：

```text
不同 slot 负责不同手部区域或不同运动效果
```

这也解释了为什么关闭 slot 会损害结果：虽然 slot 是冗余的，但网络已经把输出幅值建立在“很多相似分支共同平均”上。

## 8. 零初始化加重了 decoder 的均匀问题

当前 `flow_edge` 最后一层：

```python
nn.init.zeros_(weight)
nn.init.zeros_(bias)
```

它同时输出：

```text
1 个 decoder logit
3 个候选 flow 分量
```

初始化时所有 slot 都有：

[
l_k=0,\qquad \mathbf f_k=0
]

这时 softmax 完全均匀，并且 logit 的梯度为：

[
\frac{\partial\hat{\mathbf f}}
{\partial l_k}
==============

w_k(\mathbf f_k-\hat{\mathbf f})
=0
]

因此初始阶段 decoder logit 几乎学不到选择行为，所有候选 flow 先以相似方向更新，容易维持均匀混合。

建议将 logit 和 flow 输出拆开：

```python
self.edge_backbone = ...
self.edge_logit_head = nn.Linear(hidden_dim, 1)
self.edge_flow_head = nn.Linear(hidden_dim, 3)
```

初始化：

```python
nn.init.normal_(
    self.edge_logit_head.weight,
    std=1e-3,
)
nn.init.zeros_(
    self.edge_logit_head.bias,
)

nn.init.zeros_(
    self.edge_flow_head.weight,
)
nn.init.zeros_(
    self.edge_flow_head.bias,
)
```

这样点流仍从零开始，但 decoder 权重不再完全对称。

# 我建议下一轮按这个优先级修改

## 第一优先级：修复 slot 数量损失

```python
slot_count_loss = (
    slot_nonzero_prob.sum(dim=-1)
).mean()
```

保持：

```yaml
loss_slot_count_weight: 1.0e-3
```

并将 gate bias 从 `2.0` 改成 `0.0`。

## 第二优先级：消除 null 与 active count 的耦合

将 17 路 flat softmax 改成：

```text
null vs dynamic
        ↓
active dynamic slots 内部 softmax
```

这是当前最重要的架构修正。

## 第三优先级：拆开 decoder logit 与 flow head

避免全零初始化导致所有专家长期平均使用。

## 暂时不要加入

```text
active overlap loss
assignment entropy loss
decoder usage entropy loss
```

当前根本问题不是 slot 重叠惩罚不够，而是：

1. gate 数量惩罚太弱；
2. flat softmax 奖励更多 active slot；
3. decoder 初始化和结构允许所有 slot 预测相同结果。

先修这三点，再观察 overlap。
