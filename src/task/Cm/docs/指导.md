可以。当前先取消所有 warmup，用单阶段训练直接观察是否出现“全部 gate 关闭 + null 占满 + 点流全零”的坍缩，更容易判断架构本身是否成立。

不过你提出的 null 设计需要稍微区分：

> **null slot 可以像普通 slot 一样从手部特征中产生，也可以使用相同的点流解码器；但必须给它固定身份，并额外监督它的候选点流接近零。**

这时它更准确地叫 `no_effect_slot`，即“无作用 slot”，因为它不再被硬编码为严格零流。

# 1. 推荐的新结构

建议配置语义改成：

```text
16 个动态 slot
+ 1 个始终存在的 null slot
= Slot Attention 总共输出 17 个 slot
```

其中：

* 前 16 个动态 slot：使用 Hard-Concrete gate；
* 第 17 个 null slot：始终开启，不参与 gate；
* 17 个 slot 都通过相同的点流解码器；
* null slot 的候选点流额外受到零流监督；
* 最终 17 个分支共同进行 softmax 加权解码。

当前 Slot Attention 本身使用每个索引独立的可学习初始化向量 `slot_init[1,K,D]`，因此可以稳定地把最后一个初始化向量指定为 null，而不是完全无法区分的随机 slot。

建议代码语义明确写成：

```python
self.num_dynamic_slots = 16
self.num_total_slots = self.num_dynamic_slots + 1
self.null_slot_idx = self.num_dynamic_slots

self.slot_attention = SlotAttention(
    dim=cm_dim,
    num_slots=self.num_total_slots,
    num_iterations=num_slot_iters,
)
```

前向传播：

```python
all_tokens, all_assignment, all_slot_weights = self.slot_attention(
    u_hand
)

dynamic_tokens = all_tokens[:, :self.num_dynamic_slots]
null_token = all_tokens[:, self.null_slot_idx:self.null_slot_idx + 1]

dynamic_assignment = all_assignment[:, :self.num_dynamic_slots]
null_assignment = all_assignment[:, self.null_slot_idx:self.null_slot_idx + 1]
```

gate 只预测动态 slot：

```python
slot_gate_logits = self.slot_gate_head(
    dynamic_tokens
).squeeze(-1)

dynamic_gate, dynamic_nonzero_prob = self.hard_concrete(
    slot_gate_logits
)
```

# 2. null 和其他 slot 使用同一个解码器

17 个 slot 都构造相同的 edge feature：

```python
edge_input = torch.cat(
    [
        obj_context.unsqueeze(2).expand(
            -1, -1, self.num_total_slots, -1
        ),
        all_tokens.unsqueeze(1).expand(
            -1, num_obj, -1, -1
        ),
        relative,
        anchor_normal.unsqueeze(1).expand(
            -1, num_obj, -1, -1
        ),
    ],
    dim=-1,
)

edge_output = self.flow_edge(edge_input)
```

输出：

```python
all_logits = edge_output[..., 0]   # [B, O, 17]
all_flow = edge_output[..., 1:]    # [B, O, 17, 3]
```

然后拆分：

```python
dynamic_logits = all_logits[..., :16]
dynamic_flow = all_flow[..., :16, :]

null_logits = all_logits[..., 16:17]
null_flow = all_flow[..., 16:17, :]
```

这样 null：

* 和其他 slot 一样从手部特征产生；
* 有自己的手部 assignment；
* 有自己的 anchor；
* 有自己的逐物体点 logit；
* 有自己的候选点流；
* 只是始终不会被 gate 关闭。

这符合你说的“它是一个底线，但仍然是正常 slot”。

# 3. null 候选流使用零流监督

不再写死：

```python
null_flow = 0
```

而是增加：

[
\mathcal L_{\text{null-zero}}
=============================

\operatorname{SmoothL1}
\left(
\mathbf f_{\text{null}},
\mathbf 0
\right)
]

代码可以直接复用现有尺度一致的损失：

```python
null_flow_m = null_flow.squeeze(2)

null_zero_loss = internal_flow_smooth_l1(
    null_flow_m,
    torch.zeros_like(null_flow_m),
    valid,
    beta_m=float(self.cfg.meta.flow_smooth_l1_beta),
    internal_scale=float(
        self.cfg.meta.internal_point_flow_scale
    ),
)
```

总损失：

[
\boxed{
\mathcal L
==========

\mathcal L_{\text{flow}}
+
\lambda_{\text{count}}\mathcal L_{\text{count}}
+
\lambda_{\text{null}}\mathcal L_{\text{null-zero}}
}
]

第一轮可以采用：

```yaml
loss_slot_count_weight: 1.0e-3
loss_null_zero_weight: 0.05
loss_active_overlap_weight: 0.0
```

`loss_null_zero_weight` 建议先从 `0.01～0.1` 试，不要一开始设成 `1.0`。

---

# 4. 为什么 null zero loss 不能过大

因为当前 `flow_edge` 是所有 slot 共享的。

也就是说：

```text
动态 slot
null slot
```

都经过同一套 MLP 和最后线性层。

当你最小化：

```text
null_flow → 0
```

这个梯度不仅会改变 null token，也会改变共享的 `flow_edge` 参数，因此可能间接将所有动态 slot 的流也压小。

这不是一定会发生，因为 decoder 还可以根据不同 token 输出不同结果，但这是最主要的潜在风险。

第一版可以保持完全共享，代码最简洁；若实际出现：

```text
null_flow 接近 0
dynamic_flow 也全部接近 0
pred_flow_norm 远低于 gt_flow_norm
```

再只拆分最后的 flow projection：

```text
共享 edge backbone
├── dynamic_flow_head
└── null_flow_head
```

不需要一开始就增加这种复杂度。

# 5. 最终混合方式

对动态 slot 使用 gate，null 始终存在：

```python
dynamic_gate = dynamic_gate[:, None, :]  # [B, 1, 16]

gated_dynamic_logits = (
    dynamic_logits
    + torch.log(dynamic_gate.clamp_min(1e-12))
)

gated_dynamic_logits = gated_dynamic_logits.masked_fill(
    dynamic_gate == 0,
    -torch.inf,
)

mixture_logits = torch.cat(
    [null_logits, gated_dynamic_logits],
    dim=2,
)

mixture_flow = torch.cat(
    [null_flow, dynamic_flow],
    dim=2,
)

mixture_weight = torch.softmax(
    mixture_logits,
    dim=2,
)

pred_obj_flow_internal = (
    mixture_weight.unsqueeze(-1)
    * mixture_flow
).sum(dim=2)
```

这时：

* 其他 slot 都关闭时，null 权重自动为 1；
* 动态 slot 置信度较低时，null 会占更大权重；
* 动态 slot 有足够证据时，可以压过 null；
* null 流不是严格零，但受到零流监督；
* null 和动态 slot 可以共同混合。

当前代码只用 `clamp_min(1e-8)`，关闭的 slot 理论上仍可能取得极小但非零权重，建议增加上面的 `masked_fill(..., -inf)`。

# 6. 不使用 warmup 时的初始化

取消 warmup 没问题，但 gate 最好初始化为倾向开启。这不是阶段训练，只是初始状态。

```python
nn.init.zeros_(
    self.slot_gate_head[-1].weight
)
nn.init.constant_(
    self.slot_gate_head[-1].bias,
    2.0,
)
```

这样训练开始时大部分动态 slot 都可以工作，之后固定的 (L_0) 数量损失逐渐淘汰不必要的 slot。

null 不需要特殊 logit 初始化。当前 `flow_edge` 最后一层全零初始化，因此初始 17 个 logit 都接近 0，null 初始权重大约只是 (1/17)，不会一开始独占输出。当前代码确实将 `flow_edge` 最后一层权重和偏置全部初始化为零。

取消以下全部字段即可：

```python
slot_gate_warmup_ratio
slot_count_warmup_ratio
null_warmup_ratio
null_warmup_logit
gate_warmup_progress
null_warmup_progress
effective_slot_nonzero_prob
```

Runner 直接：

```python
prediction = model(batch)

slot_count_loss = (
    prediction["slot_nonzero_prob"].mean()
)

total_loss = (
    loss_flow_weight * flow_smooth_l1
    + loss_slot_count_weight * slot_count_loss
    + loss_null_zero_weight * null_zero_loss
)
```

# 7. null 进入 Slot Attention 的潜在行为

null 与其他 slot 一起参加手点分配竞争：

[
\sum_{k=1}^{17}
A_{k,h}=1
]

这意味着 null 可能聚合：

```text
手在运动，但没有对物体产生作用的区域
```

这其实有合理语义。例如：

```text
小指在移动
但真正推动物体的是拇指和食指
```

null 可以吸收小指附近的手点，动态 slot 负责真正产生作用的区域。

但风险是 null 吸收过多手点，导致动态 slot 得不到足够信息。因此需要记录：

```python
null_assignment_mass = (
    null_assignment.mean()
)
```

理想情况下：

* null 可以占一部分；
* 不应在所有运动样本中都接近 1；
* 运动明显时，动态 slot 仍应获得明确区域。

如果以后观察到：

```text
null_assignment_mass > 0.8
decoder_null_usage > 0.8
pred_flow_norm << gt_flow_norm
```

才说明 null 发生了整体坍缩。

# 8. 当前还应修正的逻辑问题

## Gate 只稀疏了解码，没有稀疏 Slot Attention

当前所有动态 slot 都先参与 Slot Attention，之后才 gate。

所以被关闭的 slot：

* 仍然参与手点竞争；
* 仍然吸收一部分 assignment；
* 仍然被完整计算；
* 只是最后不参与点流混合。

因此当前实现严格来说学到的是：

> **动态 decoder slot 数量**

而不是：

> **真正只使用少数 slot 完成手部表征。**

第一版可以接受，但解释实验结果时需要明确这一点。先验证 decoder sparsity 是否有效，再决定是否把 gate 放进 Slot Attention 内部。

## `hard_active_count` 指标命名错误

当前使用：

```python
hard_active_count = (
    slot_nonzero_prob > 0.5
).sum(...)
```

这统计的是“概率阈值数量”，不是训练时实际采样的 Hard-Concrete gate。

应该分别记录：

```python
expected_active_count = (
    slot_nonzero_prob.sum(dim=-1)
)

sampled_active_count = (
    slot_gate > 0
).sum(dim=-1)
```

当前 Runner 将概率阈值统计命名为 `hard_active`，容易误判。

## decoder usage entropy 需要重新归一化

加入 null 后，动态 usage 的总和是：

[
1-u_{\text{null}}
]

不是 1。

当前代码直接对动态 usage 求熵，因此熵值同时受 null 使用率影响。

可以计算完整 17 类熵：

```python
full_usage = torch.cat(
    [
        decoder_null_usage[:, None],
        decoder_slot_usage,
    ],
    dim=-1,
)

usage_entropy = -(
    full_usage.clamp_min(1e-8)
    * full_usage.clamp_min(1e-8).log()
).sum(dim=-1).mean()
```

或者只计算动态分支内部熵：

```python
dynamic_usage = (
    decoder_slot_usage
    / decoder_slot_usage.sum(
        dim=-1,
        keepdim=True,
    ).clamp_min(1e-8)
)
```

这些仍然只作为日志，不参与反传。

## 提取脚本仍会错误处理 `shared.npz`

当前目录扫描：

```python
source.glob("**/*.npz")
```

会同时获得：

```text
shared.npz
left.npz
right.npz
```

而 Dataset 只接受 `left.npz` 和 `right.npz`。

应只扫描：

```python
inputs = sorted([
    *source.glob("**/left.npz"),
    *source.glob("**/right.npz"),
])
```

同时导出元信息时，需要从 `shared.npz` 读取 `seq_id`、`object_name` 等字段。

## Stage 4 直接固定当前合同即可

既然不考虑旧数据兼容，可以直接规定：

```python
ds_rate = 4
effective_fps = 30 Hz
min_stride = 1
max_stride = 10
```

当前 `prepare_cm.py` 的 `--ds-rate` 默认仍是 1，Dataset 构造函数的 `max_stride` 默认仍是 12；虽然训练配置会覆盖，但容易误运行。

建议直接改成：

```python
--ds-rate default=4
max_stride default=10
```

不需要保留旧 schema 或迁移逻辑。

# 9. 第一轮训练建议

第一版采用：

```text
16 dynamic slots
+ 1 learned no-effect slot
+ Hard-Concrete
+ no warmup
+ no overlap loss
```

损失：

```yaml
loss_flow_weight: 1.0
loss_slot_count_weight: 1.0e-3
loss_null_zero_weight: 0.05
loss_active_overlap_weight: 0.0
```

重点记录：

```text
flow_mse
gt_flow_norm
pred_flow_norm

slot/expected_active_mean
slot/sampled_active_mean

null/candidate_flow_norm
null/decoder_usage
null/assignment_mass
```

坍缩的典型特征是：

```text
pred_flow_norm / gt_flow_norm 持续接近 0
null/decoder_usage 持续接近 1
slot/sampled_active_mean 持续接近 0
```

训练前还应统计数据中的实际静止比例，而不是只凭直觉判断：

[
\operatorname{mean}_i
|\mathbf f_i^{GT}|
<
1\text{ mm},\ 2\text{ mm},\ 5\text{ mm}
]

分别占多少。当前 `active_only=true` 只保证当前帧存在 5 cm 内的物体候选点，并不保证未来物体一定运动；配置中也明确保留静止目标用于学习“无作用交互”。

整体上，你提出的“可学习 null slot + 零流监督”是可行的。第一版最重要的是让 null **始终存在但不参与数量惩罚**，并将它的 assignment、候选流和 decoder usage 单独监控。
