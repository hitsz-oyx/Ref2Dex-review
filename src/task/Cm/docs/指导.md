# 仍需修复的主要问题

## 1. metadata 校验还不够完整

当前 Runner 已经检查：

```python
flow_target_rms_m * object_flow_target_scale ≈ 1
```

并检查：

```python
config.object_flow_target_scale
==
metadata.flow_target_scale
```

这是有效的改进。

但是统计 scale 不仅取决于数据目录，还取决于：

```text
min_stride
max_stride
active_only
num_obj_points
stride weighting
```

统计脚本已经保存这些信息，但 Dataset 目前只传播：

```text
statistics_num_obj_points
statistics_point_weighting
```

没有传播：

```text
statistics_active_only
statistics_stride_distribution
statistics_stride_weighting
```

而且 Runner 对已经传播的 `statistics_num_obj_points` 也没有实际比较。 

因此这种错误仍可能通过：

```text
metadata 是按 stride 1～5 统计的
训练配置使用 stride 1～10
YAML 仍手工复制了 metadata 中的旧 scale
```

配置和 metadata 的 scale 数字一致，所以当前检查不会报错，但统计分布已经不匹配。

建议在 Dataset metadata 中同时传播：

```python
for key in (
    "flow_target_rms_m",
    "flow_target_scale",
    "statistics_split",
    "statistics_active_only",
    "statistics_num_obj_points",
    "statistics_stride_distribution",
    "statistics_stride_weighting",
    "statistics_point_weighting",
):
    ...
```

然后 Runner 增加：

```python
expected_distribution = (
    f"uniform_{self.cfg.data.min_stride}"
    f"_to_{self.cfg.data.max_stride}"
)

if metadata["statistics_stride_distribution"] != expected_distribution:
    raise ValueError(...)

if bool(metadata["statistics_active_only"]) != bool(self.cfg.data.active_only):
    raise ValueError(...)

if int(metadata["statistics_num_obj_points"]) != int(self.cfg.meta.num_obj_points):
    raise ValueError(...)
```

这是当前最值得继续补的一项。

## 2. `active_only=False` 的统计逻辑不匹配 Dataset

统计脚本当前只有在：

```python
if active_only:
    flow = flow[candidate]
```

时才选择 5 cm 候选点。也就是说设置 `--include-inactive` 后，它会统计全部物体点。

但 Dataset 即使设置：

```yaml
active_only: false
```

也仍然通过：

```python
sample_object_indices(candidate_mask)
```

只从 5 cm 候选点采样。`active_only` 只是决定是否保留没有候选点的 frame，并不意味着改成采样全部物点。

所以统计脚本应该始终写成：

```python
flow = flow[candidate]
```

区别只在于：

```python
if active_only and not candidate.any():
    continue
```

对于无候选点的 inactive frame，最后 `available_count == 0`，自然跳过。

当前正式配置使用 `active_only=true`，因此不会影响这次训练，但这个命令行选项现在语义错误。

## 3. overfit 配置的 best checkpoint 仍然无效

`overfit.yaml` 现在写的是：

```yaml
val_path: null
val_split: 0.0
metric_for_best: train_epoch/flow/epe_mm
```

但 BaseRunner 目前只在验证路径中调用：

```python
_handle_validation()
→ _save_if_best()
```

训练 epoch 指标只记录，不参与 best checkpoint 选择。

所以这个指标名虽然现在存在，仍不会生成真正的 `best.pt`。

处理方式二选一：

```yaml
# smoke/overfit 不需要 best
metric_for_best: null
```

或者在每个 epoch 后明确支持训练指标：

```python
if not self.val_loaders:
    self._save_if_best(train_metrics, epoch + 1)
```

如果 overfit 只用于确认能否拟合，直接依靠最后 checkpoint 最简单。


但当前还有 **3 个必须优先修复的问题**，否则可能选不到 best checkpoint，或者验证指标会受 batch 划分影响。

# 一、严重：很多配置的 `metric_for_best` 已经失效

当前 `CmActionRunner` 实际返回的验证汇总指标是：

```text
val/mean_stride_epe
val/mean_stride_relative_epe
val/epe_p90
val/zero_flow_improvement
val/norm_ratio
val/stride_1_epe
val/stride_5_epe
val/stride_10_epe
```

新配置使用的：

```yaml
metric_for_best: val/mean_stride_relative_epe
```

是正确的。

但是很多旧配置仍然写着：

```yaml
metric_for_best: val/flow_residual_norm_mean
```

或者：

```yaml
metric_for_best: val/mean_stride_flow_residual_norm_mean
```

例如 `baseline.yaml` 就使用了一个当前完全不存在的指标名。代码搜索还能找到十多个类似配置。

更危险的是，BaseRunner 遇到指标不存在时只是静默返回：

```python
if key not in metrics:
    return False
```

不会报错，也不会保存 best checkpoint。训练看起来正常结束，但 `best.pt` 可能从未被更新。

## 必须修改

所有正常验证配置统一改为：

```yaml
metric_for_best: val/mean_stride_relative_epe
```

或者更稳定地先使用：

```yaml
metric_for_best: val/mean_stride_epe
```

同时建议把 BaseRunner 改成直接报错：

```python
def _save_if_best(self, metrics: dict[str, float], epoch: int) -> bool:
    key = self.cfg.train.metric_for_best

    if key not in metrics:
        raise KeyError(
            f"metric_for_best={key!r} is unavailable. "
            f"Available metrics: {sorted(metrics)}"
        )

    value = float(metrics[key])
    ...
```

此外，一些 overfit 配置使用：

```yaml
metric_for_best: train_epoch/flow_residual_norm_mean
```

但当前 `_save_if_best()` 只在验证之后调用，并不会根据 `train_epoch/...` 保存 best。没有验证集的 overfit 实验需要单独增加 train-metric checkpoint 逻辑，或者不要配置 `metric_for_best`。

# 二、严重：`relative_epe` 当前是“平均 batch 比值”，不是全验证集比值

当前每个 batch 内计算：

```python
flow_epe_mean = residual_sum / valid_count
gt_norm_mean = gt_norm_sum / valid_count

flow_relative_epe = flow_epe_mean / gt_norm_mean
flow_norm_ratio = pred_norm_mean / gt_norm_mean
```

然后 BaseRunner 再对每个 batch 得到的比值求平均。

这意味着最终指标实际是：

[
\frac{1}{M}\sum_{b=1}^{M}
\frac{\operatorname{EPE}_b}
{\operatorname{GTNorm}_b}
]

而不是更合理的：

[
\frac{\sum_b\operatorname{EPEsum}_b}
{\sum_b\operatorname{GTNormSum}_b}
]

两者通常不相等。

## 为什么这是重要问题

假设两个 batch：

| Batch |   EPE | GT 流模长 | 相对 EPE |
| ----- | ----: | -----: | -----: |
| A     |  1 mm |   2 mm |   0.50 |
| B     | 10 mm | 100 mm |   0.10 |

当前做法：

[
\frac{0.5+0.1}{2}=0.30
]

全局比值：

[
\frac{1+10}{2+100}=0.108
]

差距非常大。

你们数据明确保留了“有接触但物体没有明显运动”的静态目标，因此部分 batch 的 GT 流模长可能很小。这类 batch 会让 `relative_epe` 突然变得很大，进而影响 best checkpoint 选择。

小数据配置的 batch size 又只有 2，问题会更明显。

## 推荐改法

在 `step()` 中分别返回可累加的统计量：

```python
from src.base.metrics import MetricStat

residual_sum = (residual_norm_map * valid.float()).sum()
gt_norm_sum = (gt_norm_map * valid.float()).sum()
pred_norm_sum = (pred_norm_map * valid.float()).sum()
valid_count = valid.sum()

metrics = {
    "flow/epe_mean": MetricStat(
        total=float(residual_sum.detach()),
        count=float(valid_count.detach()),
    ),
    "flow/gt_norm_mean": MetricStat(
        total=float(gt_norm_sum.detach()),
        count=float(valid_count.detach()),
    ),
    "flow/pred_norm_mean": MetricStat(
        total=float(pred_norm_sum.detach()),
        count=float(valid_count.detach()),
    ),
}
```

等整个 stride 的 loader 聚合完之后再算：

```python
relative_epe = (
    metrics["flow/epe_mean"]
    / max(metrics["flow/gt_norm_mean"], 1e-8)
)

norm_ratio = (
    metrics["flow/pred_norm_mean"]
    / max(metrics["flow/gt_norm_mean"], 1e-8)
)
```

这样结果不会随着 batch size 和 batch 分组方式变化。

## 静态样本最好单独统计

建议增加：

```text
flow/moving_relative_epe
flow/static_pred_norm
```

例如：

```python
moving = gt_norm_map >= 0.005  # GT 位移至少 5 mm
static = ~moving
```

* 对运动样本统计 normalized EPE，中文是“按真实位移归一化的误差”；
* 对静态样本统计预测流模长，判断模型是否错误地产生运动。

不要用一个分母接近零的 `relative_epe` 同时描述这两类样本。

# 三、严重程度较高：当前 P90 不是全局 P90

现在每个 batch 执行：

```python
flow_epe_p90 = torch.quantile(
    residual_norm_map[valid],
    0.9,
)
```

随后 epoch 层面对这些 batch P90 求平均；验证汇总时又对不同 stride 的 P90 求平均。

因此当前：

```text
val/epe_p90
```

实际是：

```text
不同 stride 的“平均 batch P90”的平均
```

不是整个验证集 90% 点误差的分位数。

例如两个 batch 的 P90 分别是 5 mm 和 100 mm，平均为 52.5 mm，但把全部样本合并后的真实 P90 不一定接近 52.5 mm。

## 还有性能问题

`flow_epe_p90` 当前在**每一个训练 step**都执行 `torch.quantile`，但 step 面板根本不记录它，只在 epoch 层面保留一个数学意义不准确的平均值。

`torch.quantile` 需要排序或选择操作，比普通 mean 昂贵，建议训练阶段直接删除。

推荐：

```python
if mode != "train":
    flow_epe_p90 = ...
```

但是目前 `step()` 一开始执行了：

```python
del mode
```

应当保留 `mode` 参数。

验证时可以选择：

1. 汇总所有残差后计算真实 P90；
2. 数据太大时使用固定区间直方图近似；
3. 暂时只保留 mean，删除 P90。

如果保留当前近似算法，至少应改名：

```text
val/mean_stride_mean_batch_epe_p90
```

避免把它误认为真正的全局 P90。

# 四、日志压缩过头：完整 stride 信息被直接丢弃

你之前的目标是减少 W&B 曲线，而不是删除验证信息。

但当前：

```python
def evaluate_all(self):
    return self._summarize_stride_metrics(
        super().evaluate_all(),
        split="val",
    )
```

`super().evaluate_all()` 算出了 stride 1～10 的完整指标，随后 `_summarize_stride_metrics()` 只返回汇总值和 stride 1、5、10 的 EPE，其余结果全部丢弃。

这意味着：

* stride 2、3、4、6、7、8、9 的指标不进入 W&B；
* 同样也不进入 JSONL；
* 最终返回值中也无法查看；
* 不能在训练结束后恢复完整表格。

## 更合理的结构

应该将“计算和保存完整指标”与“W&B 展示哪些曲线”分开：

```python
def evaluate_all(self) -> dict[str, float]:
    detailed = super().evaluate_all()
    summary = self._summarize_stride_metrics(detailed, split="val")
    return {**detailed, **summary}
```

然后给 BaseRunner 增加：

```python
def select_eval_metrics(
    self,
    metrics: dict[str, float],
) -> dict[str, float]:
    return metrics
```

W&B 只记录：

```python
self.wandb_run.log(
    self.select_eval_metrics(metrics),
    step=self.global_step,
)
```

而 JSONL 可以：

* 保存完整指标；
* 或者单独写 `val_stride_metrics.json`；
* W&B 使用 Table，而不是生成几十条曲线。

# 七、两个中等问题

## `slot/top1_usage` 名称不够准确

当前计算是：

```python
mean_decoder_slot_usage = decoder_slot_usage.mean(dim=0)
top1_usage = mean_decoder_slot_usage.max()
```

它表示“整个 batch 中最常用的固定 slot 编号占比”。

假设每个样本都只使用一个 slot，但不同样本选择不同编号，这个值仍可能很低。它不能表示每个样本是否由一个分支主导。

建议改名：

```text
slot/global_top1_usage
```

并新增更直观的：

```python
per_sample_top1_usage = (
    decoder_slot_usage.max(dim=-1).values.mean()
)
```

```text
slot/per_sample_top1_usage
```

## 仍有无效计算

即使：

```yaml
loss_active_overlap_weight: 0.0
```

当前代码仍然计算：

```python
normalized_weights
slot_similarity
slot_weight_overlap
```

但 `slot_weight_overlap` 已经不放入 metrics，也不参与 loss。

应将整个相似度计算放入条件：

```python
if (
    num_slots > 1
    and float(self.cfg.meta.loss_active_overlap_weight) != 0.0
):
    ...
```

否则默认配置下是纯额外计算。
