## 1. PCA 扰动的尺度逻辑仍然不正确

配置说明是：

```text
有 per-dim std：
delta_std = train_std[k] × noise_scale

没有 per-dim std：
delta_std = hand_pca_std
```

当前默认值为：

```python
hand_pca_std = 0.5
hand_pca_noise_scale = 0.10
hand_pca_noise_clip = 3.0
hand_pca_train_std_per_dim = None
```

正式 GRAB 配置只覆盖了 `hand_pca_std=0.5`，没有提供每维标准差。

但 Runner 实际逻辑是：

```python
if per_dim_std_t is not None:
    delta = noise * per_dim_std * hand_pca_scale
else:
    if hand_pca_scale > 0:
        delta = noise * hand_pca_scale
    else:
        delta = noise * hand_pca_std
```

由于默认 `hand_pca_scale=0.10 > 0`，当前正式训练实际使用的是：

[
\Delta p_k\sim\mathcal N(0,0.1^2)
]

而不是配置中看起来的：

[
\Delta p_k\sim\mathcal N(0,0.5^2)
]

因此 `hand_pca_std=0.5` 实际被忽略了。

### clip 也不是 3σ

有每维标准差时，当前代码：

```python
delta = noise * std * scale
bound = std * clip
```

假设：

```text
scale = 0.1
clip = 3
```

扰动标准差是：

[
0.1\sigma_k
]

但裁剪边界是：

[
3\sigma_k
]

相当于在扰动分布的 ±30 个标准差处裁剪，基本没有作用。

正确实现应是：

```python
if per_dim_std_t is not None:
    effective_std = per_dim_std_t * hand_pca_noise_scale
else:
    effective_std = torch.full(
        (num_pca_comps,),
        hand_pca_std,
        device=device,
        dtype=dtype,
    )

noise = noise.clamp(
    min=-hand_pca_noise_clip,
    max=hand_pca_noise_clip,
)

delta = noise * effective_std
```

即先把标准正态噪声裁剪到 ±3，再乘实际扰动标准差。

这是当前最需要修正的逻辑问题。

## 2. `mano_v_template_sha` 预计算优化实际上没有生效

Dataset 返回的是 Python 字符串：

```python
result["mano_v_template_sha"] = sha1
```

DataLoader 默认会将一批字符串整理成：

```python
list[str]
```

但 Runner 只处理 Tensor：

```python
sha_t = batch.get("mano_v_template_sha")

if torch.is_tensor(sha_t):
    sha_list = ...
else:
    sha_list = [None] * batch_size
```

因此实际会进入 `else`，随后重新调用：

```python
sha_i = self._v_template_sha(v_template, i)
```

这又会把每个样本的 `v_template` 从 GPU 复制回 CPU 并计算 SHA1。

应改为：

```python
sha_t = batch.get("mano_v_template_sha")

if isinstance(sha_t, str):
    sha_list = [sha_t] * batch_size
elif isinstance(sha_t, (list, tuple)):
    sha_list = [str(value) for value in sha_t]
elif torch.is_tensor(sha_t):
    sha_list = [str(value) for value in sha_t.reshape(-1).tolist()]
else:
    sha_list = [None] * batch_size
```

这不是正确性错误，但当前提交宣称解决的 GPU→CPU SHA 开销实际上仍然存在。

## 3. Hand 扰动仍有逐样本 GPU 同步

`_sample_passed_gate()` 每个样本都会执行：

```python
per_sample_apply[i_global].item()
```

而 `per_sample_apply` 已经在 GPU 上。每次 `.item()` 都可能要求 CPU 等待 GPU，batch 16 就会产生最多 16 次同步。

建议在进入循环前一次性转换：

```python
apply_list = (
    per_sample_apply
    .detach()
    .cpu()
    .reshape(-1)
    .tolist()
)
```

然后：

```python
if not apply_list[i_global]:
    continue
```

运行时物体采样还存在类似的小开销：

```python
selected_all.append(chosen_idx.to(device=device))
```

当前是每个样本单独执行一次 CPU→GPU 小张量复制。可以先在 CPU 上 stack，再一次性传输：

```python
selected_cpu = torch.stack(selected_all_cpu, dim=0)
selected = selected_cpu.to(device=device)
```

这些不会导致错误，但会影响你关注的“在线重建和采样到底慢不慢”。

## 4. MANO forward 没有显式放在 `no_grad`

当前流程是：

```python
batch = super().prepare_batch(batch)

self._reconstruct_hand_from_mano(batch)

with torch.no_grad():
    self._resample_object_from_perturbed_hand(batch)
    self._build_supervision_gpu(batch)
```

即 MANO reconstruction 位于 `torch.no_grad()` 之外。

MANO layer 创建后也没有显式：

```python
layer.eval()
layer.requires_grad_(False)
```

虽然当前传入的 MANO 参数通常不要求梯度，未必真的建立大型反向图，但这里不应该依赖 smplx 内部实现。建议：

```python
with torch.no_grad():
    if mano_side is not None and self._should_reconstruct_mano(batch):
        self._reconstruct_hand_from_mano(batch, side=mano_side)

    self._resample_object_from_perturbed_hand(batch)
    self._build_supervision_gpu(
        batch,
        contact_seed_list=contact_seed_list,
    )
```

MANO layer 创建后也执行：

```python
layer.eval()
layer.requires_grad_(False)
```

## 6. 两个较小的配置问题

### 重复字段

同时存在：

```python
hand_proxy_face_count = 256
num_hand_proxy_points = 256
```

运行时实际读取的是：

```python
hand_proxy_face_count
```

因此以后只修改 `num_hand_proxy_points` 不会生效。建议删除旧字段，避免误配置。

### 显存注释算错了

注释写：

```text
B × 512 × 256 floats ≈ 0.5 MB at B=16
```

实际 FP32 为：

[
16\times512\times256\times4
=8{,}388{,}608\text{ bytes}
\approx8\text{ MB}
]

不是 0.5 MB。不过 8 MB 仍然很小，分块策略本身没有问题。
