我看了现在的 `ai/ObjectInteractionCmv2/v1.13-io-acceleration`。我的判断是：**如果目标已经包含未来在线 Cm planner，那么现在正是改结构的合适时间。**因为 V1.13 主要解决了训练 I/O 和 endpoint-KNN 重复计算，full cache 和正式训练还没开始；但 `EndpointInteractionEncoder` 的核心计算仍然很重。

当前路径是：

```text
1024 object points
    ↓ geometry_encoder → 128D
每个 object point × 32 endpoint edges
    ↓
24D edge feature
    ↓
MLP 24 → 128 → 128
    ↓
key 128 → 128
value 128 → 128
    ↓
object-query attention
    ↓
contact_i [128D]
    ↓
16 surface tokens
    ↓
part query / part-surface attention
    ↓
per-part SE(3)
```

真正应该改的是中间这块。

## 为什么我认为它现在过重

对于一个 state、K=8：

$$
8\times1024\times32=262,144
$$

条 edge。

每条 edge 当前大致要经过：

$$
24\rightarrow128\rightarrow128
$$

再过：

$$
K:128\rightarrow128,\qquad
V:128\rightarrow128
$$

只粗算线性层乘法量，每 edge 就是：

$$
24\times128
+128\times128
+128\times128
+128\times128
\approx52,000
$$

所以 K=8 单 state，仅这部分就是数量级：

$$
262144\times52,000
\approx13.7\text{ billion}
$$

次乘法。

这也解释了为什么我们之前把 KNN/swept 改快了，`edge/contact` 仍然和搜索一样重。

**问题不是 32 个邻居本身，而是每一个邻居都被升到了 128D 做完整神经处理。**

---

# 我会改成“窄 interaction，宽 reasoning”

这是我目前最推荐的结构。

高层仍保留你 V1.12/V1.13 很好的设计：

* 1024 object points；
* endpoint top-32；
* 16 surface tokens；
* part routing；
* part-to-surface attention；
* part self-attention；
* per-part SE(3)。

我不会推翻这些。

只把 candidate-dependent 的 local interaction 改窄。

结构变成：

```text
                         STATIC / shared
object geometry
    ↓
geometry encoder
    ↓
g_i [128D]
    ↓
part geometry G_l [128D]
    │
    └───────────────────────────────┐
                                    │
                         DYNAMIC / per candidate
endpoint top-32 edges               │
        ↓                           │
raw edge feature [24D]              │
        ↓                           │
small edge encoder                  │
24 → 32 → 32                        │
        ↓                           │
small edge attention                │
        ↓                           │
contact_i [32D]                     │
        ↓                           │
 ┌──────┴───────┐                   │
 ↓              ↓                   │
16 tokens     part pool             │
[32D]         [32D]                 │
 ↓              ↓                   │
lift to 128    part encoder ◄────────┘
 ↓              ↓
surface token  part query
128D           128D
      \          /
       cross attention
             ↓
       part self-attn
             ↓
       per-part SE(3)
```

也就是：

$$
\boxed{
\text{dense edge processing: }32D
}
$$

而：

$$
\boxed{
\text{token/part reasoning: }128D
}
$$

## 具体怎么改 `EndpointInteractionEncoder`

现在：

```python
self.edge  = MLP(24, 128, 128)
self.query = Linear(128, 128)
self.key   = Linear(128, 128)
self.value = Linear(128, 128)
```

我会改成类似：

```python
interaction_dim = 32

self.edge = MLP(24, 32, 32)
self.query = Linear(128, 32)
self.key = Linear(32, 32)
self.value = Linear(32, 32)
```

于是：

$$
q_i\in R^{32}
$$

$$
e_{ij}\in R^{32}
$$

attention 仍然是：

$$
\alpha_{ij}
=
\operatorname{softmax}
\left(
q_i^\top k(e_{ij})/\sqrt{32}
\right)
$$

最后：

$$
c_i
=
\sum_j\alpha_{ij}v(e_{ij})
\in R^{32}
$$

注意这里**完全没丢掉 32 个 edge 的 attention**。

只是不要让它们这么早进入 128D。

---

# 然后 `contact_i` 不再是 128D

现在：

$$
c_i\in R^{128}
$$

我会让：

$$
c_i\in R^{32}
$$

这会影响后面的两个地方。

### Part interaction

当前：

$$
C_{\rm part}=\operatorname{segmentMean}(c_i)
$$

然后：

```text
geometry 128
interaction 128
active fraction 1
→ part encoder
```

改成：

```text
geometry 128
interaction 32
active fraction 1
→ part encoder
→ 128D part
```

即：

$$
[128+32+1]\rightarrow128
$$

很自然。

### Surface token

当前 token 对 128D `contact` 聚合。

我会让 surface token 在 interaction branch 里也是 32D：

$$
t_k\in R^{32}
$$

然后只有 16 个 token，所以这时候再升维：

```text
token:
32 contact
+ anchor 3
+ normal 3
+ mass 1
       ↓
token_encoder
       ↓
128D
```

也就是：

$$
39\rightarrow128\rightarrow128
$$

只有：

$$
16
$$

个 token 要做这个，而不是：

$$
1024\times32
$$

条 edge 做 128D 网络。

这就是最大的区别。

---

# V1.13 的 compact cache 基本可以原样保留

这是这个方案很重要的优点。

V1.13 cache 已经保存：

```text
edge_hand_points
edge_hand_normals
edge_hand_flow
edge_source_id
edge_valid_mask
```

这些足够重新构造当前的 24D raw edge feature。

所以：

> **不用重做 V1.13 compact cache schema。**

模型只改变：

```text
raw edge
→ interaction representation
```

之后的编码网络。

当然 checkpoint schema 要变，必须重新训练模型，但 V1.13 本来就还没有正式训练，所以现在改的 sunk cost 很小。

---

# 我甚至还想再进一步：取消 edge 的独立 key/value 128 投影

前面那个 32D 方案已经比较保守。

更激进、我也很看好的形式是让 edge encoder直接输出：

$$
e_{ij}
=
[\ell_{ij},v_{ij}]
$$

其中：

* 一个 scalar/logit component 用来做 attention；
* 一个 32D value。

例如：

```text
raw geometry 24D
+
small projected object query 16D
         ↓
small MLP
         ↓
attention logit 1D + value 32D
```

变成：

$$
\ell_{ij},v_{ij}
=
f_{\rm edge}(x_{ij},q_i)
$$

然后：

$$
c_i=
\sum_j
\operatorname{softmax}(\ell_{ij})v_{ij}
$$

这样连：

```text
key Linear
value Linear
```

都不需要独立存在。

但我会把这个作为第二档，因为第一版保留 Q/K/V 语义更容易验证。

---

# 还有一个更重要的共享机会

V1.13 最终是 per-part SE(3)，而 object geometry 对 K 个 candidate 完全相同。

所以 planner 模式不要再传：

$$
[BK,1024,\dots]
$$

整个 object batch。

模型接口应该直接支持：

```text
object:
[B,1024,...]

candidate interaction:
[B,K,1024,32,...]
```

先算一次：

$$
g_i=E_{\rm geometry}(o_i)
$$

一次：

$$
G_l=\operatorname{partPool}(g_i)
$$

然后 K 个 candidate 共用。

模型 API 我会设计成：

```python
state = model.encode_object(
    obj_points,
    obj_normals,
    obj_part_id,
    part_valid_mask,
)

output = model.forward_candidates(
    state,
    candidate_edges,
)
```

这是**真正的共享**。

不是现在那种：

```text
expand
→ reshape BK
→ model 内再发现每 K 个一样
→ repeat_interleave
```

# 所以我设想的最终结构

我会把 Cm 明确拆成两层：

### Static object encoder

每个 state 只运行一次：

$$
O_t
\rightarrow
\{g_i,G_l,\text{object metadata}\}
$$

它完全 candidate-independent。

### Dynamic interaction encoder

每个 candidate：

$$
a_k
\rightarrow
\text{endpoint neighbors}
\rightarrow
24D raw edges
\rightarrow
32D contact evidence
$$

然后：

$$
32D\ interaction
+
128D\ static\ geometry
$$

在 token/part 层汇合。

所以逻辑上是：

```text
                    object state
                        ↓
                 wide static encoder
                     128D
                        │
       ┌────────────────┼─────────────────┐
       │                │                 │
candidate 0        candidate 1       candidate 7
       ↓                ↓                 ↓
 endpoint edges     endpoint edges     endpoint edges
       ↓                ↓                 ↓
 narrow 32D         narrow 32D         narrow 32D
 interaction        interaction        interaction
       ↓                ↓                 ↓
 surface/part fusion with shared static geometry
       ↓                ↓                 ↓
   SE(3)_0          SE(3)_1          SE(3)_7
```

我会把这个原则概括成：

$$
\boxed{
\text{Static geometry can be wide; candidate-dependent physics must stay narrow.}
}
$$

---

## 为什么我更喜欢这个，而不是直接砍到一个 MLP

因为它还保留了你们 Cm 的主要 inductive bias：

* object point grounding；
* endpoint hand-object neighborhood；
* normal/tangent flow；
* physical scale；
* 16 surface tokens；
* part-aware routing；
* part permutation equivariance；
* per-part SE(3)。

我们并没有变成：

$$
(state,action)\rightarrow6D
$$

这种黑盒。

只是把昂贵的：

> “32 个邻居 × 每条边 128D reasoning”

改成：

> “32 个邻居只做低维 interaction sensing；真正的高维 reasoning 到 token/part 层再做。”

我认为这在科学上也更合理。

---

## 我暂时不会动的东西

第一轮我不会同时改：

* K=32；
* surface token K=16；
* D=128 的 part reasoning；
* routing \(\rho_{lk}\)；
* part self-attention；
* SE(3) head；
* loss；
* GT；
* endpoint-KNN 定义。

否则速度提高以后无法判断到底是谁造成效果变化。

第一轮只改：

$$
\boxed{
\text{Local interaction width }128\rightarrow32
}
$$

以及：

$$
\boxed{
\text{真实的 candidate-axis sharing}
}
$$

这两件事。

### 我的预期

不能在没有 benchmark 的情况下承诺 FPS，但从结构 FLOPs 看，这比继续优化 KNN 更有机会产生数量级收益。

因为现在真正可怕的是：

$$
262k\text{ edges}
\times
128D\text{ MLP/K/V}
$$

而改完以后会接近：

$$
262k\text{ edges}
\times
32D\text{ cheap encoder}
$$

真正 128D 的部分主要发生在：

$$
8\times16\text{ tokens}
$$

和：

$$
8\times L\text{ parts}
$$

上。

这里的规模差距非常大。

**所以如果现在让我决定下一版 Cmv2 的结构，我不会继续在 V1.13 上做纯 I/O 小修，而会把它作为数据/edge contract 保留下来，在其上做“32D local interaction + 128D token/part reasoning + candidate-axis static sharing”。**

这同时解决我们现在两个最大的结构问题：`edge/contact` 太重，以及 K 个 candidate 重复计算静态 object geometry。
