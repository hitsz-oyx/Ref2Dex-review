# 5. 但是我发现第一个重要问题：**Contact GT 的时间没有对齐**

现在 GT 是这样构造的：

```python
hand = gather_points(
    batch["future_hand_points_object_endpoint"],
    batch["action_patch_knn_idx"]
)

obj = prediction["obj_patch_centers_object"]

distance = ...
```

也就是：

[
\boxed{
H_{t+8}
\quad vs\quad
O_t
}
]

Dataset 中：

`future_hand_points_object_endpoint` 确实是：

[
H_{t+8}
]

转换到 **当前 (t) 时刻 object frame** 下。

这本身没问题。

问题是：

```python
prediction["obj_patch_centers_object"]
```

来自**当前时刻物体**：

[
O_t.
]

于是现在算的是：

[
\boxed{
d(H_{t+8},O_t)
}
]

而我们真正想监督的是：

[
\boxed{
d(H_{t+8},O_{t+8})
}
]

两者都应该表达在同一个 (t) 时刻 object frame 下。

---

## 6. 这个问题尤其可能解释现在的 contact 稀疏

因为 object 在 8 帧里本来就在移动。

当前 Dataset 已经算出了：

[
obj_disp_chunk_gt
=

O_{t+k}-O_t
]

并返回。

所以根本不需要新增 cache。

直接：

[
\boxed{
O_{t+8}
=

O_t+
\Delta O_{t+8}
}
]

即可。

然后用**同一个当前 object patch KNN index** gather：

[
O_{t+8}^{patch}
]

再和：

[
H_{t+8}^{patch}
]

算距离。

---

## 7. 我建议先把 target 改成这样

概念上：

```python
object_endpoint = (
    batch["world_obj_points_object"].float()
    + batch["obj_disp_chunk_gt"][:, -1].float()
)

object_endpoint_patch = gather_points(
    object_endpoint,
    prediction["obj_knn_idx"],
)

object_endpoint_center = object_endpoint_patch.mean(2)
```

然后：

[
d_{jm}
======

\min_{p\in handpatch_j}
|
h^{t+8}_{jp}
------------

o^{t+8}_m
|.
]

再：

[
C_{jm}
======

\exp
\left(
-\frac{d_{jm}^2}{2\sigma^2}
\right).
]

**我建议这个先修，再讨论 weighted loss。**

否则我们是在对一个可能时间错位的 target 做 class balancing。

# 8. 第二个问题更加结构性：V15 只拿了“最后一步 Action”预测最终抓取

现在：

```python
pred_contact_matrix =
    contact_head(cm[:, -1, 1:])
```

也就是只使用：

[
\boxed{
C_{m,7}^{art}
}
]

来预测：

[
Contact_{t+8}.
]

但现在 ActionToken V2 已经被我们明确设计成：

[
\boxed{
A_t=E(\Delta H_t)
}
]

它只代表：

> **这一小步怎么动。**

它**不包含当前姿态，也不包含前面 7 步发生了什么。**

所以：

[
A_7
]

只是：

[
t+7\rightarrow t+8
]

最后一步 motion。

从它单独预测：

> t+8 时整只手最终形成了什么 grasp/contact

实际上信息是不充分的。

# 9. 更关键的是，当前 A→W 的 position embedding 也一直是初始位置

现在代码是：

```python
action_patch = gather_points(
    batch["world_hand_points_object"],
    batch["action_patch_knn_idx"]
).mean(2)

position = ...
query = raw + self.action_position(position)[:, None]
```

这个：

[
position
]

来自：

[
H_t
]

当前手的位置。

然后：

```python
[:, None]
```

直接复制给全部 8 个 timestep。

所以：

[
A_0,A_1,\dots,A_7
]

都拿到的是**同一个初始 hand patch position**。

这意味着最后的：

[
C_{m,7}
]

知道：

* 最后一步 articulation flow；
* 初始 hand patch position；
* 当前 World；

但不知道：

[
\boxed{
\text{前 7 步累计以后，手已经跑到哪里了}
}
]

# 10. 这和我们之前的设计原则其实不冲突

我们之前说：

> ActionToken 本身不应该建模时间关系，时间关系后面再做。

这个原则仍然对。

问题只是：

[
\boxed{
\text{V15 已经到了“后面”这一层，却没有真正组合 8 个 ActionToken。}
}
]

现在是：

```text
A0 → Cm0 ─┐
A1 → Cm1  │
...       │
A7 → Cm7 ─┴→ 实际只拿 Cm7 → Contact
```

前 7 个 Cm 对 contact loss 几乎没有直接作用。

# 11. 我认为最小修改不要上 Temporal Transformer

不需要重新复杂化。

有两个很小的选择。

### 方案 A：最简单

Contact branch 使用：

[
\boxed{
\bar C_m^{art}
=

\frac18\sum_{t=0}^7C_{m,t}^{art}
}
]

然后：

[
\bar C_m^{art}
\rightarrow ContactHead.
]

至少让全部 8 个 motion 都参与。

但是 mean 不知道顺序。

---

### 方案 B：我更推荐

直接让一个 contact query 读取：

[
\boxed{
C_m^{art}
\in[B,8\times64,384]
}
]

也就是把：

[
[8,64]
]

flatten 成：

[
512
]

个 interaction tokens。

再用很小的 attention/readout 得到 contact representation。

这属于：

> **Interaction 层做 temporal composition**

而不是污染 ActionToken。

我觉得理论上更正确。

# 12. 但在加 temporal readout 前，我会先做更简单的 sanity check

我建议下一轮顺序不是直接：

> weighted MSE → 再训。

而是：

```text
1. 修正 endpoint object contact GT
       ↓
2. 重新统计 active fraction
       ↓
3. 可视化 5~10 个 GT contact matrix
       ↓
4. 确认真正接触的 hand/object patch 被点亮
       ↓
5. 再跑同一个 32-chunk overfit
```

如果这时候：

[
active\ fraction
]

仍然只有：

[
0.4%\sim0.7%
]

那再做：

* positive weighting；
* balanced BCE；
* positive-region normalized MSE。

这是合理的。

# 13. 我还会做一个非常便宜的 Oracle

这个非常有价值。

暂时不走 ActionToken / Cm。

直接输入：

[
\boxed{
H_{t+8}^{patch}
}
]

或者 endpoint hand patch center，

让一个小 MLP 预测 contact matrix。

如果连这个都 overfit 不起来：

[
\boxed{\text{contact GT / loss 本身有问题}}
]

如果它轻松做到 >90%，而 Cm 做不到：

[
\boxed{\text{才是 Cm 输入信息或 readout 的问题}}
]

这样不用再猜。
