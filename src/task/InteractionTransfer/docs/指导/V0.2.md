浏览了当前 `hitsz-oyx/Ref2Dex-review` 的 `oyx` 分支。最新提交是 `787049f`：**“修正 V0.1 CUDA 环境诊断与 DenseToken 实验”**。

现在 `InteractionTransfer` 已经从最初骨架明显前进了：真实 DenseToken/PTv3 已接入，默认加载 DenseToken checkpoint；`Relation → gate × Action → Cm` 的 zero-preserving 路径仍保留，`ObjectAggregator.proj` 也已经改为 `bias=False`。当前在 RTX 3090 上已经用真实 DenseToken 跑通 `(1,512,1538) → (1,512,3)` forward，并验证 zero hand-flow 时 edge message 严格为 0。

不过我看下来，**现在还不建议直接开始正式训练**，有几个 P0 问题：

1. **vendored DenseToken 还没有完全等价复刻原 DenseToken。** 原来的 DenseToken point feature 中第三个 opposite-cloud 特征是“指向另一点云质心方向与当前法向的投影”；现在 `dense_state_encoder.py` 直接把这个第三维设成了 0。 原实现明确计算了 `proj_cent`。这意味着你虽然加载了 pretrained PTv3 权重，但输入分布发生了改变。因此现在的 `z_obj/z_hand` 不能严格认为是原 DenseToken 的 feature。

2. **pretrained edge relation 实际没有进入 (R_{ij})。** `FrozenDenseStateEncoder` 实现了 `edge_features()`，也建立了 `edge_shared/cross_head`；但当前 `model.py` 实际还是直接：
   [
   R_{ij}=E_R([z_i^O,z_j^H],g_{ij})
   ]
   没调用 `edge_features()`，也没把 pretrained contact probability 放进 RelationEncoder。
   所以现在 DenseToken 只是作为 static point token backbone 使用，并没有完全实现我们之前设想的：
   [
   R_{ij}=E_R(e_{ij}^{dense},g_{ij},p_{ij}^{contact}).
   ]
   这不一定错，但需要**明确二选一**，不要代码里留一套没使用的 edge head。

3. **当前 dataset 会严重污染实验。** `InteractionTransfer/dataset.py` 把每一个相邻帧都作为 transition，只读取 `shared.npz + right.npz`，完全没有检查左手是否正在作用物体。
   而你已经验证成功的 PointWorld V0.2A 数据集专门要求：
   [
   \text{right active at }t,t+1
   ]
   且
   [
   \text{left inactive at }t,t+1.
   ]

   如果这里不对齐，会出现：

   > 左手推动了物体，但 InteractionTransfer 只拿右手动作解释 (\Delta O)。

   这会直接破坏 Cm 的学习。**我认为这是目前最优先修的地方。**

4. **点数也没有对齐。** 当前 dataset 默认是：
   [
   N_O=1024,\quad N_H=256
   ]

   但 DenseToken checkpoint 是在：
   [
   512\ object + 1538\ hand
   ]
   上训练的，CUDA sanity 也专门改成了 `(512,1538)`。
   既然 V0 的目的就是验证这个表示，第一版最好直接使用原 DenseToken 的 `512/1538`，不要同时引入采样分布变化。

5. **V0.1 的 shuffle diagnostic 现在有 bug。** CUDA 下：

   ```python
   b = 1
   ```

   但 shuffle 写成：

   ```python
   action.flip(0)
   ```

   `dim=0` 是 batch 维。batch size 为 1 时：
   [
   \operatorname{flip}(action,0)=action.
   ]
   所以 CUDA 下所谓 `shuffle` 实际就是 GT。应该随机打乱 **hand-point dimension 1**：

   ```python
   perm = torch.randperm(action.shape[1], device=action.device)
   shuffled = action[:, perm]
   ```

6. **正式 train 脚本现在默认仍然跑 CPU。** `train_one_step(..., device="cpu")`，而 `main()` 没有传 device。 你们自己已经确认真实 PTv3/spconv 需要 CUDA，因此当前 README 所说的真实训练命令实际上还没有和真实 DenseToken 环境接好。需要加 `--device cuda:0` 或自动选择 CUDA。

还有一个不是立即 bug、但后面必须监控的问题：Effect Decoder 仍然直接读取

[
[o_i,n_i,C_i^O,\operatorname{mean}(C^O)]
]

因此它理论上可能从静态 object geometry 学 shortcut。 暂时不用删 xyz/normal，因为 dynamics decoder 本来就需要物体结构；但正式训练后必须比较：

[
GT\ action,\quad zero,\quad reverse,\quad shuffle
]

下的 **effect EPE**，而不能只比较 `edge_message.norm()`。

### 我建议现在下一步

**先不要改 Cm 架构，也不要上 SetTransformer / inverse。**

直接做一个 `V0.2 data + DenseToken fidelity fix`：

```text
P0-1  完整复制原 DenseToken point-feature 计算，保证 pretrained 输入一致
P0-2  dataset 完全复制 PointWorld V0.2A 的 transition 筛选逻辑
P0-3  改成 512 object + 1538 hand
P0-4  修复 shuffle = hand-point permutation
P0-5  train.py 支持 CUDA
P0-6  明确 R_ij 是否使用 pretrained edge feature/contact prior
```

修完以后再跑真正有意义的第一个实验：

[
\boxed{
\text{Direct PointWorld V0.2A}
\quad vs\quad
\text{InteractionTransfer V0}
}
]

用**完全相同 transition 和数据表示**比较 forward EPE，同时做 GT/zero/reverse/shuffle intervention。现在这个节点已经很接近可以真正判断这条 Cm 路线了，但还差这几个实验控制变量没有清干净。
