我看了当前 `oyx` 最新状态。现在最新提交是 `2c41c71`，V0.4 已经补了 self-contained direct baseline 和训练后的 intervention。单序列 100-step overfit 结果是：Cm GT EPE `9.91 mm`，zero `40.42 mm`，reverse `66.91 mm`，point-shuffle `9.78 mm`；当前 direct baseline GT 是 `50.72 mm`。

我的判断是：**现在不要进入 inverse action，也不要改 Cm 架构。下一步应该做 V0.5：先修两个 P0，再做真正公平的 multi-transition / multi-sequence causal benchmark。**

## 先修两个 P0

第一个比之前发现的问题还重要：**当前所谓 pretrained DenseToken edge/contact prior 很可能实际上没有把 edge head 权重加载进来。**

原 DenseToken checkpoint 里的模块名字是：

```python
edge_shared_backbone
cross_edge_head
```

原模型就是通过这两个模块产生 edge feature 和 contact probability。

但新 `FrozenDenseStateEncoder` 里名字变成了：

```python
self.edge_shared
self.cross_head
```

而 checkpoint loader 只做了：

```python
target = key[len("backbone."):] if key.startswith("backbone.") else key
if target in own:
    selected[target] = value
```

也就是说它没有：

```text
edge_shared_backbone.* -> edge_shared.*
cross_edge_head.*      -> cross_head.*
```

这个映射；而且当前只检查 `missing` 里有没有 `backbone.*`，没有检查 edge head 是否 missing。

因此很可能现在：

[
z_O,z_H=\text{pretrained}
]

但：

[
e_{ij}^{dense},p_{ij}^{contact}
]

来自**随机初始化后冻结的 edge head**。

这个必须第一优先级确认和修复。

最简单的做法甚至不是写映射，而是把 vendored 模块名字直接保持和原模型一致：

```python
self.edge_shared_backbone = ...
self.cross_edge_head = ...
```

然后严格检查这三块都成功加载：

```text
backbone.*
edge_shared_backbone.*
cross_edge_head.*
```

不能只检查 backbone。

---

第二个 P0 是 **Frozen DenseToken 的 eval 状态没有真正冻结。**

现在初始化时：

```python
self.requires_grad_(False)
self.eval()
```

没问题。

但训练时：

```python
model.to(device).train()
```

会递归执行：

```python
static_encoder.train()
```

所以 PTv3 又进入 training mode。参数虽然没有 gradient，但 Dropout、DropPath 等训练态行为仍可能恢复。

直接在 `InteractionTransfer` 里：

```python
def train(self, mode: bool = True):
    super().train(mode)
    self.static_encoder.eval()
    return self
```

或者 override `FrozenDenseStateEncoder.train()`。

这两个修完以后，我才认为 DenseToken 真正叫“Frozen pretrained relation encoder”。

# 然后不要急着解决现在的 shuffle

因为我发现现在的 shuffle test 和你之前 PointWorld V0.2A 根本不是一个东西。

当前 V0.4：

```python
perm = torch.randperm(action.shape[1])
shuffle = action[:, perm]
```

是：

[
\boxed{\text{hand point 内部乱序}}
]

也就是把同一个 transition 的：

[
\Delta h_1,\Delta h_2,\ldots
]

重新分配给别的 hand points。

但是 PointWorld V0.2A 当时的 shuffled action 是：

```python
torch.roll(flow, shifts=1, dims=0)
```

即：

[
\boxed{\text{不同 transition 之间交换整套 hand flow}}
]

这完全不同。

而 PointWorld 当时：

[
EPE_{GT}=5.12\text{ mm}
]

[
EPE_{shuffle}=19.22\text{ mm}
]

[
EPE_{zero}=37.86\text{ mm}.
]

因此现在：

[
GT=9.91,\qquad point\text{-}shuffle=9.78
]

**不能据此说 Cm 没有学到 action correspondence。**

因为 GRAB one-step 的 hand point flow 很可能高度平滑，例如整个手都主要向一个方向运动：

[
\Delta h_j\approx v_{\text{global}}+\epsilon_j.
]

这种情况下把：

[
\Delta h_1,\Delta h_2,\Delta h_3
]

换位置，本来变化就很小。

---

# 所以我建议下一版本直接叫 V0.5

V0.5 **不改模型结构**，专门做 representation validation（表示验证）。

我会按这个顺序：

1. **修 DenseToken checkpoint edge-head 加载 + frozen eval。**

2. 新增 `diag_action_field.py`，先测数据本身：
   [
   r_{\rm local}
   =============

   \frac{
   \frac1N\sum_j|\Delta h_j-\overline{\Delta h}|
   }{
   \frac1N\sum_j|\Delta h_j|
   }.
   ]
   这个量就是“局部动作差异相对于整体动作有多大”。如果它只有 0.05～0.1，那么 point-shuffle 本来就是一个很弱的 intervention。

3. 把 intervention 正式拆成：
   [
   \text{GT}
   ]
   [
   \text{zero}
   ]
   [
   \text{reverse}
   ]
   [
   \boxed{\text{cross-sample shuffle}}
   ]
   [
   \text{point-shuffle}
   ]
   再额外加一个很有价值的：
   [
   \text{mean-flow}
   ]
   即所有 hand point 都使用：
   [
   \Delta h_j=\overline{\Delta h}.
   ]
   这样可以直接判断模型到底只用了整只手的 global translation，还是确实使用了局部 point-flow structure。

4. **cross-sample shuffle 才作为硬 gate。**例如 eval batch：

   ```python
   wrong_flow = torch.roll(hand_flow, shifts=1, dims=0)
   ```

   当前 (O,H) 搭配别的 transition 的 (\Delta H)。

5. 建正式 train/val split。现在 `compare_v04.py` 是训练完直接测：

   ```python
   dataset[0]
   ```

   而这个样本就在训练数据里，所以目前的 `9.91 mm` 是 overfit capacity result，不是 generalization result。
   下一步至少按 **sequence 划分**，不能随机 transition 划分，否则相邻帧泄漏严重。

6. 补正式 evaluator：
   [
   \text{point EPE (mm)}
   ]
   [
   \text{translation error (mm)}
   ]
   [
   \text{rotation error (deg)}
   ]
   再记录：
   [
   D(C^{GT},C^{zero}),
   D(C^{GT},C^{reverse}),
   D(C^{GT},C^{cross})
   ]
   以及 point-shuffle/mean-flow。

## 还有一个问题：当前 direct baseline 不够强

当前 `DirectForward` 做的是：

```python
hand_features = [hand xyz, normal, flow]
hand_state = MLP(hand_features).mean(dim=1)
object_flow = MLP([obj xyz, normal, hand_state])
```

也就是说整个 1538 点 hand action 被：

[
\boxed{\operatorname{mean}}
]

成一个 global vector。

这比 InteractionTransfer 的 DenseToken + local KNN edges 弱太多。

所以目前：

[
\frac{EPE_{Cm}}{EPE_{direct}}=0.195
]

并不能说明“Cm bottleneck 比 direct dynamics 更强”，只能说明：

> 当前 InteractionTransfer 比这个简单 global-mean MLP 强。

因此 V0.5 我建议保留它作为 `DirectGlobalMLP` sanity baseline，但**再加一个 architecture-matched direct baseline**：

[
R_{ij},a_{ij}
]

仍然完全一样，然后不经过我们受约束的：

[
R_{ij}\rightarrow gate\rightarrow C_{m,ij}
]

而直接：

[
\boxed{
M^{direct}_{ij}
===============

MLP([R_{ij},a_{ij}])
}
]

再走同一个：

[
Aggregator\rightarrow EffectDecoder.
]

这样：

```text
InteractionTransfer:
R_ij + action
   ↓ gated zero-preserving Cm
Cm_ij
   ↓
Aggregator
   ↓
Effect

DirectEdge:
R_ij + action
   ↓ unrestricted MLP
edge feature
   ↓
same Aggregator
   ↓
same Effect
```

这个 baseline 才真正回答：

[
\boxed{
\text{加入 Cm bottleneck 到底损失了多少 forward capacity？}
}
]

之后再把 PointWorld V0.2A 的 5.12 mm 当强外部 baseline。它之前确实已经证明正确 hand flow 相比 shuffled/zero 有非常明显优势。

# 我认为下一阶段的生死判据应该改成

不是要求 point-shuffle 一定失败。

真正要求的是：

[
\boxed{
EPE_{GT}
<
EPE_{cross-sample}
}
]

[
\boxed{
EPE_{GT}
<
EPE_{zero}
}
]

[
\boxed{
EPE_{GT}
<
EPE_{reverse}
}
]

并且这些结论在**未见 sequence** 上成立。

同时：

[
\boxed{
EPE_{Cm}
\lesssim1.25EPE_{DirectEdge}
}
]

如果 point-shuffle 与 GT 接近，但我们测出来：

[
\Delta H_{\rm point-shuffle}
\approx\Delta H_{GT}
]

本身就很相似，那这不是失败。

反而 `mean-flow` 会告诉我们：

> Cm 是否只学到了全局手运动。

## V0.5 通过以后才做下一件真正有研究价值的事

那就是之前说的：

[
\boxed{
\Delta H^\star
==============

\arg\min_{\Delta H}
D(
C^{obj}(O,H,\Delta H),
C^{obj}_{target}
)
}
]

先**直接把 hand point flow 当优化变量**，验证 Cm distance 能不能指导 action。

这个成功以后，再接 differentiable MANO / robot FK。

现在还没到 Flow Matching，更没到 cross-embodiment。

所以我会把接下来的路线压缩成：

```text
修两个 P0
    ↓
V0.5 action-field diagnostic
    ↓
正确的 cross-sample intervention
    ↓
sequence-level train/val
    ↓
DirectEdge 公平 baseline
    ↓
V0.5 生死判据
    ↓
通过
    ↓
Cm-guided action optimization
```

**当前最不应该做的是因为 point-shuffle ≈ GT 就马上改 Cm 网络。现在这个现象大概率首先是 intervention 定义不合适，而且仓库里还有 DenseToken edge-head 加载和 frozen-eval 两个更值得先修的问题。**
