### 1. 当前 overfit 实验没有真正覆盖动作

  EXP-001 使用的是训练集第一个 episode 的前 32 帧：

  src/task/CmDecoder/docs/logs/experiment_log.md:27

  我按当时的 split 复现后发现：

  episode: inspire_f1/brown_ramen/4
  前 31 个 q_next - q_t 全部为 0

  也就是说，这次训练目标是静止动作。直接使用：

  q_next = q_t

  就能得到 0° 误差，而当前 MLP 最后只有 0.132°。

  全缓存上的 identity baseline 也很低：

  q_next = q_t
  平均 MAE ≈ 0.085°～0.10°

  因此当前 EXP-001 只能说明：

  - 模型和 optimizer 能运行；
  - checkpoint 可以加载；
  - Decoder 可以拟合一批静态目标。

  不能说明 Cm 携带了有效动作信息。当前日志中的 SUPPORTED 结论过强，更合适的是 INCONCLUSIVE，并注明实验窗口选择没有覆盖运动。

  这不是代码链路断了，而是实验样本选择不适合验证研究假设。

  ### 2. 30 Hz 相邻帧的 q 预测本身太容易

  当前任务是：

  q_t → q_{t+1}

  但在 30 Hz 下，大量相邻帧几乎不动。这样 q_t 本身就是很强的 shortcut，Cm 很可能完全没被使用。

  可以先选取有明显移动的帧跑过拟合


  ### 4. cache 的 fingerprint 目前只是写入，没有真正校验

  src/task/CmDecoder/build_cache.py:95

  当前 cache 是否复用只判断：

  if task/manifest.json exists:
      return cached

  虽然后面写入了：

  source_sha256
  num_hand_points
  num_obj_points
  sampling_seed

  但下次读取时没有检查这些字段。

  因此以下变化都可能静默复用旧 cache：

  - 原始 q 或 object pose 变化；
  - URDF 变化；
  - hand/object 点数变化；
  - sampling seed 变化；
  - HRDexDB loader 逻辑变化。

  cache key 目前只由 episode 路径决定，不能保证 cache 内容和当前配置一致。这是一个真实的可复现性问题。

  ### 5. 时间对齐仍然有需要确认的风险

  在 apple/2 中我检查到：

  video timestamp: 517 帧
  object pose:     501 帧
  frame_id 中还存在缺帧

  但当前实现做的是：

  src/task/CmDecoder/build_cache.py:110

  q_video → np.linspace + round → 501 帧

  同时：

  delta_time_s = 1 / 30

  这隐含了两个假设：

  1. pose 文件和 video timeline 可以按均匀位置对应；
  2. 每个相邻 pose 都严格相隔 1/30 秒。

  目前代码没有使用 pose 的显式 frame id，也没有保留真实相邻时间差。只要 pose 文件是经过过滤的帧，而不是完整连续的 30 Hz 帧，hand flow 和 q delta 的物理时间语义就会不准确。

  这部分在继续实验前应该单独做一个 frame mapping 检查。

  ### 6. 新 cache 仍然没有解决训练阶段的主要性能瓶颈

  分层 cache 预计算了：

  - hand/object world geometry；
  - hand-root frame geometry；
  - q 和 flow。

  但模型每个 batch 仍然会重新执行完整的冻结 Cm：

  src/task/CmDecoder/model.py:41

  self.cm(batch)["cm_tokens"]

  也就是说，冻结的 DenseToken 和 Cm head 会在每个 epoch 重复计算。对于 50 个 episode，这仍然会成为训练主要开销。

  更合理的结构是：

  geometry cache
      ↓
  一次性 GPU 提取 frozen cm_tokens
      ↓
  cm_tokens mmap cache
      ↓
  Decoder 训练

  ### 7. 还有两个实现细节

  - q_input_scale 和 q_target_scale 在配置里存在，但代码没有使用：
    src/task/CmDecoder/config.py:25

  - 当配置使用 cache_manifest 时，max_episodes 和 max_frames_per_episode 会被忽略：
    src/task/CmDecoder/dataset.py:268

  因此以前用于小规模 smoke 的 override，在新 cache 分支下不再具有同样效果。

  另外，当前选定的 Cm checkpoint 配置本身是 use_slot_gate=false，所以当前 CmDecoder 实验并不是在使用 hard-gated collapse checkpoint；slot 的匿名顺序问题仍然存在，但 gate 坍缩不是这次实验的首要风险。

  我的建议顺序是：

  1. 让当前 50-episode cache 完成，但先不要训练。
  2. 修正或至少验证 cache fingerprint 和时间帧映射。
  3. 重新选择包含真实运动的 overfit window。
  4. 先跑 q_t-only / Cm-only / q_t+Cm / shuffled-flow 对照。
  5. 使用 active-motion 和多帧 horizon 指标。
  6. 确认 Cm 确实带来增益后，再改 token-aware Decoder 或固定语义 token 架构。

  目前最应该优先修正的不是 MLP，而是 静止帧 shortcut、时间映射和 cache 可复现性。
