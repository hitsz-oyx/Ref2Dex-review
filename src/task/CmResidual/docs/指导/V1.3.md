I would **not** redesign the architecture again before training. Looking at the current code, I see **three changes I consider genuinely necessary**, plus one sanity check. Everything else can wait.

| Priority        | Issue                                                                       | What I would change now                                                         |
| --------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| **Must fix**    | Cm dimensions/config are inconsistent                                       | Set `cmFeatureDim: 32`, provide the real OI-Cm checkpoint and reference path    |
| **Must fix**    | DExplore “contact” input is currently hand-link velocity, not contact force | Feed the actual simulator contact-force tensor                                  |
| **Must fix**    | PPO residual has essentially full DExplore action authority                 | Add a small physical residual scale instead of `base_action + actions` directly |
| **Must verify** | Frozen DExplore base may still differ from native DExplore behavior         | Run zero-residual evaluation before PPO                                         |

Everything else I mentioned previously—prospective Cm, SE(3) effect output, articulated objects, moving OI-Cm to GPU, token redesign—**does not need to block the current training experiment**.

### 1. Fix the Cm configuration first

This one can literally prevent the environment from running correctly.

`task.py` currently assumes:

$$
D_{Cm}
=
N_{\rm slots}D_{\rm token}
+
3N_{\rm slots}
+
3,
$$

with default token dimension 32 and 16 slots. So the actual context produced is

$$
16\times32+16\times3+3
=
\boxed{563}.
$$

But `CmResidualOnline.yaml` still specifies:

```yaml
cmFeatureDim: 128
```

which makes the task allocate

$$
16\times128+48+3=2099
$$

features instead. The actual OI-Cm output cannot be copied into that tensor without an override. `task.py` also requires `reference.path` and `basePolicy.oiCmCheckpoint`, neither of which appears in the checked-in online task config.

I would simply make the task config contain:

```yaml
basePolicy:
  mode: dexplore
  cmFeatureDim: 32
  cmNumSlots: 16
  oiCmCheckpoint: <V1.3 checkpoint>

reference:
  path: <reference data>
```

There is also a second OI-Cm checkpoint requirement in the PPO network config via `OI_CM_CHECKPOINT`. The PPO builder loads another OI-Cm model even though it never uses it—the actual Cm inference occurs in the task.

For now, either set that environment variable to the same checkpoint, or preferably remove the unused second model loader later. **I would not spend significant time refactoring it before training.**

---

### 2. Fix the contact observation

This is the most important semantic bug I see.

The environment correctly refreshes a real contact-force tensor:

```python
self.contact_force = ...
```

but in `compute_observations()` the value called `contact` is currently constructed from:

```python
self.rigid_body_state[..., 7:10]
```

which is **linear velocity**, not contact force. Then `build_dexplore_observation()` thresholds that tensor as though it were force:

$$
\text{contact}
=
\mathbf 1[
\max |\text{contact\_forces}|>0.1].
$$



So DExplore is effectively being told:

> “this fingertip is in contact if its velocity magnitude exceeds 0.1”

instead of receiving physical contact.

That can directly corrupt the frozen base policy's observation and therefore corrupt all subsequent residual learning.

I would change the construction to use the corresponding entries from:

```python
self.contact_force
```

for those five contact links.

This is small but important.

---

### 3. Scale the residual action down

I think this is the most likely issue to damage PPO learning even if everything technically runs.

Currently:

$$
a_t=
\operatorname{clip}
(
a_t^{DExplore}
+
a_t^{PPO},
-1,1
).
$$



But PPO itself outputs a normalized 18-D action in approximately \([-1,1]\).

That means the “residual” initially has authority comparable to the entire DExplore action.

For the wrist translation dimensions, the current DExplore mapping uses a scale of **1.0**, so a normalized residual of \(0.5\) can correspond to an enormous positional target change. Rotation uses a \(\pi\) scale.

That defeats the purpose of starting from a strong base policy.

I would use:

$$
\boxed{
a_t
=
a_t^{base}
+
\alpha\odot a_t^{RL}
}
$$

with a deliberately small physical authority.

Even better, apply the residual **after converting DExplore's action to physical targets**:

$$
q^{target}
=
q^{base}
+
\delta q,
$$

$$
T^{target}
=
T^{base}\oplus\delta T.
$$

We already had reasonable scales in the earlier residual controller:

$$
\delta p_w\approx15\text{ mm},
$$

$$
\delta R_w\approx0.2\text{ rad},
$$

$$
\delta q_{\rm finger}\approx0.08\text{ rad}.
$$

I would reuse approximately that authority envelope for the first run.

The objective should initially be:

> **PPO can correct DExplore, but cannot completely replace DExplore in one action.**

Later, if residuals constantly hit the bound, enlarge it.

---

## 4. Before PPO: one zero-residual test

This is not another large experiment.

Set

$$
\delta a=0
$$

for all steps and run the frozen DExplore policy through our environment.

We need to see sensible hand/object behavior before training.

The DExplore observation side now looks substantially better: current code genuinely queries reference states at \(+1\) and \(+16\), passes reference link poses, velocities, angular velocities, object pose/twist and contact targets into the 721-D builder.

So I would **not modify that architecture further unless the zero-residual test shows a problem**.

---

## What I would explicitly leave alone for now

I would **keep the current retrospective Cm**:

$$
\Delta H_t=H_t-H_{t-1}.
$$

Yes, this means the policy gets information about the interaction that just occurred rather than the predicted effect of the candidate action.

That is not the final world-model architecture, but it is completely acceptable for the first question:

$$
\boxed{
\text{Does real OI-Cm context help residual PPO at all?}
}
$$

I would also leave the current tokens + anchors + mean predicted object flow as-is. The mean flow loses rotational information, but changing it is unnecessary before we know whether Cm helps at all.

I would leave OI-Cm on CPU unless profiling shows it makes PPO unacceptably slow. That's a performance optimization, not a correctness requirement.

I would leave the simple lift/distance reward alone for this first training run. If the question is simply whether the residual can improve lift over frozen DExplore, it is adequate.

And I would not implement articulated-object link IDs or the new contact/part token architecture yet. That is a separate OI-Cm V2 problem.

### So the minimal path I recommend is

$$
\boxed{
\text{fix config dimensions/checkpoints}
\rightarrow
\text{fix contact-force input}
\rightarrow
\text{bound residual authority}
\rightarrow
\text{zero-residual DExplore test}
\rightarrow
\text{train}
}
$$

I would stop there.

If those four items are handled, I think the current implementation is good enough to perform the **first meaningful DExplore + frozen OI-Cm + residual PPO experiment**. Everything else can be driven by what that experiment actually shows.
