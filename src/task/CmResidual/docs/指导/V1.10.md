The repository has moved to **`CmResidual V1.9.2`**. The main new development is that the **critic-only OI-Cm ablation is now implemented and has passed the engineering smoke gate**, but the actual T10/E10 efficacy experiment has not started yet. `ObjectInteractionCm` itself is still officially **V1.3.2**.

The new A/B comparison is much cleaner than the previous Cm integration:

$$
\textbf{A: control}
$$

$$
\pi(o_{1442}),\qquad V(o_{1442})
$$

versus

$$
\textbf{B: critic-Cm}
$$

$$
\pi(o_{1442}),\qquad
V(o_{1442},C_m^{563}).
$$

Both environments actually construct the same **2005-D observation** and run the same frozen OI-Cm. The actor in both cases explicitly slices only the first 1442 D, so Cm cannot affect the action path directly. Only B's critic reads the 563-D Cm suffix.

That 563-D suffix is still the current representation:

$$
16\times32\ \text{tokens}
+
16\times3\ \text{anchors}
+
3\ \text{mean predicted object flow}.
$$

So this experiment is specifically testing **current OI-Cm as critic information**, not the stride-1 / swept-contact V2 architecture we just discussed.

### The implementation is now genuinely asymmetric

The network builder now has explicit:

```text
actor_input_dim
critic_input_dim
```

and slices them separately. For control:

$$
D_\pi=1442,\qquad D_V=1442,
$$

while for critic-Cm:

$$
D_\pi=1442,\qquad D_V=2005.
$$

The two configs reflect exactly that.

This is the critic structure we had been converging toward conceptually: Cm informs value/advantage estimation without yet perturbing policy action generation.

---

## They also found a subtle A/B experimental bug and fixed it

Initially, even with the same seed and identical actor parameters, the 1442-D and 2005-D critic first layers consumed different amounts of PyTorch random numbers during initialization.

So after network construction, the two processes had different RNG states. That meant the supposedly matched policies received different action noise from the first rollout.

This was not a Cm effect.

V1.9.2 fixes it by constructing **both candidate critic layers `[1442, 2005]` in the same fixed order in both variants**, then retaining whichever one the variant actually uses. This equalizes RNG consumption.

After that fix, the static checks report:

$$
\text{post-build CPU RNG equal}=true
$$

and

$$
\max|a^{stochastic}_A-a^{stochastic}_B|=0
$$

for the first sampled action.

This is good experimental hygiene.

# Both 2-epoch smoke runs now pass

After the RNG fix:

| Variant   | Epoch-1 success | residual RMS | Epoch-2 critic loss |     KL |
| --------- | --------------: | -----------: | ------------------: | -----: |
| Control   |          0.1875 |      0.10321 |              3.7078 | 0.0288 |
| Critic-Cm |         0.15625 |      0.10321 |              3.7245 | 0.0240 |

Both checkpoint reload differences are exactly `0.0`, sigma stays at ~0.1, and all tensors/optimizer states remain finite.

I would **not interpret those loss/success differences**. Two epochs are only a wiring smoke, and the repo correctly does not interpret them.

In particular, even after static RNG/action parity, the two separately launched GPU simulations already show slightly different epoch-1 success fractions. The repository attributes the remaining lack of trajectory-level equality to possible CUDA sampling / GPU PhysX nondeterminism and explicitly refuses to use those smoke metrics as Cm evidence.

I agree with that.

Trying to force bitwise-identical GPU physics trajectories is not worth further engineering effort. The correct answer is repeated seeds and deterministic checkpoint evaluation.

# The biggest positive change is methodological

V1.9 now isolates the causal question properly:

$$
\boxed{
\text{Does giving Cm only to the critic improve residual PPO?}
}
$$

without simultaneously changing:

* actor observation;
* residual exploration;
* reward;
* DExplore base;
* action scale;
* OI-Cm weights;
* environment code path.

The plan explicitly keeps:

$$
\mu_0=0,\qquad\sigma=0.1
$$

from the successful V1.8 safe residual configuration.

This is much more scientifically interpretable than the old `actor + critic both get Cm` experiment.

# What I would do next

I think the repository is finally ready for the actual **A/B T10 experiment**.

I would keep everything exactly as V1.9.2 defines it and run:

$$
A:\text{ control T10}
$$

and

$$
B:\text{ critic-Cm T10}.
$$

Then deterministic E10 for both under the same 367-step protocol.

The key comparison should not be only terminal success. Look at:

$$
\text{mean-env-max lift},
$$

$$
\text{contact occupancy},
$$

$$
\text{episode return},
$$

and especially learning dynamics across epochs.

If critic-Cm is useful, the first signal I would expect is not necessarily a much higher final lift after 10 epochs. It may instead be:

$$
\boxed{\text{lower-variance / faster value learning and more stable advantage estimates}}
$$

which should eventually translate into better policy learning.

But I would not use `c_loss` alone as evidence, because the two critics have different representational capacity and value normalization/on-policy distributions. The V1.9 plan correctly says that critic loss is diagnostic only.

My current judgment is that **the CmResidual branch is now in good experimental shape**. I would stop changing that branch and proceed to the T10/E10 A/B comparison.

Separately, we can continue designing OI-Cm V2 with the stride-1 + swept soft-contact formulation. That separation is useful: V1.9 tells us whether **even the current Cm representation has RL value**; OI-Cm V2 asks whether we can make that representation physically better.
