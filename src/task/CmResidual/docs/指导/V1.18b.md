
现在 profiler 已经说明：

```text
62 ms total
其中约 43 ms
= swept_topk + edge/contact
```

所以我不会去砍 attention、token 数或者小 MLP，那些总共才几个百分点。

真正要改的是：

```text
1024 object points
× 1538 hand points
× candidate swept flow
```

这一层 dense interaction。

我会按从保守到激进的顺序做。

### 1. 先做 candidate-independent computation sharing

现在 K=8 flatten 后，很多相同东西被重复处理：

```text
object geometry
current hand geometry
object encoder
```

应该变成：

$$
z_{\rm obj}=E_{\rm obj}(s_t)
$$

只算一次，然后 K 个 candidate 共用。

这个不会解决全部 43 ms，但属于应该先清掉的明显浪费，而且可以尽量保持 checkpoint 语义。

---

### 2. 把 dense hand-point search 改成“两级 broad-phase → fine interaction”

这是我觉得最值得尝试的结构。

现在对每个 object point 都直接在 1538 个 hand points 上找 swept KNN。

但 Inspire 实际上只有十几个 link。

可以先：

```text
candidate action
↓
18 个 link 的 candidate pose / swept AABB / sphere
↓
判断哪些 object regions 可能靠近哪些 links
↓
只在这些 link 内的 hand points 上做精确 swept interaction
```

也就是：

$$
\text{link-level broad phase}
\rightarrow
\text{point-level narrow phase}
$$

而不是：

$$
1024\times1538
$$

全局暴力搜索。

这个方案的优点是**仍然保留真实 hand surface 和 swept geometry**，不像直接做小 MLP 那么激进。

如果每个 object point 最后只需要检查 1–3 个附近 link，计算量可能降很多。

---

**现在甚至没有真正物化完整的 `1024×1538` cdist 矩阵**；V1.18a 的 `swept_topk()` 已经按 `object_chunk=128, hand_chunk=256` 分块算了。

但它仍然做了近似完整的：

$$
1024\times1538
$$

次 point-to-segment 距离计算，所以**算力复杂度没降，只是显存降了**。

而且我刚看代码，当前 `swept_topk` 还有一个很明显的性能点：

```python
distance = torch.linalg.vector_norm(...)
...
candidates_d = torch.cat((best_dist, distance), -1)
...
argsort(by index)
argsort(by distance)
```

每个 hand chunk 都做两次 stable `argsort`。所以 20.5 ms 不只是“距离矩阵”本身，**反复排序也很贵**。

我现在会从三个层次优化。

### 第一层：不改语义的直接优化

这个应该最先做：

1. **不要算 sqrt**

现在：

$$
d=\sqrt{x^2+y^2+z^2}
$$

但 top-k 排序根本不需要 sqrt，可以直接用：

$$
d^2=x^2+y^2+z^2
$$

最后只对选中的 32 个距离开根，甚至 radius 判断也直接用：

$$
d^2<0.02^2
$$

2. **`argsort` 改成 merge-topk**

现在每个 chunk 把：

$$
32+256=288
$$

全部 stable sort。

实际上只需要最小 32 个：

```python
values, positions = torch.topk(
    candidates_d,
    k=32,
    largest=False
)
```

然后 gather index。

如果严格要求“距离完全相同时 lower hand index 优先”，可以单独处理 deterministic tie-break；但对于连续浮点几何，真实 exact tie 很少。我不会为了这个 tie contract 每轮付两次 stable argsort 的成本，除非测试证明它必要。

这两个改动我认为应该先 benchmark，可能就能明显削掉 `swept_topk` 的 20 ms。

---

### 第二层：真正避免 \(1024\times1538\)

这里我认为关键思路不是“KNN”，而是：

> **我们其实根本不关心全局最近的 32 个点，我们只关心 2 cm interaction radius 以内的点。**

当前逻辑是：

$$
\text{全局 top32}
\rightarrow
d<2cm\text{ mask}
$$

可以反过来：

$$
\boxed{
\text{先找可能在 2cm 内的 pairs}
\rightarrow
\text{再在这些 pair 里 top32}
}
$$

如果真正接触区域很稀疏：

$$
N_{\rm candidate}\ll1538
$$

复杂度就会降很多。

---

### 我尤其建议利用手的 link 结构

这是比端点 cdist 更有前景的优化。

1538 个 hand points 并不是无结构的，它们属于十几个刚体 link。

对于每个 candidate、每个 link，可以非常便宜地构造一个 **swept AABB**：

```text
该 link 所有 hand points 的 start
+
所有 hand points 的 end
        ↓
取 min/max
        ↓
向外扩 2 cm
```

因为当前 Cmv2 的 swept 定义本身就是每个点从 start 到 end 的**线段**，所以 start/end 的整体 AABB 一定包含这个 link 上所有 point segments。

于是：

```text
object point
   ↓
落在某个 link 的 expanded swept AABB 内？
   ├─ 否 → 这个 link 的所有 hand points 都不可能在 2cm 内
   └─ 是 → 才计算这个 link 内的 exact segment distance
```

这可以做到**保守、不漏有效 contact**。

例如原来每个 object point：

$$
1538\text{ points}
$$

如果 broad phase 最后只筛到附近两个 finger links，也许只剩：

$$
100\sim300\text{ points}
$$

再算 exact swept distance。

这个比：

> start/end 分别做完整 `1024×1538 cdist`

更有意义，因为后者还是 \(O(NH)\)。

---

### 第三层：空间哈希 / voxel grid

如果 link broad-phase 还不够，可以更彻底。

因为 **object geometry 对 K 个 candidate 是相同的**，可以每个 state 建一次 object spatial index：

```text
1024 object points
      ↓
voxel hash / uniform grid
      ↓
K candidates 共享
```

然后每个 hand swept segment 只查询附近几个 voxel。

概念上：

$$
O(NH)
$$

变成接近：

$$
O(N+H+E)
$$

其中 \(E\) 是真正附近的 interaction edges。

对于接触这种本来就很 sparse 的问题，这才是理想复杂度。

而且 K=8 时收益更大，因为 object spatial structure 可以共用。

---

## 所以我反而会调整你刚才的方案

你刚才说：

> 点流两端取并集，再按最近 32 排序。

这个可以作为很容易实现的近似版本，但如果目标是**真正解决 latency**，我现在更倾向：

```text
共享 object/current-hand state
          ↓
link-level swept AABB broad phase
          ↓
只留下可能进入 2cm 的 link-point pairs
          ↓
exact point-to-segment distance
          ↓
每个 object point 最多 top32
          ↓
edge/contact
```

这样有几个优势：

* **没有完整 cdist；**
* **没有完整 \(1024×1538\) pair evaluation；**
* 保留当前 exact segment-distance 定义；
* 2 cm 内的真实 interaction 可以做到不漏；
* K=8 可以共享很多 state-level 数据；
* 不需要重新训练 Cmv2。

这比“端点近似 swept”更漂亮，因为它主要是**搜索算法优化，而不是物理模型近似**。

还有一点很重要：既然最终所有 `>2cm` 的 neighbor 都会被 mask，那么我们根本没有必要维持“全局 exact top-32”这个合同。真正应该保持的是：

$$
\boxed{\text{2cm 内的有效 top-32 interaction edges 等价}}
$$

而不是：

$$
\text{连 20cm 外那些最终会被 mask 的第 28~32 个邻居也必须完全一致}
$$

这一个合同变化，很可能能把整个搜索问题简化很多。

**如果让我选下一版实现顺序：**

1. squared distance；
2. `argsort → topk`；
3. shared flatten；
4. **swept-link AABB broad phase + exact segment narrow phase**；
5. 再看是否还需要 endpoint/midpoint 近似或者 voxel hash。

我现在最看好第 4 个。它有机会在基本不损失 Cmv2 物理语义的情况下，真正把那 20 ms 的 swept search 打下来。
