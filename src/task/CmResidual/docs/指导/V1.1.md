I checked the repository again, including today’s `CmResidual` changes. The project has moved significantly, but there is one important issue: **the current implementation is not yet the architecture we conceptually agreed on, despite looking similar from the logs.**

The good news is that the DExplore-based residual branch is now real infrastructure rather than a sketch. `CmResidual` has been converted to use the released Inspire DExplore checkpoint as a frozen base, with a 1442-D observation contract and native 18-D action/residual:

$$
a=\operatorname{clip}(a_{\rm DExplore}+\delta a,-1,1).
$$

The code checks the DExplore checkpoint shapes and SHA, freezes its parameters, and reuses the 18-D Inspire action mapping.

Three corrected PPO runs have also finished today at 1000 epochs. Their best training-period mean rewards were roughly 29.8, 25.8, and 18.3, although the activity log correctly says these are **not independent success-rate evaluations**.

However, I see **three structural problems that I would address before interpreting those runs scientifically**.

### 1. The “Cm” currently used by PPO is not our OI-Cm

This is the biggest issue.

The new PPO network defines:

$$
C^{online}=\mathrm{MLP}(o_{1442})
$$

with

```python
self.cm_online = nn.Sequential(
    nn.Linear(obs_dim, 128),
    nn.ELU(),
    nn.Linear(128, 128)
)
```

and an EMA copy called `cm_target`. Both features are concatenated with the original observation and fed to actor and critic.

There is no `ObjectInteractionCm`, no pretrained OI-Cm checkpoint, no `cm_tokens`, no object anchors, no hand-point flow, and no object-effect prediction in this path.

So at present:

$$
\boxed{\text{“Cm feature”} \neq C_m^{OI}}
$$

It is simply a learned 128-D feature encoder over the DExplore observation.

That means the three completed runs **cannot tell us whether OI-Cm helps RL**.

They only tell us whether PPO can train with an additional learned observation embedding.

This also differs from the architecture document we discussed, which explicitly says Cm-online should be trained from simulator transitions using supervised object-effect/no-effect losses and then slowly synchronized to a target.

---

### 2. The current Cm-online is being trained directly by PPO—the opposite of the intended separation

The implementation explicitly says:

> “The online feature receives PPO gradients through actor and critic.”

There is no auxiliary dynamics loss in `get_aux_loss()`.

Therefore the current update is essentially

$$
\nabla_{\theta_{Cm}}J_{\rm PPO},
$$

which is exactly what the architecture record said **not** to do initially. The documented intended design was:

$$
(s_t,a_t,s_{t+1})
\rightarrow
L_{\rm object-effect}
+
L_{\rm no-effect}
+\cdots
\rightarrow C_m^{online},
$$

followed by a slower EMA update to \(C_m^{target}\).

There is another subtle implementation issue: the EMA update currently happens inside `_cm_input()` on every actor/critic forward call, not once at the boundary of a PPO block.

So the target representation is not actually “frozen throughout a PPO block” in the sense we intended.

I would regard this as an implementation mismatch rather than a minor detail.

---

### 3. The DExplore checkpoint is not actually receiving the DExplore reference observation it was trained with

This may be just as important.

The repository now correctly outputs 1442 dimensions instead of the earlier invalid `71D + zeros` implementation. That earlier version was explicitly audited and declared `INVALID_IMPLEMENTATION`.

But look at how the new 721-D component is built.

Several reference-dependent fields are still explicitly zero:

```python
torch.zeros(...)  # root position error
torch.zeros(...)  # root rotation error
...
torch.zeros((b, 48))
torch.zeros((b, 96))
...
```

and many object-reference quantities are zeroed as well. Most importantly, the two temporal DExplore observations are currently just:

$$
[o_t,o_t],
$$

because the code says:

> “repeat the same measured state for the 1-step and 16-step slots.”



Thus:

$$
\boxed{
o_{\rm ours}^{1442}
\text{ has the correct dimension, but not yet the original DExplore semantics.}
}
$$

The frozen DExplore network was trained using reference-conditioned information. Feeding current state twice with missing reference targets is a major distribution shift.

So I would **not yet call this “using DExplore as a strong frozen base policy.”**

It is more accurately:

> using DExplore's pretrained weights on a partially reconstructed observation schema.

Those are different claims.

---

## The current control/reward side is also still simplified

The physical environment currently rewards:

$$
r =
w_{\rm lift}\Delta z
-
w_{\rm dist}d_{\rm fingertip-object}
-
w_a\|\delta a\|^2.
$$



So even if training reward improves, this does not establish interaction-preserving tracking, Cm benefit, or reproduction of DExplore performance.

The current activity log is appropriately cautious and labels the three new runs `INCONCLUSIVE` pending independent evaluation.

---

# What I think we should do now

I would **not launch another large RL experiment immediately**.

First fix the base-policy contract.

We need an actual reference provider so that the frozen DExplore teacher sees the same semantic quantities it saw during training:

$$
o_t^{DExplore}
=
f(
s_t,\,
r_{t+\Delta_1},\,
r_{t+\Delta_{16}},\,
O_t^{ref},\,
contact_t^{ref},
\ldots
).
$$

The two offset slots should genuinely correspond to the reference phases used by DExplore rather than duplicating the current simulated state.

Then perform the decisive zero-residual check:

$$
\delta a=0.
$$

Our wrapped DExplore policy should reproduce the native DExplore policy behavior to reasonable numerical/physical tolerance.

Until that passes, residual PPO results are hard to interpret.

Second, replace the current generic `cm_online = MLP(obs)` with the **actual OI-Cm pipeline**:

$$
(O_t,H_t,\Delta H_t)
\rightarrow
OI\text{-}Cm
\rightarrow
C_m,\hat{\Delta O}.
$$

For the first valid experiment I would freeze this completely.

Then compare:

$$
\text{DExplore}
$$

$$
\text{DExplore + ordinary residual PPO}
$$

$$
\text{DExplore + residual PPO + frozen OI-Cm features}.
$$

Only after demonstrating that actual OI-Cm features help would I enable online Cm adaptation.

And when we do enable it, I would follow the architecture record already sitting in the repository:

$$
\boxed{
\text{simulator transition}
\rightarrow
\text{supervised OI-Cm update}
\rightarrow
\text{slow target synchronization}
}
$$

rather than backpropagating PPO reward directly into Cm.

---

There is also a small governance inconsistency: `docs/current_versions.yaml` still says `CmResidual: V1.0.1`, while today's activity log is already at **V1.1.3**.

So my current reading of the warehouse is:

$$
\boxed{
\text{The infrastructure has advanced quickly, but we are one layer short of a scientifically valid DExplore + OI-Cm experiment.}
}
$$

The most important next correction is **not PPO tuning**. It is to make the frozen DExplore input genuinely reference-compatible and replace the placeholder “Cm MLP” with the real pretrained OI-Cm representation. Once those two contracts are correct, the experiment we've been discussing becomes meaningful.
