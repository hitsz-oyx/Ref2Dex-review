## 目标与对象

以当前固定的 `subject-10/20201022_110806/right` 72 帧、`002_master_chef_can` 为首个单轨迹训练对象。在冻结发布版 DExplore Inspire base policy 和远端 `ObjectInteractionCmv2V13Model` checkpoint 的前提下，使 residual PPO 的 actor 与 critic 均读取 Cmv2 的结构化交互上下文，只更新 residual 策略及其训练状态。residual 从新的零均值初始化开始，不加载 V1.8/V1.10 residual checkpoint。

本轮检验：该固定轨迹与物体的训练输入、Cmv2→actor/critic 接口和物理 PPO 是否形成可复核的有限闭环，以及训练后在同一轨迹上的确定性行为。单轨迹不提供独立 held-out 测试，不能证明 DexYCB 泛化，也不能单凭一个 Cm-enabled run 证明 Cm 的因果收益。

## 冻结与接口边界

1. DExplore base checkpoint、观测公式和 base action 不改；Cmv2 也冻结、`eval()`、无梯度。只训练 residual PPO actor/critic，不训练或微调 Cmv2，也不修改其 GRAB 训练任务。
2. 仅接受远端 V1.3 刚体模型 `architecture_version=v1_3_rigid_only` 的显式 checkpoint，校验文件 SHA256、配置和严格权重加载；checkpoint 未放到本地前可做静态接口/模拟输入验证，但不得启动正式训练。
3. Cmv2 输入来自当前仿真的 Inspire hand/object 几何与逐帧 hand flow，全部使用相同 z-up 世界坐标、米、秒；reset 后首帧 flow 为零。DexYCB MANO 只用于既有几何 retarget，不当作 Inspire GT 或在线 Cm 输入。
4. actor 与 critic 均读取 `cm_tokens [B,16,32]`、`token_anchors`、`token_normals`、`token_mass`、`token_mask`。具体编码、维度、空 token 处理和数值范围在同版本计划中冻结，不静默混用旧 OI-Cm 的 563-D token/anchor/effect 合同。
5. residual 维持现有 18-D action、零 mean 初始值、固定 `sigma=0.1`、已有物理尺度与关节约束；不改变 DExplore base、机器人/物体资产、仿真坐标、reward 组成或 checkpoint 的历史解释。现有 PPO reward 是 lift、tip distance、action penalty，DexYCB 标注轨迹不作为新的模仿 loss；若需改变目标，另行协商。

## 单轨迹数据与结论边界

- 保留 V1.11 的 72 帧 `evaluation`、`training_eligible=false` reference、cache、manifest 和运行产物；新建独立训练版本，重新核验身份、source/reference、坐标、reset、retarget、速度/加速度、joint limit、几何接触和全部输入 SHA，只有通过预先定义的门禁才标为 training eligible。不能复制旧 manifest 后只把布尔值改为 true。
- 仅本条 sequence 进入 train；不把同一 sequence 的帧随机拆成 val/test，不借用其他 DexYCB 轨迹。评估仍在同一轨迹上进行，明确标为 in-sample。
- 主要描述 wrist/fingertip/object reference error、仿真 contact occupancy、tip distance、相对首帧 lift、episode return 和 residual 幅度/饱和；几何近邻不等于真实接触力 GT。V1.11 的 airplane `0.08 m` 成功阈值不得用作 DexYCB 抓取成立的科研结论。
- 工程 smoke 只证明接线与可运行；完整训练和同轨迹评估也只能支持这一条轨迹上的行为描述。Cmv2 是否带来相对无 Cm 的因果收益、多物体/多人泛化与统计显著性均保持 `INCONCLUSIVE`。

新增
After looking at the **actual `ObjectInteractionCmv2` implementation**, I would frame the problem differently from our earlier CmResidual discussion:

> **OI-Cm can participate in policy learning, but I do not think “append its latent to PPO” or “unfreeze it and let PPO optimize it” is the most convincing role.**
>
> V2 is much more naturally a **one-step action/effect model of local hand–object interaction**. The missing bridge is not another decoder; it is a causal mapping
> **robot action → nominal robot surface motion → OI-Cm → predicted object effect**.

That distinction changes quite a lot.

## 1. What OI-Cm v2 actually is

The repository itself has converged toward a fairly clean mathematical object.

The V1.1 plan literally describes:

$$
(O_t,\ H_t,\ \Delta H_{t\rightarrow t+1})
\;\xrightarrow{\mathrm{OI\!-\!Cm}}\;
\Delta O_{t\rightarrow t+1}.
$$

It explicitly changed the old arbitrary multi-stride endpoint displacement into a fixed **one-step, \(1/30\) s local transition**.

And the current V2/V1.3 GRAB implementation really enforces that:

* GRAB + MANO only;
* stride = 1;
* \(dt=1/30\) s;
* swept 2 cm KNN32 interaction;
* rigid-only object effect;
* no residual flow in V1.3;
* 16 grounded interaction tokens.

Most importantly, the data contract is:

$$
\Delta H = H_{t+1}-H_t
$$

and

$$
\Delta O = O_{t+1}-O_t.
$$

The model receives current object geometry, current hand geometry and the **actual next-step MANO hand sweep**, while future object motion is the supervision target.

V1.3 then predicts a rigid object transform

$$
\hat{\Delta \xi}_{obj}\in SE(3)
$$

and analytically transforms the current object points with that SE(3). Training directly supervises translation, rotation and reconstructed point flow.

And yes, as its own model it is genuinely trainable: `train_grab.py` runs forward, computes the V1.3 rigid loss, backpropagates through OI-Cm and steps Adam.

So I no longer see the fundamental issue as *“can Cm learn a meaningful representation?”*

The harder issue is:

**What does \(\Delta H\) mean when we move from demonstrations to an RL robot?**

---

# 2. This is where I disagree with simply “putting OI-Cm into PPO”

There are two very different meanings of “participate in training”.

**Representation participation:** compute OI-Cm features and concatenate them into actor/critic observations.

**Objective participation:** OI-Cm affects which actions are considered good through prediction, rewards, supervision, planning, curriculum, or policy improvement.

The previous CmResidual implementation only did the first one. It explicitly froze OI-Cm parameters, set `requires_grad=False`, and defined no auxiliary OI-Cm loss.

That means PPO can learn to *use* OI-Cm features, but cannot make OI-Cm better suited to robot control.

More importantly, PPO is also free to **ignore those 16×32 latent dimensions completely**.

That is why I don't regard:

$$
\pi(a_t\mid s_t,z_{cm})
$$

as a particularly strong integration by itself.

There is an even stronger objection. In IsaacGym we already know the real next object pose after stepping physics. If OI-Cm is merely used as a “critic” that says whether the resulting object motion looks correct, then it is often replacing **ground-truth simulator information with a learned approximation**.

Why do that?

If the simulator can directly tell us

$$
T^{obj}_{t+1},
$$

then for ordinary tracking reward,

$$
d(T^{obj}_{t+1},T^{obj,ref}_{t+1})
$$

is better than having OI-Cm estimate it.

So I would not justify OI-Cm by saying:

> “It is a better reward/critic than physics.”

That argument is weak.

OI-Cm becomes useful when it gives information **before the action is executed**, or transfers information from **human interaction reference → robot interaction** that vanilla tracking does not encode.

---

# 3. The important missing link is action realization

Right now OI-Cm sees:

$$
\Delta H_{human}=H^{MANO}_{t+1}-H^{MANO}_{t}.
$$

But suppose PPO proposes action \(a_t\).

What should OI-Cm see?

It cannot see the *realized* robot \(H_{t+1}\), because that only exists after simulation.

Instead:

$$
a_t
\rightarrow
\hat q_{t+1}
\rightarrow
FK
\rightarrow
\hat H_{t+1}
\rightarrow
\Delta\hat H(a_t).
$$

Then query:

$$
\boxed{
\hat{\Delta T}^{obj}(a_t)
=
CM(
O_t,\,
H^{robot}_t,\,
\Delta\hat H(a_t)
)
}
$$

Now OI-Cm has become **action-conditioned**.

This is much closer to a world model.

And this is exactly the direction several recent world-model papers are moving toward.

**Kinema4D** explicitly separates robot kinematics from environmental dynamics. An abstract robot action is converted by IK/FK and the URDF into an explicit 4D robot trajectory; the learned model only has to model the environment's reaction. ([开放获取计算机视觉基金会][1])

Even closer to our problem, **Robot-Factored World Models via Robot Rendering** argues that an action affects the world through two stages:

$$
\text{command}
\rightarrow
\text{robot realization}
\rightarrow
\text{environment response}.
$$

They explicitly move the first part outside the learned world model: command → controller/kinematics → deployment-available nominal trajectory. The world model learns the scene response. They also point out that using logged future robot states would leak the result that the model is supposed to predict. ([arXiv][2])

That decomposition maps unusually well onto OI-Cm.

---

# 4. I would therefore **not train the FK**

This is one place where I would push against the phrase “our OI-Cm forward kinematics.”

There are actually two things here.

Your V1.3 OI-Cm contains an analytical rigid transform of the **object**:

$$
O_{t+1} =
\Delta T_{obj}\,O_t.
$$

That is the structured output decoder.

Robot FK is a different component:

$$
q \rightarrow H(q).
$$

I would keep them separate.

### Deterministic side

$$
a_t
\xrightarrow{\text{controller}}
\hat q_{t+1}
\xrightarrow{FK/URDF}
\Delta\hat H_t
$$

### Learned side

$$
(O_t,H_t,\Delta\hat H_t)
\xrightarrow{OI-Cm}
\hat{\Delta T}_{obj}.
$$

The model then only has to learn the piece physics makes uncertain:

> **Given this robot surface sweep around this object, what object motion will the interaction induce?**

That is a much tighter learning problem than learning both robot kinematics and object interaction dynamics.

There is an important caveat, though: if your action is not directly a joint-position target, FK alone is insufficient. For torque/velocity actions you need at least the low-level controller/actuator realization model first. Under strong contact, commanded and realized \(q\) can diverge as well.

So I would call it **nominal hand sweep**, not predicted true hand sweep.

---

# 5. This also explains why CmDecoder-style action inversion was difficult

This is not an implementation accident.

Suppose OI-Cm knows that the desired effect is

$$
\Delta T^{obj}.
$$

Can we decode a unique robot action?

Generally no.

There may be many different:

* wrist trajectories,
* finger configurations,
* contact locations,
* force distributions,
* joint-space paths,

that produce approximately the same object SE(3).

So

$$
\Delta T_{obj}\rightarrow a
$$

is severely one-to-many.

OI-Cm has deliberately compressed away information necessary to invert this map.

The forward direction is much better posed:

$$
a
\rightarrow
\Delta H(a)
\rightarrow
\Delta T_{obj}.
$$

So I would stop asking OI-Cm to be an inverse action generator.

Let the **policy** resolve the inverse problem; let OI-Cm evaluate its physical consequence.

---

# 6. Reference data should probably be used twice

This is where I think BeyondMimic is useful—but also where the analogy should not be pushed too far.

BeyondMimic is primarily a humanoid **motion tracking / distillation** framework, not an HOI dynamics model. Its starting point is to transform kinematic human references into robust physical robot motions, and then distill the motion primitives into a more general diffusion policy. ([arXiv][3])

For actual object interaction, **SkillMimic** and **InterMimic** are closer comparisons.

SkillMimic defines a skill through **HOI state transitions**: successful interaction means the simulated humanoid produces human-object transitions that match the reference transitions. ([开放获取计算机视觉基金会][4])

InterMimic first obtains teacher policies that mimic/refine imperfect MoCap, then distills those teachers into a student using direct supervision and improved references, and finally RL-fine-tunes the student. ([开放获取计算机视觉基金会][5])

The common pattern is:

> Reference is not merely another feature.
> It tells training **what transition should occur**.

For us, that suggests something stronger.

Compute two Cm quantities.

### Reference interaction

From the human/reference trajectory:

$$
\Delta H_t^{ref}
\rightarrow
OI\text{-}Cm
\rightarrow
\Delta T_{obj}^{ref}
$$

or, because reference object pose is already available, simply extract

$$
\Delta T_{obj}^{ref}
=
(T^{obj,ref}_t)^{-1}T^{obj,ref}_{t+1}.
$$

This answers:

> **What effect should happen now?**

### Candidate robot interaction

For a candidate action:

$$
a_t
\rightarrow FK
\rightarrow
\Delta H^{robot}_{nom}(a_t)
\rightarrow
OI\text{-}Cm
\rightarrow
\hat{\Delta T}_{obj}(a_t).
$$

This answers:

> **What effect will this robot action probably cause?**

Then the important quantity is not `cm_token` itself.

It is:

$$
e_{effect}(a_t)=
d_{SE(3)}
\left(
\hat{\Delta T}_{obj}(a_t),
\Delta T_{obj}^{ref}
\right).
$$

Now OI-Cm is directly connecting **reference imitation** with **robot action selection**.

That is much more compelling to me than concatenating 512 latent dimensions to PPO.

# 7. There are several ways OI-Cm could participate, with very different levels of risk

| Mechanism                                       | OI-Cm role                         | My concern                                                                               |
| ----------------------------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------- |
| Frozen `cm_tokens` in observation               | representation                     | May simply be ignored; weak causal role                                                  |
| OI-Cm features only in critic                   | privileged value representation    | Useful experiment, but still does not exploit forward prediction strongly                |
| OI-Cm as teacher/distillation target            | interaction representation teacher | More defensible; preserves OI-Cm semantics                                               |
| Auxiliary one-step effect prediction during PPO | representation regularizer         | Strong option if trained from real simulator transitions                                 |
| Reference-effect reward                         | desired-effect alignment           | Useful, but redundant after physics step unless it provides something reference-specific |
| Candidate-action scoring                        | learned local dynamics model       | Much more interesting                                                                    |
| MPC / residual action reranking                 | short-horizon world model          | Probably the strongest use of current V2 architecture                                    |
| End-to-end PPO through entire OI-Cm             | jointly learned representation     | Highest risk of representation collapse / reward exploitation                            |

There is also contemporary support for keeping world-model learning and policy learning coupled but **with a separate predictive objective** rather than throwing pure RL gradients through everything. For example, recent World-Action work explicitly studies online world-model adaptation together with actor improvement. ([开放获取计算机视觉基金会][6])

# 8. A particularly natural design for your residual PPO

I think our previous residual-PPO idea becomes more coherent if we use OI-Cm as an **action evaluator**, not as the action decoder.

Suppose the base tracking policy gives

$$
a_t^{base}.
$$

Residual PPO proposes

$$
a_t=a_t^{base}+\delta a_t.
$$

For several candidate residuals:

$$
\delta a_t^{(1)},\ldots,\delta a_t^{(K)},
$$

we compute:

$$
a_t^{(k)}
\rightarrow
\hat q_{t+1}^{(k)}
\rightarrow
FK
\rightarrow
\Delta H^{(k)}
\rightarrow
OI\text{-}Cm
\rightarrow
\hat{\Delta T}_{obj}^{(k)}.
$$

Compare them with the reference object transition.

That gives us a local “interaction feasibility” signal before simulation.

This can be used in several ways without making the system fully model-based:

$$
a^{base}
\rightarrow
\boxed{\text{small residual search}}
\rightarrow
CM\text{-based effect score}
\rightarrow
a_t.
$$

Or PPO can simply receive the scalar/model outputs:

$$
[
e_{effect},
\hat{\Delta \xi}_{obj},
contact\_mass,
anchors,\ldots].
$$

I would prefer this over dumping the raw 16×32 tokens into the actor.

# 9. There is still a serious domain problem in V2

This may actually be the largest experimental risk.

Current V2 training explicitly requires **GRAB/MANO** input.

But our policy controls an Inspire robot hand.

The architecture is nicely geometry-based rather than joint-ID-based, which helps. But that does **not** prove embodiment invariance.

OI-Cm has learned:

$$
P(\Delta O\mid
\text{MANO surface},
\text{MANO sweep},
O)
$$

and we want:

$$
P(\Delta O\mid
\text{Inspire surface},
\text{Inspire sweep},
O).
$$

Different finger shapes, surface density, reachable contacts, stiffness and collision geometry can change this mapping.

This is exactly why the recent robot-factored world-model work is interesting: it explicitly retargets motions into the actual robot embodiment and renders the corresponding robot geometry. ([arXiv][2])

So before putting OI-Cm into PPO, I would require one test that is more important than another GRAB validation number.

---

# 10. The experiment that would convince me

The important evaluation is **not**:

> “Does OI-Cm predict held-out GRAB object flow accurately?”

That only validates supervised human-interaction modeling.

Instead, fix a simulated robot state \(s_t\), generate multiple feasible robot actions \(a_t^{(k)}\), and for every action:

$$
a_t^{(k)}
\rightarrow
controller/FK
\rightarrow
\Delta H_{nom}^{(k)}
\rightarrow
OI\text{-}Cm
\rightarrow
\hat{\Delta T}_{obj}^{(k)}.
$$

Then actually execute each candidate in IsaacGym and obtain:

$$
\Delta T_{obj,true}^{(k)}.
$$

Measure:

$$
d_{SE(3)}
(
\hat{\Delta T}_{obj}^{(k)},
\Delta T_{obj,true}^{(k)}
).
$$

And, more importantly, check whether OI-Cm **ranks candidate actions correctly** with respect to the reference effect.

For example, if candidate A genuinely moves the airplane in the desired direction more than candidate B, does OI-Cm also prefer A?

That is the real test of whether it can participate in control.

If that fails, I would **not start a large OI-Cm-guided PPO run**, even if its GRAB EPE is excellent.

---

# 11. I would also keep the one-step Cm

I would not go back to the old “large stride captures approach → grasp → lift” formulation.

For dynamics modeling,

$$
\Delta t = 1/30\,s
$$

is cleaner.

The *policy/reference* can have a future horizon:

$$
r_{t+1}, r_{t+4}, r_{t+8}, r_{t+16},
$$

while the dynamics model remains local:

$$
(s_t,a_t)\rightarrow s_{t+1}.
$$

Those are different jobs.

This is also the standard world-model decomposition: local transition dynamics can be rolled forward or embedded in a longer-horizon controller. Modern robot world-model literature generally defines the useful object as prediction of future world states **under actions**, rather than direct reproduction of an entire demonstration endpoint. ([arXiv][7])

So the earlier stride problem was pointing at a real conceptual mistake: **we were asking one model to simultaneously represent interaction semantics and long-horizon task progress.**

V2 has mostly corrected that.

---

# Where I currently land

I would describe the architecture this way:

$$
\boxed{
\text{reference}
\rightarrow
\text{desired object effect}
}
$$

while independently:

$$
\boxed{
a_t
\rightarrow
\text{controller}
\rightarrow
FK/URDF
\rightarrow
\text{nominal surface sweep}
\rightarrow
OI\text{-}Cm
\rightarrow
\text{predicted object effect}
}
$$

and the policy learns to close:

$$
\boxed{
\text{predicted effect}
\longrightarrow
\text{desired effect}.
}
$$

That gives each component a clean responsibility:

**Reference** says *what should happen*.

**Base policy** supplies general motion/tracking competence.

**FK/controller** says *what geometric robot motion this action nominally produces*.

**OI-Cm** says *what object effect that local robot motion is likely to produce*.

**PPO/residual policy** decides *which action to take*.

This also gives OI-Cm a reason to exist that the simulator itself does not already satisfy: **counterfactual prediction before taking the action**.

So my main concern is no longer “OI-Cm cannot participate.” It is almost the opposite: **we have been trying to make it participate at the wrong interface.** V2 gives us the ingredients for an action-conditioned local interaction model, but we have not yet completed the crucial `action → controller/FK → robot surface sweep` interface, nor demonstrated MANO→Inspire transfer.

I would make that interface and the counterfactual-action validation the next experiment **before** deciding whether the next major run should be residual PPO.
