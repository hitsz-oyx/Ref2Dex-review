I checked the repository again. The main changes are in **CmResidual**, not OI-Cm itself.

The current version pointer is now `CmResidual V1.1.4`, while `ObjectInteractionCm` remains `V1.3.2`. ([GitHub][1])

### What improved

The DExplore side is materially better than the version we reviewed earlier. The environment now has a real `ReferenceProvider`, and `task.py` queries the reference at **\(t+1\)** and **\(t+16\)** separately. Those two 721-D observations are concatenated into the expected 1442-D input before calling the frozen DExplore teacher. ([GitHub][2])

The placeholder `MLP(obs)` called “Cm” has also been removed from the PPO network. The new network loads the real `ObjectInteractionCm V1.3` checkpoint, freezes it, and feeds the resulting pooled Cm feature into both actor and critic. The current plan explicitly says that OI-Cm must remain frozen in the first valid experiment. ([GitHub][3])

So the intended architecture is now much closer to:

$$
\text{DExplore frozen base}
+
\text{residual PPO}
+
\text{frozen OI-Cm features}.
$$

That is the correct high-level direction.

---

## But I found a serious new problem in the OI-Cm connection

At the moment I would **not start a long experiment with V1.1.4**.

The code loads the correct OI-Cm model, but the tensors being fed into it do not have OI-Cm semantics.

The current network does:

$$
\texttt{obj}=\texttt{obs[:,0:48]}\rightarrow[16,3]
$$

$$
\texttt{hand}=\texttt{obs[:,48:96]}\rightarrow[16,3]
$$

$$
\texttt{flow}=\texttt{obs[:,96:144]}\rightarrow[16,3].
$$

It then invents normals as constant \(+Z\) and marks every point valid. ([GitHub][4])

But the DExplore observation does **not** begin with object points, hand points and hand flow.

Its beginning consists of quantities such as:

$$
\text{reference root-position error},
$$

$$
\text{root rotation error},
$$

$$
\text{root velocity},
$$

$$
\text{link-local positions/rotations},
$$

and other tracking state. ([GitHub][5])

Therefore the current bridge is effectively doing something like

$$
\boxed{
\text{tracking-state numbers}
\overset{\text{reshape}}{\longrightarrow}
\text{fake XYZ points}
\rightarrow OI\text{-}Cm.
}
$$

The fact that the smoke test runs only demonstrates **tensor compatibility**. It does not demonstrate a semantically valid OI-Cm inference.

This is currently the biggest blocker.

---

## There is a second DExplore compatibility issue

The two temporal references are now genuinely different, which fixes the largest previous problem.

However, when constructing each observation, the code currently passes:

$$
v_{\rm link}^{ref}=0,
\qquad
\omega_{\rm link}^{ref}=0,
$$

and

$$
contact^{ref}=0,
$$

rather than the actual reference link velocities/contact targets. ([GitHub][2])

The observation builder explicitly uses these values in terms such as

$$
v_{\rm link}^{ref}-v_{\rm link},
$$

$$
\omega_{\rm link}^{ref}-\omega_{\rm link},
$$

and

$$
contact^{ref}-contact.
$$

([GitHub][5])

So the frozen DExplore teacher is **closer to its native observation distribution than before, but still not exactly on it**.

I would fix this before treating DExplore performance as our strong baseline.

---

# The OI-Cm integration also loses almost everything interesting about Cm

After OI-Cm outputs its slots, the current implementation simply computes

$$
\bar C_m
=
\frac1K\sum_k C_{m,k}.
$$

Then it concatenates:

$$
[o,\bar C_m,\bar C_m].
$$

([GitHub][4])

There are three issues with this.

First, averaging slots throws away:

* slot/contact identity;
* anchors;
* spatial distribution;
* which part of the object each interaction concerns.

That goes directly against the object-grounded representation we were just discussing.

Second, the exact same feature is concatenated **twice**:

$$
[\bar C_m,\bar C_m].
$$

This appears to be residue from the old `online/target` design. There is no reason to duplicate it when OI-Cm is frozen.

Third—and most importantly—the network does not expose OI-Cm's **predicted object effect** to the policy at all.

So PPO currently gets:

$$
\text{a globally averaged latent}
$$

rather than

$$
\boxed{
\text{interaction structure}
+
\text{predicted action effect}.
}
$$

That is a much weaker test of our hypothesis.

---

# I would change the bridge before doing anything else

The OI-Cm tensors should be constructed from the simulator geometry directly, not reconstructed from the 1442-D policy observation.

The environment already has:

* actual Inspire link transforms;
* robot q;
* object pose;
* reference/action information;
* the actual 18-D DExplore action.

So the correct path is approximately:

$$
a_t^{base}
\rightarrow
\text{target q/wrist}
\rightarrow
FK
\rightarrow
P_h^{t+1}
$$

and therefore

$$
\Delta P_h=P_h^{t+1}-P_h^t.
$$

Then construct the same quantities OI-Cm saw in training:

$$
P_o,\quad N_o,
$$

$$
P_h,\quad N_h,
$$

$$
\Delta P_h,
$$

with the same surface sampling, coordinate convention, masks and 2 cm interaction logic as V1.3.

Then:

$$
(P_o,N_o,P_h,N_h,\Delta P_h)
\rightarrow OI\text{-}Cm.
$$

That is the only comparison I would regard as valid.

---

## And I would expose more than the mean token

Given the discussion we just had about the future architecture, I would initially expose three things:

$$
C_m^{pool}
$$

for a compact summary,

$$
\hat{\Delta P}_o
$$

or preferably a compact rigid effect,

$$
\hat e=
(\Delta p_o,\Delta R_o),
$$

and some grounded interaction representation such as anchors/contact-token features.

Then actor input could look approximately like

$$
[
o_{\rm DExplore},
C_m^{pool},
\hat e,
C_m^{contact}
].
$$

Eventually the better architecture is not a global mean at all; it is contact/part tokens.

---

# There is also some obsolete code left behind

`task.py` still instantiates `CmOnlineTarget`, which is the old two-MLP online/EMA representation:

$$
\texttt{self.cm = CmOnlineTarget(...)}.
$$

([GitHub][2])

But the PPO `cm_network_builder.py` now independently loads the frozen real OI-Cm.

So there are currently **two different “Cm” concepts in the code**, one apparently unused.

Also, `get_aux_loss()` still contains the stale comment saying the online feature receives PPO gradients, even though the actual OI-Cm parameters are now set to `requires_grad=False` and inference runs under `torch.no_grad()`. ([GitHub][4])

I would remove those remnants before the next experiment. Otherwise future modifications will become confusing.

---

## My assessment of the warehouse right now

The repository has made a good conceptual correction:

$$
\boxed{
\text{real DExplore reference}
+
\text{real frozen OI-Cm}
+
\text{residual PPO}.
}
$$

But the **OI-Cm adapter is currently semantically invalid**.

So I would classify the present V1.1.4 smoke result as:

$$
\boxed{\text{engineering path supported; scientific OI-Cm integration not yet valid}.}
$$

The next work should be very specific:

1. Generate genuine OI-Cm point-cloud inputs from the simulator/FK rather than slicing the DExplore vector.
2. Restore actual reference link velocities and contact targets to the DExplore observation.
3. Remove the obsolete `CmOnlineTarget`.
4. Stop duplicating the same pooled Cm feature.
5. Expose object-effect prediction alongside Cm—not only mean slots.
6. Run **zero-residual DExplore equivalence first**, then DExplore+residual, then DExplore+residual+OI-Cm.

I would do those before another 1000-epoch PPO run. The current problem is no longer RL optimization; it is the representation contract between the simulator, DExplore and OI-Cm.
