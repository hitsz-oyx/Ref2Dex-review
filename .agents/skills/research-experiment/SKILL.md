# 科研实验执行规范

## 0. 前置条件与规则优先级

本 Skill 只在用户需求已经达到可执行状态后开始科研实验流程。

仓库根 `AGENTS.md` 中的：

- 需求确认与歧义处理；
- 用户明确任务范围；
- Git 权限；
- 仓库文档与目录规范；

优先于本 Skill。

如果仍存在 `AGENTS.md` 定义的关键需求歧义：

```text
先确认需求
→ 歧义消除
→ 再进入本 Skill
```

不得使用「快速实验」「连续推进」或「最小实现」等原则，绕过应由用户确认的关键设计问题。

同时：

> 研究结果未知，不等于需求存在歧义。

如果未知问题本身就是用户要求研究的问题，应通过假设和实验回答，而不是要求用户提前给出答案。

本 skill 包含进行科研实验时默认遵循的研究工程通用规范。涉及本仓库特定结构、研究目录、文档组织、Git 规范等内容，仍以仓库根 `AGENTS.md` 为准。

## 1. 基本工作流程

研究和实验任务默认遵循：

1. 先阅读相关代码，理解现有执行路径。
2. 写一个简短研究计划，说明：
   - 当前假设；
   - 最小实验；
   - 预期可观测结果。
3. 尽快实现并运行实验，不长时间停留在文档规划和方案讨论。
4. 优先产出：
   - 可运行代码；
   - 定量指标；
   - 日志；
   - 图表；
   - 可视化；
   - 直接行为观察。
5. 获得足够证据后记录结论，并决定：
   - 保留；
   - 撤回；
   - 修改假设；
   - 进行下一个实验。

优先采用：

```text
检查 -> 假设 -> 修改 -> 运行 -> 观察 -> 记录
```

避免：

```text
检查 -> 猜测 -> 设计 -> 写长文档 -> 重设计 -> 泛化 -> 实现
```

除非用户明确要求设计方案，否则不要长时间停留在 planning 阶段。

### 1.1 用户级目标与中间 Gate

研究任务必须区分：

- 用户级研究目标；
- 指导文档中定义的完整实验路线；
- 中间研究假设；
- implementation gate；
- sanity check。

其中：

> 中间 gate 的通过表示可以继续推进，不表示整个任务完成。

例如当前研究路线为：

```text
实现
-> forward sanity
-> 真实数据短训
-> baseline
-> 正式训练
-> evaluation
-> intervention
-> 形成结论
```

则：

```text
forward 成功
```

只表示：

```text
可以进入真实数据训练
```

而不是：

```text
当前任务完成
```

同理，以下结果默认都属于中间 gate，而不是用户级任务完成条件：

- import 成功；
- tensor shape 正确；
- forward 无报错；
- NaN / Inf 检查通过；
- 单 batch 可训练；
- synthetic data 实验成功；
- 单样本 overfit；
- 数十步或数百步短训 loss 下降；
- 单序列实验成功。

除非用户明确只要求验证上述问题，否则在这些 gate 通过后应继续推进。

如果：

- 下一步已经明确；
- 不需要用户提供新的信息；
- 当前环境具备运行条件；
- 下一步仍直接服务于当前用户级目标；

则默认继续执行下一步，不因为一个局部实验成功而停止。

研究任务的默认行为应是：

```text
快速通过必要 gate
-> 尽快进入真实实验
-> 连续推进主要实验链路
-> 获得能够回答用户级问题的证据
-> 再停止
```

连续推进过程中发现新的潜在问题时，不应自动为每个问题创建新的诊断实验。

只有当该问题：

- 阻塞下一阶段；
- 会使当前结果无法解释；
- 或可能使核心结论错误；

才优先调查。

否则记录后继续主实验链路。

Gate 只用于解除当前实验真实存在的可信度风险，不应为了遵循流程而人为增加 Gate。

如果现有证据已经足以进入下一阶段，应直接进入下一阶段，不需要额外设计一个 smoke test、短训或诊断来"证明可以继续"。

### 1.2 指导文档执行原则

如果用户已经提供研究指导文档、实验方案或明确的执行路线，应将其中与当前用户请求直接相关的连续实验链路视为当前研究任务的主要 scope。

用户当前明确请求的范围优先于指导文档。
指导文档用于决定当前目标内部如何连续推进，不自动扩大用户明确指定的任务边界。

指导文档不是待用户逐项触发的 TODO 菜单。

指导文档中的步骤还应区分：

- 当前阶段明确要求完成的主实验链路；
- 条件触发的备选实验；
- 后续工作、未来方向和可选优化。

只有当前阶段的主实验链路默认连续执行。

对于"如果失败再做""必要时再做""后续考虑""未来可以尝试"等条件性或未来性内容，
只有触发条件真实成立，或它对回答当前用户级问题确有必要时才执行；
不要仅因为它出现在指导文档中就自动展开。

如果指导文档定义：

```text
A
-> B
-> C
-> D
```

并且 A 完成后 B 的执行条件已经满足，则应继续执行 B；
B 完成后继续执行 C。

不要默认采用：

```text
完成 A
-> 写结论
-> 停止
-> 等用户再次要求 B
```

而应优先采用：

```text
完成 A
-> 检查结果
-> 若结果允许，立即进入 B
-> C
-> D
-> 在足够回答研究问题后统一形成结论
```

只有以下情况可以提前偏离或停止指导路线：

1. 当前假设已经被明确证伪，导致后续实验失去意义；
2. 后续步骤缺少必要数据、环境、权限或依赖；
3. 后续步骤涉及用户未授权的高成本资源消耗、付费服务、不可逆操作或明显超出当前研究任务正常规模的计算，需要用户决策；
4. 实际结果发现指导文档中的前提不成立，需要先修改研究假设；
5. 已经获得足够证据回答用户提出的核心研究问题。

如果只是某个 sanity check、短训或局部 gate 通过，不属于上述停止条件。

正常的训练、仿真、evaluation、benchmark 和数据处理，只要属于当前指导路线且环境资源已经可用，不应仅因为运行时间更长而停止或请求确认。

## 2. 研究优先级

优先考虑：

1. 可运行实验；
2. 最小原型；
3. 定量结果；
4. 直接对比；
5. 能回答具体问题的消融；
6. 相关行为的可视化；
7. 简洁、可复查的实验记录；
8. 工程泛化和抽象。

如果修改约 20 行代码并运行一次实验就能快速检验假设，应先这样做，不要先搭建通用框架。

但"最小实验"用于快速获得方向反馈，不是默认任务终点。

如果最小实验通过，并且下一步实验路径已经明确，应立即继续推进后续实验，而不是因为当前局部假设已经得到验证就停止。

如果一个问题可以通过一次小实验直接验证，不应仅通过代码阅读和理论推测得出结论；验证后若仍未回答用户级研究问题，应继续进入下一阶段。

---

## 3. 最小正确实现

- 只做验证当前假设或实现当前需求所需的最小改动。
- 遵循现有目录结构、接口和代码约定。
- 不重构与当前任务无关的代码。
- 不为一次性实验引入多余的：
  - 抽象层；
  - wrapper；
  - compatibility layer；
  - factory；
  - plugin architecture；
  - 配置系统。
- 没有明确兼容要求时，不为旧实验逻辑增加额外 fallback。
- 明确过时且阻碍当前实验的逻辑可以删除。
- 在简单实验实现和面向假想未来需求的泛化实现之间，默认选择前者。
- 只有出现真实、重复的需求后，再考虑抽象和泛化。

---

## 4. 必要的可信度检查

只进行会影响实验结论可信度的检查，例如：

- tensor shape 和维度；
- dtype；
- NaN / Inf；
- 坐标系；
- 单位和尺度；
- train / val / test 划分；
- 数据对应关系；
- 时间顺序；
- loss 量级；
- 数据泄漏；
- 参数是否真实变化；
- 梯度是否真实传播；
- baseline 是否能够复现；
- 指标是否真的反映研究假设；
- 对比实验是否只改变目标变量。

判断标准是：

> 这个问题会不会让当前实验结论变错？

如果不会，通常不应让它阻塞当前研究。

除非用户明确要求，或者它直接影响实验结论可信度，否则不要把研究任务扩大成：

- 全面 QA；
- CI；
- 大规模单元测试；
- 测试覆盖率工程；
- hash / checksum 系统；
- 全面格式化；
- 部署加固；
- 极端异常输入防御；
- 与当前实验无关的性能优化。

## 5. 失败处理

开发和研究阶段默认采用 fail-fast。

- 不使用宽泛异常捕获隐藏意外错误。
- 不静默替换 fallback 值。
- 不吞掉 exception。
- 不对原因未知的失败进行无限自动重试。
- 遇到错误时优先暴露真实 stack trace 和失败状态。
- 调查会影响当前实验结论的失败。
- 无关且不阻塞当前任务的问题只需简短记录。
- 理论风险或附近代码中的潜在 bug 不自动成为当前任务范围。

发现额外问题时首先判断：

> 它是否影响当前实验结果？

如果不影响，记录即可，不立即扩大任务范围。

## 6. 范围纪律和完成条件

每个任务应：

1. 明确用户级目标以及当前研究假设；
2. 检查相关代码；
3. 选择当前最直接的信息性实现或实验；必要时先做最小 Gate；
4. 实现并运行；
5. 检查数值或行为结果；
6. 根据结果决定：
   - 进入下一实验；
   - 修改假设；
   - 撤回当前方案；
   - 或形成最终结论；
7. 连续推进直到达到用户级目标或主要研究验收标准；
8. 最后统一记录关键结论。

### 中间 Gate 与完成条件

以下两类标准必须区分：

```text
中间 Gate
```

用于判断：

```text
能否继续下一阶段
```

例如：

- forward 正确；
- 数据读取正确；
- loss 可以下降；
- gradient 正常；
- 单样本可以 overfit；
- baseline 可以运行。

而：

```text
任务完成条件
```

用于判断：

```text
当前用户级研究问题是否已经得到回答
```

例如用户要求判断一个新 representation 是否有效，则通常至少需要：

```text
实现
-> 真实数据训练
-> baseline
-> evaluation
-> 必要 intervention / ablation
-> 得出支持或反对该表示的证据
```

不能因为其中某一个中间 Gate 通过就认为整个任务完成。

默认执行路径：

```text
阅读
  ↓
提出假设
  ↓
最小修改
  ↓
运行
  ↓
检查结果
  ↓
Gate 通过则进入下一阶段
  ↓
形成能够回答用户级问题的结论
```

一旦证据足以回答当前用户级问题，不继续增加：

- 推测性鲁棒性；
- 无关测试；
- 新抽象；
- 通用框架；
- 架构重设计；
- 没有明确需求的优化。

## 7. 长时间运行任务与异步等待

对于训练、仿真、编译、数据处理、模型下载、视频渲染、benchmark 以及其他长时间运行任务，禁止通过高频 polling 反复唤醒模型。

这里的 polling 指：

> Agent 为了确认后台任务是否完成，反复调用工具查询状态，而不是让工具自身长时间等待。

核心原则：

> 让工具等待，不要让模型每隔几秒重新推理一次来确认任务是否结束。

这既减少无意义的模型调用，也避免长上下文在每次轮询中被重复处理造成大量 token 消耗。

### 7.1 空 `write_stdin` polling

当 `write_stdin` 不发送任何实际内容，只用于查询后台进程状态时：

- `yield_time_ms` MUST >= `180000`；
- 不需要中间输出时优先使用 `300000`；
- 禁止每隔数秒或几十秒执行一次空 `write_stdin`。

推荐：

```text
启动任务
-> 等待 180~300 s
-> 获得输出或状态变化
-> 再决定下一步
```

避免：

```text
启动任务
-> 10 s
-> poll
-> 10 s
-> poll
-> 10 s
-> poll
-> ...
```

### 7.2 `functions.wait`

对于长时间运行的异步任务：

```text
functions.wait
```

必须使用：

```text
yield_time_ms >= 180000
```

不需要中间状态时，优先让 wait 长时间阻塞并自然返回，而不是主动进行短间隔轮询。

### 7.3 嵌套工具等待

如果外层 `functions.exec` 中存在内部长等待工具：

```text
functions.exec
└── nested tool wait
```

则外层 `@exec yield_time_ms` 必须至少比最长的内部等待多：

```text
30000 ms
```

即：

```text
outer_exec_yield_time
>=
longest_nested_wait + 30000
```

例如：

```text
nested wait: 180000 ms
outer exec:  >= 210000 ms
```

避免出现：

```text
外层 exec 先 yield
-> Agent 被重新唤醒
-> 内层工具实际上仍然在等待
-> Agent 再次进入等待
-> 产生无意义模型调用
```

### 7.4 非空 `write_stdin`

上述长等待规则只适用于纯状态 polling。

如果 `write_stdin` 正在发送实际输入，例如：

```text
"y\n"
"\n"
Ctrl-C
交互式命令输入
```

应立即发送，不要人为等待 180~300 秒。

因此需要区分：

```text
write_stdin("")
```

表示：

```text
查询状态
-> 长等待
```

而：

```text
write_stdin("实际输入")
```

表示：

```text
与进程交互
-> 立即发送
```

### 7.5 长任务默认行为

对于预期运行超过几十秒的命令：

- 尽量一次启动后长时间等待；
- 不频繁检查 stdout；
- 不因为暂时没有输出而主动高频 poll；
- 不为了展示"任务仍在运行"而反复调用模型；
- 只有中间输出会实际影响下一步研究决策时，才提前检查；
- 如果任务预计需要数分钟，应按照分钟级而不是秒级进行状态检查。

尤其适用于：

```text
训练
仿真
Isaac Sim
MuJoCo
CUDA 编译
数据预处理
模型下载
benchmark
视频渲染
大规模测试
```

## 8. Agent 与子任务使用原则

不要为了形式上的 Agent 化而拆分大量子任务。

简单问题优先由当前 Agent 直接完成。

只有在以下情况才考虑并行或独立子任务：

- 多个调查方向彼此独立；
- 多个模块可以并行阅读；
- 大型仓库需要明确按模块拆分；
- 独立实验可以并行运行；
- 最终需要单独 review 一个已经完成的实现。

避免：

```text
收到任务
-> planner
-> researcher
-> coder
-> tester
-> reviewer
-> 每个 Agent 再继续创建子 Agent
```

如果主 Agent 自己可以在较少步骤内完成任务，不要创建额外子 Agent。

子任务数量应以提高研究效率为目标，而不是最大化并行度。

## 9. 实验记录与 log.md

每个研究 task 在 `src/task/<Task>/docs/log.md` 维护自己的研究日志（不是工作日报）。

只记录会影响研究判断的新证据，不记录每个代码修改、调试命令或普通工程操作。

`log.md` 的目标：

> 让下一次启动的 Agent 在两分钟内知道：哪些路已经走过、哪些结论可信、为什么当前研究走到了这里。

### 9.1 log.md 顶部：当前研究状态

保持简短、可更新：

```markdown
# <Task> Research Log

## 当前研究状态

### 当前目标

...

### 当前最佳路线

- 数据：
- 表示：
- 预测 / 训练方式：

### 当前最佳结果

- one-step EPE: ...
- rollout EPE: ...
- checkpoint: `outputs/.../best.pt`
- commit: `abcdef1`

### 当前主要问题

1. ...
2. ...

### 当前下一步

> <一句话验证目标>

对应指导：`docs/指导/V<n>.md`
```

### 9.2 实验历史：只追加

`log.md` 中「实验历史」区域原则上只追加，不回头重写历史结果。

```markdown
---

# 实验历史

## EXP-001 — ...
...
```

### 9.3 单个实验的固定模板

```markdown
## EXP-017 — <简短名称>

### 日期

2026-08-17

### 对应指导

`docs/指导/V2.md`

### 假设

为什么这样做可能有效，期望看到什么。

不能只写「测试 dual hand」，而要写「为什么 dual hand 可能有效」。

### Baseline

- commit: `abc1234`
- config: `configs/cm_scene_v1.yaml`
- checkpoint: `outputs/.../best.pt`

### 本次修改

- active-hand input → dual-hand input
- 其余保持不变：
  - decoder
  - loss
  - dataset split
  - training budget

### 实现审查

Verdict: PASS / FAIL

关键检查：
- 左右手坐标系正确
- inactive hand mask 正确
- 无 future leakage
- evaluator 未修改

### 实验命令

```bash
python -m src.task.Cm.train \
  --config src/task/Cm/configs/cm_dual_hand.yaml
```

### 结果

| Metric                 | Baseline | Candidate |
| ---------------------- | -------: | --------: |
| one-step EPE           |  3.21 mm |   3.05 mm |
| rollout EPE            | 12.70 mm |  11.83 mm |
| bimanual subset EPE    |  8.41 mm |   6.92 mm |
| single-hand subset EPE |  3.11 mm |   3.09 mm |

### 关键观察

提升主要集中在 bimanual subset。
single-hand subset 基本没有变化。

### 解释

结果与假设一致：另一只手提供的运动信息可能减少了双手接触场景中的状态歧义。

但当前 candidate 参数量比 baseline 多约 18%，
因此还不能把提升完全归因于 dual-hand information。

### 结论状态

**INCONCLUSIVE**

当前证据支持继续研究 dual-hand，
但不足以确认「提升来自双手信息本身」。

### 决策

不将当前模型作为最终 best。
保留实验结果和代码分支。

### 下一步

做 matched-capacity 对比：

- active-hand larger model
- dual-hand model

控制参数量后重新比较。

### 证据

- checkpoint: `outputs/...`
- metrics: `outputs/.../metrics.json`
- log: `outputs/.../train.log`
- commit: `def5678`
```

### 9.4 必填字段

- 假设
- Baseline
- 本次修改
- 实验命令
- 结果
- 关键观察
- 解释
- 结论状态
- 决策
- 下一步
- 证据位置

尤其容易缺三个：

- `假设`：必须写「为什么这样做可能有效」，不能只写做了什么。
- `结论状态`：必须明确标 `SUPPORTED / REFUTED / INCONCLUSIVE / INVALID_IMPLEMENTATION` 之一。
- `下一步`：否则下次开启 context 不知道为什么做 V3。

### 9.5 结论状态

```text
SUPPORTED
当前有效证据支持假设

REFUTED
当前有效实验满足预先定义的反证条件

INCONCLUSIVE
实验有效，但不足以支持或反驳假设

INVALID_IMPLEMENTATION
实验实现无效，不产生结论状态
```

`REFUTED` 严格定义：

> 只有实验有效且确实满足假设预定义的反证条件时使用；单纯「指标没涨」通常优先判为 `INCONCLUSIVE`。

### 9.6 实现失败 ≠ 科研失败

如果发现实现 bug 导致结果异常，必须标 `INVALID_IMPLEMENTATION`，并解释原因：

```markdown
### 结论状态

INVALID_IMPLEMENTATION

### 原因

左手 points 仍然使用 right-hand root frame，
导致双手输入语义错误。

本次结果不得用于判断 dual-hand hypothesis。
```

这能避免以后误读历史：

```text
「dual hand 以前试过，不好。」
```

实际上那次只是代码 bug。

### 9.7 何时创建新 EXP

判断标准：

> 这个操作是否产生了一条可以影响科研判断的新证据？

应该记录（✔）：

- 输入 / 表示 / 训练方式的关键改变
- 容量、组件、损失的有效消融
- intervention / counterfactual
- baseline reproduction
- 3-seed 完整验证
- zero-flow 等 sanity intervention

不应该记录（✘）：

- viewer 调颜色
- 函数重命名
- 修 typo
- 改 CLI
- 修 dataloader 性能
- viewer bug 修复
- 单纯确认代码路径能够运行

如果只是实现修复不回答研究问题，放到最近实验的「实现备注」下，或者直接留在 Git commit：

```markdown
### 实现备注

- 修复 left-hand mask；
- 修复 cache indexing；
- 不改变实验定义。
```

### 9.8 log.md 更新时机

不要在训练过程中频繁改 log.md。建议：

```text
开始实验
  ↓
Codex 工作
  ↓
实现 review
  ↓
训练 / evaluation
  ↓
拿到足够结果
  ↓
一次性追加 EXP block
```

Git 可以是：

```text
实现一个有意义实验 → commit

实验完成 + log 更新 → 一起 commit
```

或者一次 meaningful experiment 一个 commit 也可以。

### 9.9 不要在根目录维护大型 research_log.md

如果项目有多个研究 task（Cm、InteractionDynamics、InteractionTransfer、PointWorldWAM、...），不要在根目录放一个 `research_log.md` 集中记录所有实验。

研究日志跟研究对象走：

```text
src/task/Cm/docs/log.md
src/task/InteractionDynamics/docs/log.md
src/task/PointWorldWAM/docs/log.md
```

如果将来需要项目总览，根目录只做一个非常短的 `docs/项目总览.md`，写每个 task 的当前阶段，不重复实验细节。

# 执行原则摘要

遇到研究任务时，默认按照：

```text
读文档
-> 读相关代码
-> 明确用户级研究目标
-> 提出简短假设
-> 最小修改 / 最小实验
-> 运行
-> 检查结果
-> 必要 Gate 通过
-> 立即进入下一阶段
-> 必要 sanity check
-> 真实训练 / baseline / evaluation / intervention
-> 获得能够回答核心问题的证据
-> 一次性追加 EXP block 到 task docs/log.md
-> 更新最靠近事实的项目文档
-> 停止
```

始终优先：

```text
可信实验结果
```

而不是：

```text
更复杂的工程结构
```

始终优先：

```text
实际运行验证
```

而不是：

```text
长时间理论猜测
```

始终优先：

```text
最小信息性实验作为快速反馈手段
```

而不是：

```text
把最小实验本身当作任务终点
```

默认：

```text
最小实验
-> 获得反馈
-> 如果方向成立，立即扩大到足够回答研究问题的实验
```

而不是：

```text
最小实验
-> 成功
-> 停止
```

不要把研究流程理解为"尽可能少做工作"，而应理解为"用尽可能少的无效工作，连续推进到足以回答用户级研究问题"。
