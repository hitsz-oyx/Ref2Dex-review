# 长时任务与异步等待

本规则适用于训练、仿真、编译、数据处理、模型下载、视频渲染、benchmark 以及其他预计运行超过几十秒的命令。

## 核心原则

禁止通过高频 polling 反复唤醒模型。这里的 polling 是 Agent 为了确认后台任务是否完成，反复调用工具查询状态，而不是让工具自身长时间等待。

核心原则：

> 让工具等待，不要让模型每隔几秒重推理一次来确认任务是否结束。

这样可以减少无意义的模型调用，也避免每次轮询都重复处理长上下文。

## 空 `write_stdin` 查询

当 `write_stdin` 不发送任何实际内容、只用于查询后台进程状态时：

- `yield_time_ms` 必须大于等于 `180000`；
- 不需要中间输出时优先使用 `300000`；
- 禁止每隔几秒或几十秒执行一次空查询。

推荐流程：

```text
启动任务
  → 等待 180～300 秒
  → 获得输出或状态变化
  → 再决定下一步
```

应避免：

```text
启动任务
  → 10 秒
  → poll
  → 10 秒
  → poll
  → 10 秒
  → poll
  → …
```

## `functions.wait`

对于长时间运行的异步任务，使用 `functions.wait`，并令 `yield_time_ms >= 180000`。不需要中间状态时，优先让 wait 长时间阻塞并自然返回，而不是主动短间隔轮询。

## 嵌套工具等待

如果外层 `functions.exec` 中存在内部长等待工具：

```text
functions.exec
└── nested tool wait
```

外层 `@exec yield_time_ms` 必须至少比最长的内部等待多 `30000 ms`：

```text
nested wait: 180000 ms
outer exec:  >= 210000 ms
```

避免外层 exec 先返回、模型被重新唤醒，而内层工具实际上仍在等待，随后又产生无意义的等待调用。

## 非空 `write_stdin`

上述长等待规则只适用于纯状态 polling。如果 `write_stdin` 正在发送实际输入，例如：

```text
"y\n"
"\n"
Ctrl-C
交互式命令输入
```

应立即发送，不要人为等待 180～300 秒。需要明确区分：

```text
write_stdin("")         → 查询状态，长等待
write_stdin("实际输入") → 与进程交互，立即发送
```

## 长任务默认行为

- 尽量一次启动后长时间等待。
- 不频繁检查 stdout，也不要因为暂时没有输出而主动高频查询。
- 只有中间输出会实际影响下一步科研决策时，才提前检查。
- 预计运行数分钟的任务按分钟级而不是秒级检查。

典型任务包括：

```text
训练
仿真
Isaac Sim
MuJoCo
CUDA 编译
数据预处理
模型下载
benchmark
视频渲染
大规模测试
```
