## Activity 的正式定义

我建议定义成：

> **Activity 是一次“具有长期追溯价值的工作单元”的完成摘要。**

通常：

```text
一个 AI task
≈ 一个 Activity
```

不是：

```text
一次 shell command
一个 commit
一次 pytest
一次 checkpoint
一次 RUNNING 状态
```

### 应该进入 Activity 的

第一类是**完成了一次代码/配置修改**。

例如：

```text
修 V1.18 planner OOM
增加 chunked candidate evaluation
修 reference indexing bug
增加 Cmv2 adapter compatibility
```

这类非常典型。

第二类是**正式修改了指导或研究文档**。

例如你刚刚说的：

> 把我们讨论确认的一条约束追加进 `指导/V1.18.md`

这是一个 activity：

```text
ACT-...-v118-guidance-update.md
```

因为项目的正式研究意图发生了可追溯变化，哪怕代码没动。

第三类是**治理或基础设施变化**。

比如：

```text
重构 AGENTS.md
修改 Skill
增加 verify.py
增加 CI
改变目录规范
```

第四类是**重要诊断产生了可长期使用的事实**。

例如：

> 经过系统检查发现 planner 显存主要来自 K×N candidate tensor，而不是 PPO rollout buffer。

即使没改代码，如果这个结论以后会影响设计，就值得有一条 activity。

第五类是**重要操作行为**，但只限真正值得追踪的。

例如：

```text
迁移一个 cache schema
废弃某个 checkpoint
停止一个确认有错误实现的正式 run
恢复一个正式实验
```

不是所有 operation 都记。

---

# 什么不应该进入 Activity

这些全部不要再建 Activity：

```text
AI 开始任务
创建 branch
读了哪些文件
跑了一次 grep
py_compile PASS
单个 pytest PASS
第一次实现失败
改了两行再重试
GPU 当前 90%
epoch 38 checkpoint 到了
epoch 76 checkpoint 到了
RUNNING
poll 一次进程
临时 OOM 后调小 batch 再试
```

这些属于：

```text
Git
terminal log
CI
train.log
run manifest
```

不属于长期知识。

一句判断标准：

> **三个月后回来，这件事值得我单独知道吗？**

不值得，就不要建 Activity。

# `activities/README.md` 做什么

它不是另一份日志。

它只是索引。

例如：

```markdown

### V1.18
- ACT-...
- ACT-...

### V1.17
- ACT-...
```

网页 GPT 以后先读这个索引。

真正需要哪一次修改，再打开对应 ACT 文件。

# Experiment 则完全是另一套定义

Experiment：

> **一次针对明确科研假设的证据收集单元。**

例如：

```text
EXP-V118-001
Cmv2 planner candidate scoring 是否与 reference effect 对齐？

EXP-V118-002
2048 env 是否在当前实现下可训练？

EXP-V118-003
V1.18 planner PPO 是否改善 reference tracking？
```

Experiment 不关心：

```text
改了几个 Python 文件
pytest 跑了什么
AI 做了什么
```

它关心：

```text
Hypothesis
Protocol
Runs
Metrics
Evidence
Conclusion
Limitations
```

---

# Experiment 文件示例

```markdown
# EXP-V118-003 — PPO pilot

research_version: V1.18
status: completed
conclusion: INCONCLUSIVE

## Hypothesis

V1.18 Cmv2-guided planner 能提升 PPO 的 reference tracking。

## Protocol

- dataset: GRAB
- sequence: ...
- seed: 42
- num_envs: 256
- budget: ...
- metric: ...

## Runs

- `cmres_v118_pilot_seed42_...`

## Evidence

- reward ...
- object error ...
- contact ...
- baseline ...

## Conclusion

INCONCLUSIVE

虽然训练稳定，但当前预算下没有足够证据说明
Cmv2-guided planner 优于 baseline。

## Limitations

- single seed
- short horizon
- ...
```

# 一个 Activity 可以关联 Experiment

这是两者最重要的关系。

例如你先实现：

```text

```

然后运行：

```text
EXP-V118-003-ppo-pilot.md
```

Activity 中可以写：

```text
follow-up experiment:
EXP-V118-003
```

Experiment 中写：

```text

commit abc1234
activity:
ACT-20260918-v118-planner-ppo
```

于是形成：

```text
指导 V1.18
    ↓
实现 Activity
    ↓
Git commit
    ↓
Experiment
    ↓
科研结论
```

非常清楚。

# 一个 Experiment 可以包含很多 run

这一点也必须明确。

不要：

```text
seed42 = 一个 experiment
seed43 = 一个 experiment
seed44 = 一个 experiment
```

如果它们是在回答同一个科研问题：

```text
EXP-V118-003
├── run seed42
├── run seed43
├── run seed44
└── run baseline
```

Experiment 是**科研问题的单位**。

Run 是**执行单位**。

所以最终是四层：

```text
Research Version
V1.18
│
├── Activity
│   └── 做了什么修改
│
├── Git commit
│   └── 实现事实
│
└── Experiment
    ├── run_001
    ├── run_002
    └── run_003
```

# Activity 和 Experiment 的交叉判断

最简单可以用这个表：

| 事情                   |        Activity |                 Experiment |
| -------------------- | --------------: | -------------------------: |
| 修 planner bug        |               是 |                          否 |
| 优化显存                 |               是 |                          否 |
| 增加测试                 |   跟随对应 Activity |                          否 |
| 修改 V1.18 指导          |               是 |                          否 |
| 修改 AGENTS            |               是 |                          否 |
| 跑 smoke 验证 wiring    | 通常写入对应 Activity |                          否 |
| 256-env pilot 验证方法效果 |             可索引 |                      **是** |
| seed42/43/44 正式对比    |               否 | **同一个 Experiment 的多个 run** |
| checkpoint 38 到达     |               否 |                          否 |
| 正式实验最终完成             |  Activity 可只留索引 |                      **是** |
| 诊断得到重要科学发现           |              可是 |       视是否有明确 hypothesis 而定 |

# 八、关键是：什么东西能叫“补充指导”？

我建议定三个等级。

## A. Clarification：澄清原意

例如：

> Cmv2 应该更偏向 critic/guidance，不是直接 decoder action。

如果这个只是把原本 V1.18 的意图说得更明确：

```text
继续写进 指导/V1.18.md
```

并记录：

```text
V1.18.4
type: guidance-clarification
```

不升 V1.19。

---

## B. Additional constraint：增加边界，但不换方法

比如：

> V1.18 中禁止直接把未来帧 GT 输入 policy。

或者：

> planner 必须保持 frozen Cmv2。

如果仍然属于原 V1.18 的设计思想：

```text
继续 V1.18
```

作为补充指导。

---

## C. Research contract change：改变方法本身

比如原本：

```text
Cmv2 = critic / guidance
```

你后来决定：

```text
Cmv2 = direct action generator
```

或者：

```text
reward formulation 根本改变
teacher target 改变
action semantics 改变
planner objective 改变
```

那不能再叫“V1.18 补充”。

应该：

```text
V1.19
```

# 九、那讨论过程中怎么处理？

```markdown

> 本节不是正式 research contract。

- 是否限制 Cmv2 只能作为 critic？
- residual 应在接近阶段降低还是完全停止？
- 是否允许 candidate action sampling？
```

但是这里有一个风险：

网页 GPT 可能误把它当正式规则。

所以我其实更推荐单独：

```text

```

结构：

```text

= 已确认、权威

discussions/V1.18.md
= 当前仍在讨论、非权威
```

这个非常实用。
