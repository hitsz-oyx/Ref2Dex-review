# P0：必须先修的 4 个问题

### 1. 推送分支缺了它自己引用的指导文件

现在：

`docs/activities/V1.1-governance-workflow.md`

明确链接了：

```text
docs/指导/V1.1.md
docs/指导/V1.1a.md
```

`docs/README.md` 也链接了：

```text
指导/V1.1.md
```

但我直接查了远端 `ai/governance/phase1`：

```text
docs/指导/V1.1.md   不存在
docs/指导/V1.1a.md  不存在
```

所以目前远端仓库文档实际上是断的。

更重要的是 Activity 里还写着：

```text
python tools/verify.py --changed
VERIFY PASS
所有 Markdown 链接可解析
```

说明 **verify 在本机把未提交文件也当成“存在”了**。

这是当前 verify 最值得修的 bug。

应该规定：

> 对准备提交的 `activities/`、`experiments/`、README、guidance 等 Git 文档，其 Markdown 本地链接目标必须也是 Git-tracked / staged 的仓库内容，不能仅仅“本机存在”。

否则就会出现：

```text
本机 VERIFY PASS
↓
push
↓
GitHub 文件缺失
```

这和我们做 verify 的目的正好相反。

### 2. `verify --changed` 本地默认只看 staged，不够稳

现在实现是：

```text
CI：
base...HEAD

本地：
staged files
```

有一个问题。

如果 AI：

```text
修改
→ commit
→ 再跑 verify
```

这时候 staged 是空的。

verify 会得到：

```text
没有检测到变更
VERIFY PASS
```

这是一个假 PASS。

我建议改成：

```text
本地默认：
merge-base(oyx, HEAD)...HEAD
+
staged changes
```

如果是在 `oyx` 本身工作，则只看 staged。

也就是你之前定义的：

> **验证本次任务 branch 相对稳定基线的全部修改。**

而不是验证“此刻 index 里恰好有什么”。

---

### 3. `--all` 当前其实不是 full

`verify.py --all` 现在执行：

```bash
pytest -q
```

但仓库的 `pytest.ini` 还是：

```ini
testpaths = tests
```

因此：

```text
src/task/CmResidual/tests/
src/task/ObjectInteractionCmv2/tests/
...
```

并不会被这个所谓 `--all` 完整覆盖。

既然我们刚刚已经确定：

> verify 主要负责当前提交影响范围，

我反而建议**直接删除 `--all`**。

只保留：

```bash
python tools/verify.py --changed
```

以后真需要全回归，再专门设计 regression workflow。

不要保留一个名字叫 `--all`、实际上不 all 的入口。

---

### 4. 治理 Activity 的 `git_commit` 写错了

当前 Activity 写：

```text
git_commit: ebefee4e...
```

但真正包含这次治理修改的是：

```text
4871eed0...
治理：收敛 V1.1 指导与活动规范
```

`ebefee4e` 是它的 parent，而且还是：

> `CmResidual: 修复 DExplore Horovod rank 设备映射`

所以当前 Activity 的 Git 身份是不准确的。

这其实暴露了一个更深的问题：

> **Activity 文件如果和代码修改在同一个 commit 里，它无法提前知道自己的 commit SHA。**

因此我建议不要强制 Activity 写自己的 `git_commit`。

Activity 更适合记录：

```text
branch
base_commit
PR
related_commits（已知时）
```

而 Activity 文件自己属于哪个 commit，Git 本身已经能查。

否则会制造“为了记录 commit SHA，再 commit 一次；SHA 又变了”的循环。

# P0.5：治理 branch 混进了别的任务

`ai/governance/phase1` 相对 `oyx` 有 5 个 commit。

但其中前 4 个是：

```text

CmResidual: 切换 V1.17.3 双卡 DExplore 运行

```

最后第 5 个才是：

```text

```

所以现在：

```text
ai/governance/phase1
```

不是纯 governance branch。

如果这是因为你先做完 CmResidual 再从当前 HEAD 开治理，技术上当然能工作，但按照我们刚刚定义的新规则，这应该拆开。

建议：

```text
CmResidual 那四个 commit
→ 单独一个 CmResidual branch/PR

4871eed 治理修改
→ 单独 governance branch/PR
```

至少从新体系正式启用以后，不要再混。

# 11. CI 现在还没有实际运行

我也检查了：

```text
ai/governance/phase1
```

目前没有 PR。

而 workflow 配置是：

```yaml
pull_request:
push:
  branches:
    - oyx
    - main
```

所以单纯 push `ai/governance/phase1` **不会触发 CI**。

这不一定是错。

我建议规定：

> AI 第一次 push 完就创建 Draft PR。

于是：

```text
branch push
→ draft PR
→ CI verify
→ AI继续修改
→ CI持续跑
→ ready for review
```

不需要把 `ai/**` 全部加入 push trigger。

Draft PR 就是最自然的审查入口。
