## 上次提出的四项已经落实

1. 默认 `log_every_steps` 已从 1 改成 100，避免轻量模式每步执行 CUDA 同步。

2. 训练循环现在每步记录 `step_start`，并把它传给 `PerformanceMonitor.observe_step()`；性能窗口逐步累加 `_window_step_seconds`，因此验证、保存 checkpoint 和日志写入不会进入训练 step 时间。

3. `PerformanceMonitor.start()` 现在无论 light 还是 profile 模式都会重置窗口，解决模型构建、恢复 checkpoint 污染第一个统计窗口的问题。

4. 已加入 `world_size`，`samples_per_s` 现在乘以进程数，表示 DDP 全局吞吐量。`BaseRunner` 创建监控器时也正确传入了 `distributed.world_size`。

Base 的边界也保持正确：`performance.py` 只依赖通用训练阶段，没有 sequence、文件格式和缓存语义。

## 还剩一个 CUDA 计时顺序问题

当前顺序是：

```python
step_seconds = max(
    perf_counter() - step_start_seconds,
    1e-8,
)

# 先累计 step_seconds

should_log = global_step % self.log_every_steps == 0

if self.device.type == "cuda":
    torch.cuda.synchronize(self.device)
```

也就是**先计算 step 时间，再等待 CUDA 完成**。

CUDA 是异步执行的。如果窗口末尾仍有 GPU 工作未完成，这部分等待时间不会进入 `_window_step_seconds`，但同步本身仍然会拖慢训练。因此可能出现：

```text
实际训练速度被同步拖慢
但 perf/step_ms 又没有记录这段同步等待
```

当前 `train_step()` 后面把 GPU 上的 `grad_norm` 转到 CPU，实际上通常已经隐式同步，所以这个问题在现有训练路径中可能不明显；但通用的 `PerformanceMonitor` 不应依赖这种偶然同步。

### 应改成先同步，再计算最后一步时间

```python
should_log = (
    global_step % self.log_every_steps == 0
)

# 窗口最后一步先等待 CUDA 完成。
# 前面各步排队的 GPU 工作也会在这里结算。
if should_log and self.device.type == "cuda":
    torch.cuda.synchronize(self.device)

step_seconds = max(
    perf_counter() - step_start_seconds,
    1e-8,
)

self._window_steps += 1
self._window_samples += int(batch_size)
self._window_data_wait_seconds += data_wait_seconds
self._window_step_seconds += step_seconds

if not should_log:
    return None
```

然后删除后面原来的：

```python
if self.device.type == "cuda":
    torch.cuda.synchronize(self.device)
```

这样窗口最后一步会承担该窗口所有尚未完成的 CUDA 尾部时间，窗口总耗时才是可信的。

不过测试全部使用 CPU，因此无法发现上面的 CUDA 同步顺序问题。还建议增加一个纯 mock 测试，验证调用顺序为：

```text
cuda.synchronize
→
perf_counter 计算 step_seconds
→
窗口累计
```

另外有一个测试注释写着“窗口内 1 步”，但实际统计了 step 3 和 step 4 两步。这不影响当前断言，不过注释应改成“窗口内 2 步”。

## 低优先级问题

`performance.mode=off` 名义上是“完全关闭”，但 `BaseRunner` 仍然会：

```python
step_start = time.perf_counter()
data_wait_start = time.perf_counter()
self.performance.observe_step(...)
```

因此不是绝对零开销，只是开销非常小。

暂时不必为此增加训练循环分支。你主要使用的是 `light` 和 `profile`，保持当前代码更简单。

## 当前结论

这次修改已经基本完成。现在只需要修正：

```text
CUDA 同步必须发生在窗口最后一步的 step_seconds 计算之前
```

其余四项主要问题都已解决
