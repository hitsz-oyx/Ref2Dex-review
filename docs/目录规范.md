# Ref2Dex 目录规范

## 一、先按产物性质归类

| 内容 | 规范位置 | 是否提交 |
| --- | --- | --- |
| 共享运行时、Contract、Runner、Manifest | `src/base/` | 是 |
| Task 模型、Dataset、Task 工具 | `src/task/<Task>/` | 是 |
| 独立研究实验 | `src/task/<Task>/research/<experiment>/` | 定义文件是，产物否 |
| 原始数据 | `data/raw_data/` 或外部 `dataset/<name>/data/` | 否 |
| 派生 cache、split、统计 | `data/processed_data/` | 否 |
| 预训练模型、MANO、SMPL-X、URDF | `src/task/<Task>/assets/` | 外部文件忽略；描述说明可保留 README |
| 训练、评估、正式 benchmark | `outputs/<task>/<run_id>/` | 否 |
| 研究诊断、可视化、小型分析 | `research/<experiment>/output/<run_id>/` | 否 |
| 长期 Activity 与科学结论 | 当前作用域 `docs/activities/`、`docs/experiments/` | 是 |

## 二、研究目录固定格式

```text
src/task/<Task>/research/<experiment>/
├── README.md
├── experiment.yaml
├── run.py 或其他实验脚本
└── output/<run_id>/
    ├── run_manifest.json
    └── 生成的图、表、NPZ、日志
```

`research/` 根目录不放散脚本，不放结果文件，不放 checkpoint。实验目录名使用稳定的
`lower_snake_case`，日期和 checkpoint 名字属于 `run_id`。

### 重要实验标记

需要长期保留、用于论文或作为主对照的实验，在其 `experiment.yaml` 增加可选元数据：

```yaml
importance: primary       # primary / reference / exploratory
pinned: true
tags: [paper, baseline]
```

`pinned` 只表示导航优先级，不代表结果成立；最终科学结论写入独立 experiment card，并在
对应 Activity 中链接所有关键 `run_id` 和证据。不要用文件名加 `final`、
`best` 代替这个标记。

## 三、三种运行目录

- `outputs/<task>/<run_id>/`：BaseRunner 训练、评估和带 checkpoint 的正式运行；
- `research/<experiment>/output/<run_id>/`：只读诊断、可视化和局部 benchmark；
- `data/processed_data/<producer>/<schema>/<version>/`：可复用数据和 cache。

根级 `output/` 是历史兼容目录，只读、不新增。`results/`、`result/` 不再创建；需要长期保留
的结果解释写入 experiment card。运行启动、停止、完成和失败等长期活动摘要写入独立 Activity。

## 四、数据代码与数据文件

- `src/task/<Task>/dataset/`：运行时读取器、schema 和 Dataset 实现；
- `src/task/<Task>/tools/data/`：该 Task 的 cache 构建、split、校准和统计命令；
- 根 `tools/`：跨 Task 的通用工具和仓库维护命令；
- `dataset/<name>/`：外部数据集代码和官方布局；
- 实际生成的文件统一落到 `data/processed_data/`，不能写回代码目录。

## 五、Task 版本线与指导谱系

`research_version` 是研究方法身份，只有 Methods 语义变化才递增。`work_version`（如 `V1.18.4`）是可选的
工作单元编号，不替代 research_version。基线指导使用 `指导/Vn.m.md`，已确认细化使用单个小写后缀
`指导/Vn.ma.md` 至 `指导/Vn.mz.md`。读取时必须包含完整谱系；跨文件明确冲突以后字母为准，同文件冲突须用户确认、
更新指导并定稿计划后才能实施。Task 内保留代码、配置、研究文档和索引：

```text
src/task/<Task>/
├── assets/                    # 该 Task 的外部资产入口（实际内容被忽略）
└── docs/
    ├── 指导/Vn.m.md          # 用户维护的基线及字母补充指导
    ├── plan/Vn.m.md          # L2/L3 或新研究版本的最终计划
    ├── activities/README.md  # 长期工作单元索引
    ├── experiments/README.md # 科学证据索引
    └── architecture/Vn.m.md  # 用户指令下冻结的架构快照
```

数据和 cache 不放入 Task 目录，训练/评估配置直接声明其外部路径，不新增 Task 内路径索引。
Task 专属外部资产放在被忽略的 `src/task/<Task>/assets/`；迁移期间允许保留指向旧位置的兼容软链接，
但新配置必须使用 Task-local canonical 路径。根 `assets/` 不再承载新资产。

## 六、Manifest 职责

| 文件 | 位置 | 职责 |
| --- | --- | --- |
| `experiment.yaml` | `research/<experiment>/` | 实验目的、入口、指导/plan 和默认产物位置 |
| `manifest.json` | cache 根目录 | 数据来源、schema、split、坐标系、采样和统计 |
| `asset_manifest.json` | `src/task/<Task>/assets/` 或资产归档 | 外部模型/资产来源、版本和校验信息 |
| `config.json` | 每个运行目录 | 解析后的参数快照，面向用户查看“这次运行想做什么” |
| `run_manifest.json` | 每个运行目录 | 一次运行的代码、配置、输入、checkpoint、seed、research_version/git_commit/run_id 和输出；只引用 metadata，不内嵌完整数据合同 |
| `metrics.jsonl` | 训练运行目录 | 逐 step/epoch 曲线，面向机器读取和绘图 |

这些文件不可互相替代。`metadata.json`、`config.json` 和 `split.json` 可以作为子快照，但不能
替代对应的顶层 manifest。运行目录中的 `metadata.json` 由 Task Dataset/adapter 提供数据合同和
实际解析出的 split、shape、坐标系等运行时字段，BaseRunner 只补充通用运行字段（如 run 名称、步数、
warmup）；`config.json` 记录用户声明和解析后的配置意图，供用户审计；checkpoint 内嵌的
config/metadata 才由 checkpoint 加载链用于恢复模型和推理数据合同，运行目录的外部快照不自动替代
它们。不要把完整 metadata 再复制到 `run_manifest.json`。训练/评估终态、最佳 checkpoint 和失败/停止原因统一写入最近作用域的
独立 Activity；历史或 Task 专属 `summary.json` 可以保留，但 BaseRunner 新运行不再自动生成。
Activity 通过 Markdown 链接连接 plan、experiment card、变更文件和运行产物。
Task 配置不再声明 `components` 或 `component_registry`；模型、
Runner 和 Dataset 由 Task 自身的 Python 配置直接选择。

## 七、Activity、experiment 与产物导航

新 Activity 目录为最近作用域的 `docs/activities/`，每次具有长期追溯价值的完成工作单元创建一个独立 Markdown
文件；`activities/README.md` 仅按日期、版本和类型索引。根 Activity 记录跨 Task/治理事实，Task Activity 记录局部
事实。Activity 至少含目标、变更、文件、保护语义、验证、branch、git_commit 和结果。普通命令、单次 pytest、轮询、
逐 step/checkpoint 和普通 smoke 不建立 Activity。

新 experiment 目录为最近作用域的 `docs/experiments/`。每张 card 记录 hypothesis、protocol/configuration、runs、
evidence、conclusion 和 limitations；一个 card 可链接多个 run。Activity 回答“做了什么”，experiment 回答“知道了什么”。
历史 `logs/activity_log.md` 与 `experiment_log.md` 仅作只读审计，不批量回填或拆分。

activity 和 AI 最终回复中的本地导航同时满足两层要求：链接显示文本写仓库根目录相对路径；仓库内
Markdown 的目标按当前文档所在目录书写，聊天回复的 target 使用客户端支持的本地绝对文件路径。Task
日志中的显示文本应直接写 `output/research/<run_id>/metrics.jsonl`、`train.log` 或关键 checkpoint，target 再按日志所在目录计算；不要把
`../../..` 作为显示给用户的路径，仓库文档中也不要保存依赖某台机器的绝对路径。

每类事件至少提供以下关键入口：

| 事件 | 必须导航的现有目标 |
| --- | --- |
| train / eval / benchmark | 运行目录、`config.json`、`run_manifest.json`、实际生成的 `metrics.jsonl`/`train.log`、终态 Activity、最佳或最近 checkpoint（产生时） |
| research 诊断 / 可视化 | output run 目录、`run_manifest.json`、终态 Activity、支撑结论的关键图、表或数据文件 |
| data / cache 生成 | 数据目录、`manifest.json`、关键统计或验证报告 |
| code / config / documentation 修改 | plan（适用时）、Activity 和实际修改文件 |

批量帧、分片、逐 step 文件不逐个链接，由运行目录和 manifest 索引。`STARTED` / `RUNNING` 时尚未生成
的目标可在同一行标记 `PENDING`；终态 Activity 只能保留可解析的本地链接。`verify.py --changed` 检查变更
Markdown 链接；历史日志不因启用新规则而批量回填。

## 八、测试目录与验证范围

测试按所有权归类，当前根目录下已有测试暂不迁移，统一视为 legacy。未来测试目录和当前 63 个根测试
的逐文件归类见 [tests/README.md](../tests/README.md)。

| 变化范围 | 默认验证范围 |
| --- | --- |
| 单一 Task 代码、配置或局部工具 | `src/task/<Task>/tests/`；触及公共接口时加 `tests/shared/` |
| `src/base/`、公共配置、Runner 或 Manifest | `tests/shared/` + 受影响 Task 的最小 smoke |
| 跨 Task、checkpoint 或数据格式 | `tests/integration/` + 所有受影响 Task |
| `process/` 数据 adapter 或 Stage | `process/tests/` + 消费方 Task 定向测试 |
| 治理文档、Skill、目录和链接合同 | `tests/governance/` + activity 链接审计 |

在物理迁移完成前，`pytest.ini` 和根 `tests/conftest.py` 保持不变；需要全量回归时仍可运行根级
`pytest`。根 `tests/` 不再新增测试，新的测试必须进入表中的目标目录。

## 九、子任务递归规则

子任务继承根项目总览、`AGENTS.md` 和父 Task 的指导，不重复创建项目总览。只有子任务具有独立
研究问题、实现边界或可单独复现的运行时，才建立 `docs/README.md` 和相应记录目录；没有实际事件或
事实不创建空 Activity。子任务的 Activity 需要链接父 Task 的 Activity、experiment 或 run，
使用户可以从根入口逐级跳转到局部证据。
