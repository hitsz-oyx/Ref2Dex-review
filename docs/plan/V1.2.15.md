## 1. 目标与命名决定

本计划拟收口 Ref2Dex 的 AI 工作流，使“用户提出任务 → AI 执行 → 运行反馈 → 产物追溯 → 研究结论”形成可检查的闭环。

采用 `modification_version` 作为唯一的版本身份，表示一次已经确认的工作/变更边界。它可以覆盖代码、配置、数据处理、训练、评估、诊断和运行操作；不再把 `guidance_version` 或 `plan_version` 作为运行或修改的顶层版本字段。

`modification_version` 不等于每一次进程或每一条日志事件。每个事件另有稳定的 `activity_id`，每次具体执行另有 `run_id`；这样同一个治理/实现边界下可以有多个并行训练和诊断运行，而不会为了每次运行无限增加版本号。

活动时间线统一命名为 `activity_log.md`：记录代码、配置、数据、训练、评估、诊断、启动/停止和产物等实际发生的工作事件。历史 `modification_log.md` 保留为只读审计记录，不再追加新条目。

## 2. 现状边界

- `status_log.md` 不再作为新的规范入口。切换点起将其移交为 `activity_log.md` 的活动时间线；旧内容不做格式回填，历史文件仍可通过 Git 历史定位。从切换点起，活动记录使用新合同。
- 不新增独立的 `run_state.json`。运行状态只在活动记录中记录启动、停止、完成、失败等关键事件；详细 step 曲线仍由运行日志和 `metrics.jsonl` 承担。
- `experiment_log.md` 继续保留，负责假设、变量、证据、指标和科研结论；活动记录只写摘要并链接到实验记录。
- `decision_log.md` 继续保留，负责非平凡选择及其理由；不能把决定理由埋在活动记录中。
- `architecture_log.md` 和 `repo_memory.md` 继续保留，分别承担合同快照和可迁移事实。
- `machine_memory.md` 继续为 Git 忽略的本机事实，不进入公共运行 manifest。

## 3. 规范分层

### 3.1 `AGENTS.md`

只保留必须始终生效的本地安全规则、权限边界、任务模式和交接要求。增加以下模式：

- `read-only/diagnostic`：只读检查，不要求新 plan，不改变研究语义；
- `run-only/operation`：在已有 final plan 和实验定义下运行，不修改代码或研究变量；
- `change`：修改代码、配置、数据、schema 或指标，执行 plan/审批闸门；
- `governance`：修改 `AGENTS.md`、Skill、目录规范或公共合同，按 L3 处理并要求用户确认。

路径表和版本类别详细定义只在 `docs/目录规范.md`、`docs/modification_policy.md` 中维护，避免重复漂移。

### 3.2 当前版本指针

新增根级 `docs/current_versions.yaml`，只记录当前作用域的 `modification_version`，示意：

```yaml
repository:
  modification_version: V1.2.15
tasks:
  Cm:
    modification_version: V1.2.11
```

计划和用户指导不再写入运行 JSON 作为版本字段。它们的对应关系由总文档和相同的数字后缀说明；需要跳转时在活动记录、计划和实验记录中使用 Markdown 路径链接，不新增 JSON 关联层。

### 3.3 记录类型按事件触发

| 事件 | 必需记录 | 记录内容 |
|---|---|---|
| 仓库或配置实际修改 | 活动记录 | 文件、原因、影响等级、审批、验证、版本 |
| 训练/评估/benchmark/数据处理/诊断运行 | 活动记录摘要 + `experiment_log.md`（正式实验时） | 命令、run、状态、产物、证据入口 |
| 非平凡设计选择 | `decision_log.md` | 选择、理由、替代方案、回滚 |
| 数据/模型/指标合同变化 | `architecture_log.md` | schema、坐标、单位、不变量 |
| 跨任务长期事实 | `repo_memory.md` | 可迁移事实和来源 |
| 当前运行/阻塞/下一步变化 | `activity_log.md` | 低频快照和入口链接 |

### 3.4 文档职责边界

- `docs/项目总览.md`：全局入口、Task 索引和极少量全局事实；不保存详细 Tensor、实验进度或机器私有环境。
- 根 `docs/logs/architecture_log.md`：跨 Task 的 Pipeline、共享数据流和公共合同。
- `src/task/<Task>/docs/logs/architecture_log.md`：该 Task 的模型、数据字段、坐标系和局部不变量。
- `architecture_log.md` 的头部只保留 `last_updated`；不再重复写 `scope`、`last_verified`、`related` 等导航元数据，作用域由文件路径确定，相关入口由正文链接表达。
- `docs/目录规范.md`、`docs/modification_policy.md`：目录和版本规则的唯一规范源。
- `docs/ai_task_checklist.md`：一页式操作清单，只引用上述规范，不重新定义它们。

目前项目总览与根架构记录存在少量重复，先通过职责收窄解决，不直接合并文件。项目总览中的 Python/GPU/绝对路径等机器事实应迁移到 `machine_memory.md`；根架构记录中的 Cm 专属细节应逐步回收到 Cm Task 文档。

### 3.5 命名和递归目录

- 新的机器可读路径统一使用英文 ASCII 和 `lower_snake_case`；文档标题和正文可以继续使用中文。
- 时间线类记录使用 `_log.md` 后缀：`activity_log.md`、`experiment_log.md`、`decision_log.md`；架构是当前合同事实，目标命名可为 `architecture.md`，但现有 `architecture_log.md` 在引用迁移前保留。`repo_memory.md` 和 `machine_memory.md` 保持 memory 命名，因为它们不是时间线。
- `README.md` 是每个作用域的唯一入口；Task 不复制根项目总览，只从自身 README 链接到根入口。
- Task 文档按最近作用域递归维护：根记录跨 Task 事实，Task 记录本 Task 的实现、活动和结论；没有实际内容的日志不创建空文件。
- 现有中文目录（如 `指导/`）不在本计划中一次性批量重命名；新目录逐步采用 `guidance/`、`plan/`、`architecture/`、`logs/`，历史路径只保留兼容入口或 Git 历史。
- 根级说明文档的 canonical 命名为 `project_overview.md`、`directory_spec.md`、`modification_policy.md`、
  `ai_task_checklist.md`；本次用户确认后先完成后两者的重命名，旧中文文件保留为兼容跳转入口。

### 3.6 根版本的使用边界

- 根 `modification_version` 只在仓库治理、共享 `src/base`、跨 Task 架构/合同或全局目录规则发生变化时递增。
- Cm-only 的训练、评估和局部实现不递增根版本，只使用 Cm 作用域的 `modification_version` 和 `activity_id`。
- 根没有“大科学创新”时也可以保留上一次根治理版本作为定位索引；版本表示工作边界，不表示研究创新程度。

## 4. 运行与反馈合同

不新增实时状态 JSON。所有正式运行和长任务在活动记录中写入生命周期摘要：

```text
run_status: STARTED | RUNNING | COMPLETED | FAILED | STOPPED | UNKNOWN
```

活动条目至少记录精确到秒的 `timestamp`、`activity_id`、`modification_version`、可选的 `run_id`、启动/终态时间、命令、输出路径、关键 step/epoch、最佳 checkpoint、ETA（如有）和退出码（如有）。提交定位字段必须记录活动发生时可见的最近一次已提交 HEAD 哈希（例如 `base_commit`），不得写“未提交”作为提交值；若工作区有未提交改动，可另记 `worktree_dirty: true`。不要求按 heartbeat 高频更新；需要检查时，AI 记录 `last_checked_at` 和 `status_basis`（进程/日志/metrics/用户提供），而不是维护实时心跳。

AI 回复合同：每次产生新文件、运行目录、plan 或活动记录时，回复必须列出可点击的 Markdown 路径；不得只写裸路径或只写“已完成”。

科研结论单独使用：

```text
conclusion: SUPPORTED | REFUTED | INCONCLUSIVE | INVALID_IMPLEMENTATION | N/A
```

`run_status` 和 `conclusion` 不得混用。

### 4.1 递归可跳转链接

以活动记录作为“发生了什么”的导航入口，所有记录尽量形成双向链接：

```text
activity
 ├─→ plan / guidance（文档上下文）
 ├─→ experiment_log（科学证据）
 ├─→ decision_log（选择理由）
 ├─→ changed files（代码/配置/文档）
 └─→ run_id / output / config / manifest / summary
```

具体要求：

- 活动记录中的每个 `run_id` 必须链接到运行目录、`run_manifest.json`、`config.json` 和 `summary.json`（存在时）；
- 实验记录必须链接回对应的 `activity_id` 和所有关键 run；
- plan 定稿后应链接到其后续活动记录；
- AI 每次回复只要产生或更新 plan、activity、实验产物、运行目录或 manifest，就列出可点击的 Markdown 链接；
- 生成产物位于被忽略目录时仍提供路径链接；链接不存在或运行尚未完成时明确标注状态；
- 不在活动记录中复制大段指标或配置，使用链接和简短摘要保持导航可读。

## 5. JSON 职责草案

### 5.1 每个训练/评估/研究运行

- `config.json`：解析后的配置快照，回答“这次想运行什么”；保留给用户查看。
- `run_manifest.json`：运行 provenance 索引，回答“究竟由哪份代码、数据、资产、checkpoint 和配置产生”；不复制完整配置。
- `summary.json`：BaseRunner 在 train/eval 终态自动生成的最终快照，包含 `run_status`、最终指标、最佳 step、结论状态和关键产物入口，面向用户查看。
- `metrics.jsonl`：训练曲线和逐步指标，面向机器或绘图工具。

当前 `metadata.json` 暂时保留为兼容/机器快照；它与 cache 根的 `metadata.json` 不能混为同一职责。是否把运行目录中的 metadata 合并到 manifest，待消费者审计后再决定。

历史运行的 `ref2dex.run.v1` manifest 不回写、不迁移；本次不升级 schema，只把新字段作为向后兼容的可选字段。

### 5.2 数据和资产

- cache 根 `manifest.json`：来源、schema、split、坐标/单位、采样参数、数量、完成状态和文件摘要；
- 资产根 `asset_manifest.json`：外部模型/资产来源、版本、许可、路径和校验信息；
- `split.json`、`selection_*.json`：作为数据选择输入保留，并由 cache manifest 引用；
- 不把数据 manifest、运行 manifest 和实验日志互相替代。

## 6. `run_manifest` 与配置快照的边界

配置快照是“意图/参数”；run manifest 是“追溯索引”。manifest 应引用配置快照，而不是再次展开所有模型参数。
当前运行 manifest 保留 `ref2dex.run.v1` schema，并从配置中读取唯一的 `modification_version`；指导/plan
不再写入 manifest。以下字段作为后续运行入口可选扩展，只有消费者需要时才加入：

```text
modification_version
activity_id
experiment_id
parent_run
comparison_group
command
environment
```

不强制对大型 cache 全量计算 hash，但至少应对配置、数据 manifest、资产 manifest 和 checkpoint 做可选稳定摘要。
