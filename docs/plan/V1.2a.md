## 1. 背景与命名

本计划是已执行 V1.2 治理工作的后续补充，使用 `V1.2a`。指导字母后缀仅表示对同一基线
的补充，不会因为补充本身强制创建 plan；但已经定稿并执行的 plan 需要由后续指导改变其
实施合同或规范时，使用同一后缀建立后续计划。本计划据此采用 `plan/V1.2a.md`。

本分支从 `origin/oyx` 的干净基线建立，不继承未合并的 V1.2 Draft PR。该 PR 保持原状；
本计划只重建经本计划确认的治理合同，不能把旧分支的字段、记录或文档规则隐式带入。

本计划将 `work_version` 设为唯一版本术语。`git_commit` 是实现身份，`run_id` 是运行身份；
它们继续保留，但不属于 version 字段。

### 指导与 plan 的独立生命周期

- `指导/V<n><letter>.md` 是对同一基线指导的补充；读取时始终按无后缀、`a` 至最高确认
  后缀的顺序合并。补充指导本身不自动要求新建、重命名或复制 plan。
- 当一个计划在已有指导谱系（即使已经有 `a`、`b`、`c`）之后才协商定稿时，仍建立基线
  `plan/V<n>.md`；plan 不与每个既有指导补充一一对应。
- 如果基线 plan 已定稿并执行，之后的 `指导/V<n><letter>.md` 改变了可执行范围、保护项、
  风险、验证或回滚合同，才建立 `plan/V<n><letter>.md`。后缀与触发该变更的指导后缀相同，
  例如已执行 `plan/V1.2.md` 后，指导新增 `V1.2d.md`，使用 `plan/V1.2d.md`。
- 仅澄清意图、未改变已定稿实施合同的指导补充不产生 plan。计划草案在协商中原地修订；
  已定稿计划的合同发生变化时不得静默覆盖原文件，必须使用上述追加计划并获得用户确认。
- 开始 change、run 或 governance 时，先读取完整指导谱系，再读取基线最终 plan 与其中由
  后续指导实际触发的已确认计划补充；若任一文件内部冲突、或指导与计划无法同时满足，停止
  实施，在计划草案列出冲突、候选解释、拟定措辞、保护项、风险、验证和回滚，待用户确认。

## 2. 已确认范围

- 将当前规则、新代码配置、新写入的 manifest、Activity 与实验记录的规范字段统一为
  `work_version`；不再新增 `modification_version`、`research_version` 或
  `governance_version`。
- 将 `docs/current_versions.yaml` 的根与 Task 指针改为 `work_version`。本次根级治理工作
  指针为 `V1.2a`；不因该治理迁移改变 Task 的实际版本值或研究含义。
- 历史 Activity、旧日志、旧 plan、既有 run manifest、checkpoint 和 cache 保持只读，
  不批量回写。读取既有产物的代码可以把历史 `modification_version` 识别为兼容输入；
  所有新写入一律输出 `work_version`。
- 将 `docs/modification_policy.md` 的有效规则迁入现有
  `.agents/skills/research-change-control/` 与
  `.agents/skills/research-experiment-workflow/`；前者持有 change/governance、版本、记录和
  分支合同，后者持有 run 身份、manifest、状态和科学证据合同。
- 将 `docs/目录规范.md` 的目录、产物、manifest 与测试归属合同迁入
  `research-change-control` 的按需 reference；`research-experiment-workflow` 仅链接并按需
  读取该同一 reference，不复制规则。仓库继续只保留这两个 Skill。
- 审计两个 Skill 和根 `AGENTS.md` 的全部现行记录术语：长期工作单元只能使用
  `docs/activities/` 的独立 Activity，科学证据只能使用 `docs/experiments/` 的 experiment
  card；`logs/activity_log.md`、`logs/experiment_log.md` 及其他旧日志只可标为只读历史审计，
  不得再被写作当前入口、唯一时间线、必读上下文或新记录目标。
- 删除 `docs/modification_policy.md`、`docs/目录规范.md` 和
  `docs/ai_task_checklist.md`，并替换所有**当前规范入口**的引用。历史审计日志不回写；
  门禁必须把历史日志与 archive 排除在“当前链接必须可解析”的扫描范围之外。
- 更新 `AGENTS.md`、`docs/README.md`、`docs/项目总览.md`、两项 Skill、相关验证脚本和测试，
  使它们只指向两个 Skill、`current_versions.yaml`、当前 Task README、指导、plan、Activity
  和 experiment card。
- 本次形成一条根级 Activity，记录批准、迁移范围、验证、回滚入口与实际提交；不把命令、
  轮询或中间失败写入 Activity。

## 3. 实施步骤

1. 在两个现有 Skill 中建立不重复的权威规则：更新入口 `SKILL.md`，把较长的目录/产物合同
   移入 `research-change-control/references/`，并让 run Skill 指向同一 reference。逐条替换其中
   把 `activity_log.md` 或 `experiment_log.md` 当作现行记录的规则，统一为目录化
   Activity/experiment contract；旧日志仅保留历史审计表述。使用 Skill 校验器检查结构和
   frontmatter。
2. 重写根 `AGENTS.md` 为长期不变量和最小导航：四种模式、L0–L3、完整指导谱系读取、同文件
   冲突的暂停/计划/用户确认、`work_version`/`git_commit`/`run_id` 身份、分支保护、Activity
   与 experiment 的边界、以及唯一机器门禁。删除把 `activity_log.md` / `experiment_log.md`
   当作当前时间线、默认加载项或新记录目标的规则，明确其只读历史地位；明确 plan 与指导后缀
   不是强制一一对应的关系，并写入本计划“指导与 plan 的独立生命周期”规则。
3. 将当前文档、配置、运行 manifest 构建代码及其测试的规范字段从
   `modification_version` 改为 `work_version`。只在读取历史产物的边界保留窄兼容别名；不改变
   observation、action、reward、GT、坐标、单位、split、metric 或 checkpoint 解释。
4. 更新 `current_versions.yaml`、Task 当前状态页和现行入口链接；移除三份已迁入/废弃文档。
   对删除前的所有非历史引用做清单审计，确保不会留下当前入口的死链。
5. 强化 `tools/verify.py --changed` 与治理测试：检查新 Markdown/Skill 链接、当前 YAML/manifest
   的 `work_version` 合同、历史链接豁免范围、当前分支相对 `oyx` 的全量变更，以及 staged 内容。
   CI 安装测试收集所需依赖，并只把 verify 成功作为 PASS。
6. 更新或新增定向测试，运行格式、语法、YAML、链接、manifest 和 verify 检查；提交前审阅
   diff，检查 Skill/AGENTS 中没有把旧日志作为当前记录规则，并写根级 Activity。

## 4. 保护项

- 不改变任何 Task 的研究方法、模型、数据、observation、action、reward、GT、坐标、单位、
  split、指标、checkpoint 语义或实验结论。
- 不删除或重写历史日志、既有产物、cache、checkpoint、数据和用户已有修改。
- 不引入第三个 Skill，不在 `oyx` 直接开发，不合并或改写旧 V1.2 Draft PR。

## 5. 风险、验证与回滚

主要风险是字段迁移使旧配置或历史 manifest 不可读、删除文档造成当前链接断裂，以及 verify
的扫描范围错误地产生假 PASS 或误扫历史档案。通过读取兼容、定向单元测试、Markdown/Skill
链接审计、`git diff --check`、以及 `python tools/verify.py --changed` 处理。

回滚入口是本任务分支上的单个治理提交；未合并前直接关闭 PR 并保留旧分支。合并后使用一个
显式的反向治理提交恢复文件与字段兼容，不触碰历史数据或用户工作树。

## 6. 定稿条件

本计划已由用户确认。实施中若需要改变本计划的范围、保护项、兼容策略、验证或回滚，必须暂停并
以新的计划补充重新确认。
