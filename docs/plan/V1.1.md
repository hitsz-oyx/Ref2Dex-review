# Ref2Dex V1.1 治理收敛与文档记录迁移计划

> 状态：final；影响等级：L3（governance）；approval：user-approved；approved_at：2026-09-18 19:39 +0800。
>
> 本计划以 [V1.1 指导](../指导/V1.1.md) 为基础，并吸收 [V1.1a 补充指导](../指导/V1.1a.md)。用户于
> 2026-09-18 进一步确认：同一数值指导需要细化时，使用附加字母的独立指导文件，较后的字母具有更高优先级。

## 1. 目标与版本决定

根治理版本从当前的 `V1` 定为 `V1.1`。它标识本次仓库治理合同，不改变任何 Task 的
`research_version`、方法、数据、训练配置或实验结论。

本计划建立以下指导谱系规则：

- 数值基线指导命名为 `指导/V<major>.<minor>.md`，例如 `V1.1.md`。
- 对同一基线的已确认细化使用 `指导/V<major>.<minor><letter>.md`，例如 `V1.1a.md`。
- 后缀只使用单个小写 ASCII 字母 `a`–`z`。同一数值基线内，`V1.1z` 优先于 `V1.1y`，所有带字母的补充指导
  优先于无后缀的 `V1.1`；未定义的后缀不得自行解释。需要超过 `z` 时，创建下一个数值版本或取得用户决定。
- 补充指导只可澄清或追加约束；若改变 observation、action、reward、GT、坐标/单位、split、metric、checkpoint
  解释、planner formulation 或核心训练目标，必须建立新的 `research_version`，不能借字母后缀规避 L2。
- 当前实现使用的指导由已确认的同数值谱系文件共同构成。Agent 必须按“无后缀基线、`a` 至最高已有后缀”的顺序读取
  全部文件，不能只读取最新字母文件；Task README、plan 与 activity 必须链接实际适用的全部文件。
- 不同文件的要求冲突时，较后字母文件覆盖同一数值基线中较早文件的冲突部分，非冲突部分继续共同生效。覆盖只适用于
  明确冲突，不能据此删除、忽略或擅自扩展较早指导的其他约束。
- 同一指导文件内部存在互相冲突、无法同时满足或语义不充分的要求时，Agent 必须停止相关 change/run/governance
  实施，向用户指出冲突原文与受影响边界；不得以猜测、较晚段落或实现便利自行裁决。确认前先写（或修订）计划草案，
  列出冲突、候选解释、拟采用的准确措辞、保持不变项、风险、验证和回滚。用户确认后才可更新该指导文件、将计划定稿
  并继续实施；指导修订与实际实现完成后各写长期 Activity。

`V1.1a` 中“同一数值版本只保留一份权威指导、补充内容直接写入基线指导”的建议，与上述用户确认冲突；该建议将被
新治理规则取代。它关于 activity、experiment 与 work_version 的职责划分仍作为本计划的输入。

## 2. 范围

### 2.1 治理合同与导航

- 更新 `AGENTS.md`、两个 Skill、`docs/modification_policy.md`、`docs/README.md`、`docs/目录规范.md` 与
  `docs/current_versions.yaml`，使它们一致采用 `governance_version: V1.1`、research/git/run 三种身份、四种
  工作模式、L0–L3，以及指导字母后缀、全谱系读取、跨文件覆盖和同文件冲突确认规则。`AGENTS.md` 保留永久规则，
  `research-change-control` 明确计划、审批与 Activity 时机，`research-experiment-workflow` 明确 run 前必须完成
  适用指导冲突审查。
- 明确 `work_version` 是 research version 下可选的工作单元身份；它不替代 `research_version`，不进入
  `current_versions.yaml`，也不因普通命令或测试而自动创建。
- 更新 `tools/verify.py` 与治理测试，仅在文档目录与链接规则实际变化需要时调整；继续保持“本地仅检查本分支已暂存
  路径、CI 检查 PR 差异”的边界。

### 2.2 Activity 与 experiment 的目录化合同

- 将新 Activity 定义为值得长期追溯的完成工作单元；重要治理、代码/配置变更、正式指导修订、重要诊断事实与重要
  操作各写一份独立记录。普通命令、单次 pytest、轮询、临时失败和逐 checkpoint 进度不创建 Activity。
- 为根和每个 Task 定义统一的 `activities/README.md` 索引与独立 Activity 文件格式；每个新 Activity 包含目标、变更、
  保护语义、验证、branch/commit 与结果。根 Activity 记录跨 Task/治理事实，Task Activity 记录最近作用域事实；不以
  CmResidual 或任何单一 Task 作为规范前提。Activity 与 experiment 分别回答“做了什么”和“知道了什么”。
- 为根和每个适用 Task 定义 `experiments/README.md` 索引与独立 experiment card 结构。一个 experiment 可以链接多个
  run，但不把实现工作、单次命令或 run 生命周期混写为科学结论。
- 既有 `logs/activity_log.md`、`experiment_log.md` 与历史记录保留只读审计价值，不回填、不批量拆分；根和每个 Task 的
  README 将明确区分 legacy 入口与新目录化入口。规范立即适用于新记录；历史目录的物理迁移按作用域逐步进行，现有链接
  优先保持有效，如必须移动则先更新全部受影响链接并验证。

### 2.3 计划、历史冲突与活动记录

- 新根计划以本文件为准。当前工作树中仍可见的 `docs/plan/V1.2.15.md` 与新版本身份冲突；经本计划确认后删除该旧
  计划，而不是修改其历史内容。Git 历史是可恢复入口。
- 不修改用户维护的 `docs/指导/V1.1.md` 或 `V1.1a.md` 正文。新规则写入治理合同；后续新的补充指导由用户创建。
- 本计划草案不写 Activity。实施完成后，为本次 V1.1 治理迁移写一份根 Activity；以后每个符合新定义的根或 Task
  工作单元都在最近作用域写独立 Activity，记录真实 approval、范围、验证、分支、提交与回滚入口。

## 3. 保护边界

- 不修改任何 Task 的 `research_version`、研究指导内容、模型、observation、action、reward、GT、坐标、单位、
  split、cache/schema、指标、checkpoint 解释、训练/评估实现或已有科研结论。
- 不覆盖或暂存当前工作树中已有的 CmResidual、ObjectInteractionCm、ObjectInteractionCmv2、IsaacGym、版本指针、
  Task 日志、计划、指导或未跟踪文件。
- 不删除数据、cache、outputs、checkpoint、原始日志或历史运行。仅在批准后删除已确认过时的根计划
  `docs/plan/V1.2.15.md`。
- 不批量重写历史 `activity_log.md`、`experiment_log.md` 或归档；迁移从新的目录化记录开始。

## 4. 实施顺序

1. 审阅并确认本计划；确认前不实施 L3 合同、目录或历史计划删除。
2. 以最小差异更新根治理规则、版本指针和文档导航，并删除已确认过时的 `V1.2.15.md`。
3. 建立根与 Task 通用的目录化 Activity/experiment 规则、索引和模板；在不批量迁移历史记录的前提下，为现有各级
   README 提供统一的 legacy/新记录导航约定，不将规范局限于 CmResidual。
4. 调整 verify 与治理测试以覆盖新增的链接、路径和文档合同；不扩大到不相关 Task 测试。
5. 对本次明确文件执行 `git diff --check`、YAML/Markdown 链接审计、定向治理测试和
   `python3 tools/verify.py --changed`；写完成 Activity，审阅暂存范围并交接。

## 5. 风险、验证与回滚

| 风险 | 缓解 | 验证 | 回滚 |
| --- | --- | --- | --- |
| 补充指导优先级被误读 | 用固定文件名语法、单字母排序与 README 链接列出适用指导 | 针对规则的治理测试、Markdown 链接审计 | 回退本次治理 diff |
| 目录迁移破坏历史导航 | 不批量移动或改写历史记录；变更链接逐一检查 | `audit_diff.py --check-links`、`verify --changed` | 回退新增索引/记录；原文件仍在 |
| 旧计划与新合同并存造成歧义 | 明确删除 `V1.2.15.md` 并在新 Activity 记录 supersession | `rg` 检查旧计划引用与链接审计 | 从 Git 恢复该文件 |
| 工作树已有改动被混入 | 只暂存本计划的显式路径 | `git status`、`git diff --cached --name-only` | 从暂存区移除明确路径，不触碰用户改动 |

## 6. 审批请求

确认后将执行上述 L3 治理迁移。它会改变的只有治理/文档合同、根治理版本和已确认过时的根计划；保持所有研究语义和
用户现有工作树改动不变。
